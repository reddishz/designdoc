# 系统架构描述规范

本页定义系统层的架构描述方式、系统级标识（`SYS-CON` / `SYS-ADR`）与修订追溯规则。系统架构层回答「整个系统为何存在、由哪些子系统组成、各自职责边界是什么、如何协作、共同遵守哪些约束，以及关键系统决策为何如此」，**不替代**子系统内部的 `design-doc` 设计。

> 本规范借鉴 ISO/IEC/IEEE 42010 的架构描述思路（利益相关者与关注点、多视角表达、架构决策与依据、跨视图对应关系），全部规则自包含于本页，不要求查阅外部标准原文。

## 目录与权威边界

```text
ued/
├── README.md                         # 系统入口、子系统注册表（5 列）、系统发布索引
├── glossary.md                       # 全系统唯一术语表
├── architecture/                     # 系统层专属目录（非 design-doc 作用域）
│   ├── system-architecture.md        # 系统架构描述（职责分配与系统约束的唯一真源）
│   └── SYS-ADR-001-{slug}.md         # 系统级架构决策（按需）
├── releases/
│   └── sys-v1.0.yaml                 # 系统组合锁（绑定 architecture_rev）
├── references/                       # 系统级原始外部资料
└── {subsystem}/                      # 子系统：完整 design-doc 作用域
```

- `ued/architecture/` 是系统层保留目录，**MUST NOT** 登记为子系统，也 **MUST NOT** 建立 `L0-vision/`–`L6-verification/`、`baselines/`、编码计数器或全局编码索引。
- 系统层与子系统层的文档扫描相互隔离：`SYS-CON` 与 `SYS-ADR` 属于系统级命名空间，不进入任何子系统的编码集合。

## `system-architecture.md` 规范

### 元信息与四态

文档顶部 **MUST** 包含固定元信息表：

```markdown
| 字段 | 值 |
|------|----|
| 文档名称 | {project_name} 系统架构描述 |
| 状态 | 正式 |
| 修订版本号 | 1 |
| 最后更新 | 2026-11-24 |
| 规范版本 | 2.1 |
```

`规范版本` 记录本篇已迁移或核对到的 system-design-doc 规范版本（裸数字，与 `SKILL.md` 的 `metadata.version` 同形），规则见 [spec-upgrade.md](spec-upgrade.md)。它是迁移元信息：只改它不递增 `修订版本号`、不追加修订记录、不影响 `architecture_rev`。

`状态` 沿用四态语义，不另造新状态枚举：

| 状态 | 含义 |
|------|------|
| `初稿` | 尚未形成可供子系统承接与发布的有效系统架构 |
| `正式` | 当前有效的系统架构依据 |
| `草案` | 已有正式架构，当前正在讨论下一次实质性架构变更 |
| `废弃` | 整个系统架构已停用，保留历史追溯 |

- 存在任意 `正式` 子系统时，`system-architecture.md` **MUST** 存在且状态为 `正式`（若当前正在讨论下一版而处于 `草案`，其 `修订记录` 中 **MUST** 至少存在一条 `正式` 修订）。
- 历史正式修订不因当前文档进入 `草案` 而失效。

### 章节结构（必选与按需）

| 章节 | 要求 | 内容与口径 |
|------|------|------------|
| `## 系统定义` | **MUST** | 系统定位、整体目标、系统内外边界、核心涉众与系统级场景 |
| `## 子系统职责分配` | **MUST** | 以 `subsystem_key` 为主键的唯一权威职责分配表（见下节） |
| `## 系统交互` | **MUST** | 子系统协作关系、数据/事件/控制流与契约归属；若子系统间确无直接交互，**MUST** 显式声明「无直接交互」而非留空编造 |
| `## 系统级约束` | **MUST** | 跨子系统的强制性规则与全局要求（以 `SYS-CON-xxx` 承载）；确无独立于子系统的全局约束时，**MUST** 显式声明「暂无独立系统级约束」 |
| `## 系统级质量属性` | MAY | 仅在存在跨子系统整体性能、可靠性、安全、数据一致性或演进要求时填写 |
| `## 系统集成验证` | MAY | 跨子系统端到端闭环场景与验收口径；具体验证结果仍挂发布说明或 EVAL |
| `## 修订记录` | **MUST** | 可机检的固定格式历史修订表，作为 `architecture_rev` 的追溯真源 |

### 子系统职责分配表（唯一真源）

`system-architecture.md` 的「子系统职责分配」表是子系统角色与边界的**唯一权威来源**。系统根 `README.md` 不再重复职责正文。

```markdown
## 子系统职责分配

| subsystem_key | 系统角色 | 核心职责 | 明确非职责与边界 |
|---------------|----------|----------|------------------|
| w3data | 数据供应 | 行情采集、清洗与标准化供应 | 不做策略判断与交易执行 |
| w3sentinel | 风险判定 | 风险评估、风控规则判定与风险触发 | 不直接执行交易订单 |
| w3trade | 交易执行 | 订单执行、账户状态管理与执行级保护 | 不绕过风控独立做风险信号判定 |
```

规则：
- 表中 `subsystem_key` **MUST** 已在系统根注册表登记，且不得重复。
- 注册表中每个 `正式` 子系统的 `subsystem_key` **MUST** 出现在本表中，且 `系统角色`、`核心职责`、`明确非职责与边界` 三列均 **MUST** 非空。
- 注册表中 `初稿` 子系统可暂未补全（检查器报 WARNING），但激活为 `正式` 前 **MUST** 补齐。
- 子系统内部的 `L2` / `L3` 负责承接和落实分配给自己的职责，**MUST NOT** 自行改写或扩大系统层分配的职责边界；子系统内部的 `CMP` 仅用于定义内部逻辑组件。

### 系统交互表达

系统交互描述的是**架构协作关系**，不等同于单向的版本依赖（`depends_on`）；交互允许双向存在。

```markdown
## 系统交互

| 提供方 | 消费方 | 交互目的 | 方式 | 契约 |
|--------|--------|----------|------|------|
| w3data | w3trade | 提供标准化行情数据 | 数据订阅 | W3D-IF-001 |
| w3sentinel | w3trade | 下发风险触发与拦截指令 | 控制调用 | W3S-IF-001 |
| w3trade | w3sentinel | 上报订单执行与持仓状态 | 事件通知 | W3T-IF-003 |
```

规则：
- `提供方` / `消费方` 填已登记的 `subsystem_key`；涉及系统外部角色/第三方服务时，以 `external:{名称}` 或「外部：…」显式标注。
- 接口字段、协议与行为契约的权威定义仍留在提供方子系统的 L4 文档中；系统层 **MUST NOT** 复制字段明细。
- `契约` 列 **SHOULD** 指向提供方的具体全量编码（如 `W3T-IF-003`），便于检查器核验目标存在且归属提供方。
- 若子系统间确无直接交互，可不写交互表，在章节内显式说明原因。

## 系统级标识（`SYS` 命名空间）

系统层保留前缀 `SYS`（任何子系统的 `编码前缀` **MUST NOT** 使用 `SYS`）。`SYS` 不是 `design-doc` 的新项目编码前缀，而是系统级标识空间，仅包含两种标识：

| 标识 | 格式 | 定义位置 | 定位 |
|------|------|----------|------|
| `SYS-CON` | `SYS-CON-{2~4位数字}` | `ued/architecture/system-architecture.md` | 跨子系统的强制性约束与全局要求（不等同于全部系统级需求；系统目标与场景先以结构化正文表达，不急于引入 `SYS-FR`/`SYS-NFR`） |
| `SYS-ADR` | `SYS-ADR-{2~4位数字}` | `ued/architecture/SYS-ADR-{序号}-{slug}.md` | 影响多个子系统或决定系统整体组织方式的架构决策 |

### `SYS-CON` 定义格式

每条 `SYS-CON` 在 `system-architecture.md` 的「系统级约束」章节内定义，**MUST** 在标题行上方放置匹配的小写锚点，确保子系统可稳定跳转：

```markdown
<a id="sys-con-001"></a>
### SYS-CON-001：全系统统一使用 UTC 时间基准

- **约束说明**：所有子系统在持久化、跨子系统事件与接口时间戳中必须统一采用 UTC，禁止隐式本地时区。
- **适用范围**：w3data、w3sentinel、w3trade
- **落实要求**：各子系统在自身 L2/L4 中落实对应校验与契约，并在 `来源` 中回指本约束。
```

- 编号全系统唯一，不可重复；废弃后保留编号不复用。
- 子系统 **MUST NOT** 定义任何 `SYS-*` 编码。

### `SYS-ADR` 文档规则

`SYS-ADR` 借用 ADR 形式记录跨子系统决策，**不进入**任何子系统的 ADR 计数器或全局编码索引：

- 文件路径：`ued/architecture/SYS-ADR-{序号}-{slug}.md`（例如 `SYS-ADR-001-separate-risk-and-execution.md`），文档元信息中的 `文档编码` **MUST** 与文件名序号一致（如 `SYS-ADR-001`）。
- 元信息字段：`文档编码`、`状态`（四态：`初稿` / `正式` / `草案` / `废弃`）、`修订版本号`（正整数）、`最后更新`、`规范版本`（见 [spec-upgrade.md](spec-upgrade.md)）、`影响范围`（填受影响的 `subsystem_key` 列表，不得只写中文简称）。
- 正文最小结构：背景与问题、决策内容、考虑过的备选方案、决策理由、影响范围与落地要求、关联 `SYS-CON` 与子系统文档、变更记录。
- 生命周期：已被新决策替代的 `SYS-ADR` **MUST NOT** 删除，状态改为 `废弃` 并在元信息或正文注明替代决策（如 `替代方案：SYS-ADR-004`）。

**系统级 ADR 与子系统级 ADR 的作用域边界**：
- 影响多个子系统、改变子系统拆分/合并、决定跨子系统通信模式或信任边界 → **系统级 `SYS-ADR`**；
- 仅影响单一子系统内部实现（如订单状态机、本地存储选型）→ **子系统级 L3 `ADR`**。

## 子系统如何合规引用系统层

子系统文档（L2/L3/L4/L5）可在 `来源`、`依赖` 或正文中通过标准 Markdown 链接引用 `SYS-CON` 与 `SYS-ADR`。下例的相对路径以文档位于 `ued/{subsystem}/L{n}-{层名}/` 为前提（向上两级到 `ued/`）；文档位置不同时按实际层级调整 `../` 的个数，子系统根 `README.md` 则只需一级 `../`：

```markdown
- **来源**：[SYS-CON-001（全系统统一使用 UTC 时间基准）](../../architecture/system-architecture.md#sys-con-001)
- **来源**：[SYS-ADR-001（风险判定与交易执行分离）](../../architecture/SYS-ADR-001-separate-risk-and-execution.md)
```

在子系统文档末尾的「本文引用」钉住表中按跨作用域对象登记，钉住对应的系统修订号：

```markdown
| 引用对象 | 类型 | 所在文档 | 钉住代际 | 钉住日期 |
|----------|------|----------|----------|----------|
| SYS-CON-001 | 细项 | system-architecture | 1 | 2026-11-24 |
| SYS-ADR-001 | 文档 | — | 1 | 2026-11-24 |
```

**双检查器分工**：
- `design-doc/scripts/check_docs.py` 将 `SYS-*` 视为跨作用域编码放行，要求契约位置引用进入「本文引用」表，且在系统根 `--cross-scope-deps` 模式下跳过 `ued/architecture/`；
- `system-design-doc/scripts/check_system.py` 校验 `SYS-CON` / `SYS-ADR` 的定义位置、唯一性、锚点可达性、以及子系统引用目标是否存在（普通引用悬空报 WARNING，`依赖` 行悬空或指向尚未正式的架构报 ERROR）。

## 修订记录与 `architecture_rev` 追溯

`system-architecture.md` 末尾 **MUST** 保留固定四列「修订记录」表（倒序排列）：

```markdown
## 修订记录

| 修订号 | 日期 | 版本类型 | 变更摘要 |
|--------|------|----------|----------|
| 2 | 2026-11-24 | 正式 | 拆分风险判定为独立子系统 w3sentinel（见 SYS-ADR-001） |
| 1 | 2026-10-01 | 正式 | 初始系统架构：确立 w3data 与 w3trade 职责边界与核心约束 |
```

规则：
1. **何时递增**：任何影响系统定义、子系统职责分配、系统交互、系统级约束的实质性变更，或改变当前有效架构的 `SYS-ADR` 落地，**MUST** 递增 `修订版本号` 并追加一行修订记录；纯文字润色、排版或链接修复可不递增。
2. **历史不可篡改**：已记录的修订行 **MUST NOT** 删除或悄悄改写，确保历史系统发布能够还原当时依据的架构演变脉络。
3. **`版本类型`**：取 `正式` 或 `初稿`；只有 `版本类型 = 正式` 的修订号可被 `releases/sys-vX.Y.yaml` 的 `architecture_rev` 引用。
4. **发布绑定**：新建系统发布 `sys-vX.Y.yaml` **MUST** 填写 `architecture_rev`，指向当时有效的正式架构修订号；检查器会校验该修订号在修订记录中真实存在、非未来修订且为 `正式`。
