# 系统架构、结构与发布审查

先跑检查器，再按本清单人审。检查器通过不代表架构划分、职责边界、交互完整性与接口语义正确。

## 验证职责边界

- **结构与架构一致性验证**：注册表、`system-architecture.md` 与职责分配覆盖、`SYS-*` 命名空间、版本钉住、发布闭合、`architecture_rev` 追溯、跨子系统编码唯一性——由 `check_system.py` 自动完成。
- **架构合理性验证**：子系统划分是否合理、职责是否存在重叠或灰区、跨子系统约束是否真正落实、`SYS-ADR` 理由是否充分——由人工评审完成。
- **契约验证**：接口字段、类型、行为与兼容性——由提供方子系统 L4 `IF` / `ACT` 定义、评审与测试完成；checker 不判断语义。
- **集成验证**：特定版本组合的实际运行结果与跨子系统端到端闭环——由系统集成验证记录、L6 / EVAL 与发布说明记录；checker 不代替。

```bash
python3 .agents/skills/system-design-doc/scripts/check_system.py -p ued
python3 .agents/skills/system-design-doc/scripts/check_system.py -p ued --print-member-commands
python3 .agents/skills/design-doc/scripts/check_docs.py -p ued --cross-scope-deps
```

第三条是 `design-doc` 的只读跨作用域细项 `依赖` 检查（自动跳过 `ued/architecture/`）：把各子系统的 `依赖` 合成一张图，只判环与「`正式` / `草案` → 他子系统 `初稿`」。目标存在性、前缀归属与 `SYS-*` 命名空间由 `check_system.py` 负责。

## 结构

- [ ] `ued/README.md` 有「当前结构」说明与系统架构入口，明确这是系统 + 子系统。
- [ ] 系统根**没有** `产品版本`、`baselines/`、`文档索引`、`编码计数器`、`全局编码索引`。
- [ ] 系统根没有 `L0-vision/`–`L6-verification/` 设计作用域。
- [ ] `ued/architecture/` 仅包含 `system-architecture.md` 与 `SYS-ADR-*.md`，未演变成第二套 `design-doc` 作用域。
- [ ] 每个子系统目录都是 `ued/` 直接子目录，没有嵌套子系统。
- [ ] 没有未登记的目录（`architecture/`、`references/`、`assets/`、`releases/`、`deprecated/` 除外）。
- [ ] 没有固定 `shared/` 特殊概念；共享库只是普通子系统。

## 注册表

- [ ] 五列齐备：`subsystem_key` / 子系统名称 / 目录 / 编码前缀 / 状态；**无**旧 `角色文档` 列。
- [ ] 键、目录、前缀各自唯一；键未复用；前缀未使用保留词 `SYS`。
- [ ] 每个目录存在且含 `README.md`。
- [ ] 前缀与子系统 README 的 `project_code` 一致（都空或都同值）。
- [ ] 状态只取 `初稿` / `正式` / `废弃`，无 `草案`。
- [ ] `正式` 子系统均有系统架构职责分配、`产品版本`、对应基线。
- [ ] `废弃` 子系统目录与文档仍保留，且不出现在新发布中。

## 系统架构、职责与交互（重点人审）

- [ ] `ued/architecture/system-architecture.md` 存在且有效（有 `正式` 子系统时架构文档已正式或已有正式修订）；必选章节（系统定义、子系统职责分配、系统交互、系统级约束、修订记录）齐备。
- [ ] 注册表中每个 `正式` 子系统均在职责分配表中写清系统角色、核心职责、明确非职责与边界；README 未重复维护第二份职责正文。
- [ ] 子系统职责无重叠、无三不管灰区；子系统内部 `CMP` 只描述内部逻辑组件，未再承担系统级角色定义。
- [ ] 系统交互完整表达了关键协作关系（含数据流、事件流、控制流与必要的双向协作），未把交互误等同于单向 `depends_on`；确无交互时已显式说明。
- [ ] 跨子系统接口契约权威定义在提供方子系统 L4，系统交互只引用全量编码（如 `W3T-IF-001`），未复制接口字段。
- [ ] 跨子系统硬约束已定义为 `SYS-CON-*`（带匹配 `<a id>` 锚点），受影响子系统已在其文档落地并在 `来源` 回指 + 记入「本文引用」钉住表。
- [ ] 重大跨子系统架构取舍（拆分/合并、通信模式、信任边界等）已由 `SYS-ADR-*` 记录，影响范围使用 `subsystem_key`，被替代决策标为 `废弃` 且注明替代方案。
- [ ] 架构实质变更已递增 `修订版本号` 并在固定格式修订记录表留痕；历史修订未被篡改。

## 依赖

- [ ] 每个 `正式` 基线有 `depends_on` / `external_deps`（无依赖写 `[]`）。
- [ ] 依赖目标已登记且 `正式`；目标 `vX.Y` 基线存在。
- [ ] 无自依赖、无重复、无外部名冲突。
- [ ] 跨子系统 `依赖` 目标（含 `SYS-*`）存在且归属正确。
- [ ] 冻结后依赖变化通过新基线表达，不是 PATCH；冻结前修正没有改 `items` 或升版本。
- [ ] 环依赖已评估；不应存在的已消除。
- [ ] 细项 `依赖` 图跨子系统无活跃环，且无「`正式` / `草案` 细项 `依赖` 他子系统 `初稿` 细项」（`--cross-scope-deps`）。

## 系统发布

- [ ] 新发布清单已填写 `architecture_rev`，且对应修订号在 `system-architecture.md` 修订记录中真实存在、`版本类型 = 正式`，且不大于当前修订号。
- [ ] 发布清单每项在发布时均为 `正式`，且不含 `初稿`；不要求覆盖全部正式成员。
- [ ] `product_version` 与 `full_version` 一致，后者在 `patch_log` 中。
- [ ] `depends_on` 目标在清单中且版本一致。
- [ ] 清单内子系统的 `external_deps` 全覆盖且无冲突。
- [ ] 文件名、`release` 字段、README 发布索引一致；历史发布清单未被修改。
- [ ] MAJOR 接口变更的消费者均已适配并更新钉住。
- [ ] 若声称已通过系统集成验证，发布说明指向覆盖本次组合的验证记录或 EVAL / L6 证据。

## 编码与术语

- [ ] 子系统定义使用自己的前缀且不含 `SYS-*`；子系统内部可简写，跨子系统与系统级引用写全量编码。
- [ ] 同一完整编码只在一个子系统中定义；`SYS-CON` / `SYS-ADR` 仅在 `ued/architecture/` 定义。
- [ ] `ued/glossary.md` 全系统唯一；子系统没有自己的 glossary。
- [ ] 术语 `定义位置` 指向的文档存在且唯一。
- [ ] 每个子系统 `design-doc` 检查通过（使用 `--glossary`）。

## 常见驳回

- 注册表仍保留旧 `角色文档` 列，或继续用子系统内部 `CMP` 冒充子系统系统角色。
- `ued/README.md` 与 `system-architecture.md` 两处各写一套子系统职责。
- 系统根放了 `产品版本`、`baselines/` 或 L0–L6 文档；或把系统级约束塞给某个普通子系统代管。
- 共享库被建成特殊 `shared/` 作用域。
- 子系统在内部定义 `SYS-*` 编码，或引用了不存在的 `SYS-CON` / `SYS-ADR`。
- 新建系统发布未填写 `architecture_rev`，或引用了 `初稿`/不存在的架构修订号。
- 用 PATCH 改了依赖钉住，或在基线进入系统发布组合后原地改依赖。
- 发布后直接修改已发布清单，或篡改 `system-architecture.md` 的历史修订记录。
