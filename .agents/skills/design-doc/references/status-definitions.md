# 状态值标准定义

## 状态值原则

- **单一枚举**：所有对象共用同一套生命周期状态（四态），不为个别类型另设状态集合
- **一致性**：同类型文档使用相同的状态值集合
- **明确性**：每个状态值有清晰的定义、权限边界与修订号后果
- **渐进性**：状态流转遵循对象生命周期规律
- **记录与生命周期分离**：描述事实进展的字段是**记录型字段**（见 [记录型字段](#记录型字段不参与冻结)），不参与冻结。记录型字段 **MAY** 有封闭值域（如 PLN `落实情况` 的 `未落实` / `已落实`、L6 `追溯状态` 的三值），但 **MUST NOT** 与生命周期语义重叠、**MUST NOT** 被当作决定可编辑性与可否删除的第二套状态枚举使用（原 PLN `规划状态` 即因此删除）
- **字段按写入者分类**：对象种类与字段写入者总表单点在 [object-model.md](object-model.md)；本文只保留状态机、记录型/流转伴随的**含义与初值**、门控与修订号判定表。产品版本见 [product-version.md](product-version.md)

## 标准四态（唯一生命周期状态集合）

| 状态值 | 英文对照 | 定义 | 是否冻结 |
|--------|----------|------|----------|
| **初稿** | New | 已分配编码、**从未定过稿**的创作态 | 否 |
| **正式** | Approved | 已定稿的基线，可被引用 | 是 |
| **草案** | Draft | **从 `正式` 解冻、或从 `废弃` 受控复活而来的迭代态**，与修订号递增严格对应 | 否 |
| **废弃** | Deprecated | **默认终态**，原地保留备查，不可作为引用依据；受控复活是唯一例外 | 是 |

> `初稿` 与 `草案` 都是未冻结态，区别只在**是否曾定过稿**：`初稿` 从未进入基线（可改标题、可直接作废），`草案` 曾进入基线后重开（标题锁定，只能定稿、废弃，或走[维护性变更](#维护性变更第三维度mandatory)做非语义文字维护）。两者都 **MUST NOT** 删除——放弃的唯一通道是**作废**（→ `废弃`）。
>
> `废弃` **默认**是终态：需重新承担同等职责时，默认新建对象并分配新编码。只有满足 [废弃后受控复活](#废弃后受控复活受控mandatory) 的全部条件，才允许**原对象复活**（`废弃→草案`）。

四态只回答**生命周期位置**，不含「不改含义的文字维护」——后者是与之正交的记录维度，见 [维护性变更](#维护性变更第三维度mandatory)。

## 状态即基线（冻结规则，MANDATORY）

对象的 `状态`（文档）/ `细项状态`（编码）是其**唯一冻结判据**，**与版本库（git/svn）无关**。是否递增修订号、是否走废弃流程，只看状态，不看是否已提交。产品版本不参与冻结，见 [product-version.md](product-version.md)。

- **状态是基本元素（MUST 存在）**：每份文档必有 `状态`，每个编码细项必有 `细项状态`；**新建即默认 `初稿`**。
- **`细项状态` 的承载位（MUST 两处）**：清单 / 全局索引表的 `细项状态` 列与定义块内的 `- **细项状态**：{值}` 属性行**都是必备**承载位，缺任一处即违规；块内属性行 **MUST** 是属性行组的**首行**（治理段第一位，见 [coding-system.md · 细项定义块形态](coding-system.md#细项定义块形态mandatory)）。两处取值 **MUST** 一致，不一致由工具报「同一编码状态不一致」。细项废弃时块内的 `- **细项状态**：废弃` 已由本条覆盖，废弃登记字段紧随治理段与（有则）维护段、谱系段之后、与废弃对象同处（字段为 `废弃时间` / `废弃类别` / `废弃原因` / `替代方案`，见 [item-deprecation.md](item-deprecation.md)）。
- **缺字段的判定（历史版本差异）**：按 `变更记录` 判定——有定稿条目 → 按 `草案` 对待；从未定稿 → 按 `初稿` 对待；无法判定 → **按 `草案` 对待**（保守侧：可编辑正文，但不得改标题）。缺字段对象一律纳入定稿确认并补齐字段，不作为阻断性错误。
- **解冻通道（修订）**：要改已 `正式` 对象的内容，先执行 `正式→草案` 解冻（属受控状态变更，须请求确认，**此时该对象 `修订版本号` +1**），改完再 `草案→正式` 定稿。解冻确认 **MUST** 做被依赖预审（见 [本文引用 · 审查与定稿时机](coding-system.md#审查与定稿时机)）。
- **废止 ≠ 修订**：`正式` 对象若要**彻底退场**，走 `正式→废弃`（不必先解冻）；若要**改**，走 `正式→草案`。`草案` 对象既可 `草案→正式` 定稿（沿用解冻后的号），也可直接 `草案→废弃`（**最后修订号即该草案号**）。**MUST NOT** 把修订号或内容改回解冻前：未采用的改法在草案期内改正文后再定稿，或走作废。
- **复活 ≠ 撤销废弃**：`废弃` 对象默认不复用。只有满足 [废弃后受控复活](#废弃后受控复活受控mandatory) 时，才执行 `废弃→草案`（**该对象 `修订版本号` +1**，并写 `复活时间`）。复活 **MUST NOT** 直接到 `正式`，**MUST NOT** 清除原废弃登记字段。
- **编码冻结时机**：编码一经分配即**永久占用**——**ID 与类型码**从分配那一刻起不可手改，**存在性**从分配那一刻起不可删除，`初稿` 期亦无例外。放弃一个对象的唯一通道是**作废**（→ `废弃`）：编号原地保留、永不复用给**其他对象**，因此序列**不会**因作废而产生缺口。受控复活沿用原编码与原对象，不是复用；锁定细则见 [object-model.md · 锁定矩阵](object-model.md#锁定矩阵mandatory)。
- **定稿提示（审查 / 校验时 MANDATORY）**：审查或校验文档时，凡遇到未冻结对象（`初稿`、`草案`，含**缺 `状态` 字段而按上述规则对待**的对象），**MUST** 主动提示用户"该对象尚待定稿"，请其确认。此为提醒而非强制——是否升 `正式` 由人决定；AI **MUST NOT** 自行把 `初稿` / `草案` 改成 `正式`。
  - AI 完成一轮修改后的**交互式提交前定稿确认流程**见 [lifecycle.md](workflows/lifecycle.md)。
  - **未冻结对象 MUST NOT 作为实现依据**——单点表述于 [implement-from-design.md](workflows/implement-from-design.md)。

## 锁定矩阵（MANDATORY）

见 [object-model.md · 锁定矩阵](object-model.md#锁定矩阵mandatory)。治理段四行的写入者分类见同文件「字段（按写入者）」；`细项状态` 变更仍须遵守本文 [层级门控](#层级门控文档状态--细项状态mandatory)，流转伴随写入时机见 [流转伴随字段](#流转伴随字段只随指定转换写入)。

## 层级门控（文档状态 × 细项状态，MANDATORY）

细项的状态机与文档的状态机**同构**，且文档状态门控细项状态：**解冻自顶向下、定稿与整份废止自底向上**。

| 方向 | 顺序 | 规则 |
|------|------|------|
| **解冻（修订内容）** | 文档 → 细项 | 要改细项的内容，细项 **MUST** 处于 `初稿` / `草案`；细项解冻（`正式→草案`）**MUST** 先解冻所在文档（`正式→草案`，文档 `修订版本号` 在此 `+1`）。因此**细项 `草案` 而文档 `正式`** 是结构违规。本轮若文档仍为 `正式` 而细项因修订 `+1`，则文档 **MUST** 已同轮解冻并 `+1`；仅当文档本轮已是 `草案` 时，可只刷文档 `最后更新`（文档号不再加）。同一解冻轮次内文档号只 `+1` 一次 |
| **定稿（形成基线）** | 细项 → 文档 | 文档定稿（`→正式`）**MUST** 以「本文档全部细项 `细项状态` ∈ {`正式`, `废弃`}」为前置，且[本文引用](coding-system.md#本文引用跨文档钉住mandatory)已按该节「文档定稿」对齐；未满足时 **MUST** 列出缺口并提示用户确认（含[须人审](coding-system.md#须人审不能靠号)） |
| **废止（整份文档）** | 细项 → 文档 | 文档 `→废弃` **MUST** 以全部细项已 `废弃` 为前置（缺状态视为未废弃）。活细项未清零时 **MUST NOT** 改文档 `状态`，也 **MUST NOT** 为过门批量作废细项。非细项正文是否仍当依据属须人审。步骤见 [doc-deprecation.md · 整份废弃的前置](doc-deprecation.md#整份废弃的前置mandatory) |

- **新增细项同受门控**：新增即修改文档内容，因此向已 `正式` 的文档新增细项 **MUST** 先解冻文档。
- **依据方向同受门控（细项 × 细项）**：`正式` / `草案` 细项的**正文段与内容段属性行** **MUST NOT** 引用 `初稿` 细项——`初稿` 的业务含义仍可改，据它定稿等于把基线建在流沙上；要引用，先把它定稿。**豁免只覆盖**追溯段的 `出处` / `来源` 与记录型字段 `落实记录`（溯源与过程记录；二者若同受约束，互相回指的两项会谁都定不了稿）。追溯段的 **`依赖` 不豁免**：它是生效前提，`正式` / `草案` **MUST NOT** `依赖` `初稿`。
- **PLN 的定稿前置只看状态、不看落实**：想法一经定论即可定 `正式`（无论是否已展开），因此活跃追踪中的 PLN **不会**阻塞文档定稿；`初稿` 只剩「想法内容尚未写清」一种含义，阻塞定稿是合理的。`落实情况` 是记录型字段，**MUST NOT** 参与定稿前置判据（见 [type-profiles.md · 规划项生命周期](type-profiles.md#规划项生命周期pln-统一口径)）。
- **整份废止同受门控**：与定稿对称，收口自底向上。文档可以保持 `正式` 而全部细项已 `废弃`（空壳基线；定稿门控仍满足）。误把仍含活细项的文档标成 `废弃` 时，存量修正是恢复文档状态，不是杀掉活细项。
- **门控只约束顺序与前置**：文档与细项仍各自独立流转、修订号各自独立计数（见 [变更流程与版本号](#变更流程与版本号统一mandatory)）；门控 **MUST NOT** 被用来替代变更评审与影响分析。

## 记录型字段（不参与冻结）

以下字段描述事实进展或登记信息，**追加或修改都不触发解冻、不递增修订号**，即使在 `正式` / `废弃` 态也可直接维护：

| 字段 | 所属对象 | 含义 |
|------|----------|------|
| `变更记录` | 全部对象 | 修订历史，**MUST** 完整保留（不得删改历史行）；语义行首列记本文档 `修订版本号`，维护性变更写 `{当前修订号}（维护）` 行（见 [维护性变更](#维护性变更第三维度mandatory)） |
| `曾用名` | 发生过命名维护的细项 / 术语块 | 旧名与停用日期，按时间倒序；随维护直接追加，不解冻、不加修订号 |
| `最后更新` | 文档 | 文档级 last-edit：**任何一次编辑都更新它**——含记录型字段追加与废弃登记（废弃时即废弃发生的时间），即使该次编辑不解冻、不加修订号。与细项 `最后修订日期`（只记 `修订版本号` 递增那天）分工不同，**MUST NOT** 互相代替；细项治理段第四行 **MUST** 是 `最后修订日期`，**MUST NOT** 填本字段 |
| `引入版本` / `退出版本` | 文档与全部编码细项 | **基线缓存**：升产品版本时对 `added` / `removed` 回写，便于就地查阅；切片真源仍是 `baselines/vX.Y.yaml`，冲突以基线为准；定稿 **MUST NOT** 手填；见 [product-version.md](product-version.md) |
| `产品版本` | 作用域 README | 产品级发版标签；见 [product-version.md](product-version.md) |
| `废弃时间` / `废弃类别` / `废弃原因` / `替代方案` | 已废弃对象 | 废弃登记。`废弃类别` 为封闭枚举（见 [item-deprecation.md · 废弃类别](item-deprecation.md#废弃类别封闭枚举mandatory)）；`废弃原因` 为一句话说明，**MUST 非空**；`替代方案` 同时承载 ADR「取代」语义 |
| `复活时间` | 曾经废弃并已受控复活的细项 / 文档 | 记录**最近一次** `废弃→草案` 复活的日期；每次复活都刷新；与 `废弃时间` 一样是记录型，不是正文依据 |
| `落实情况` | PLN 细项 | 想法是否已全部展开为具体细项：`未落实` / `已落实`（**终局判定**）；与 `细项状态` **正交**，不参与冻结 |
| `落实记录` | PLN 细项 | 落实的**过程时间线**：展开时写入日期与目标细项编码，可多条；`落实情况` 为 `已落实` 时 **MUST** 非空 |
| `建议复审日期` | PLN 细项 | `落实情况` 为 `未落实` 且非 `废弃` 者的时间兜底；到期只提示复核，不自动改状态 |
| `来源版本` / `获取日期` / `最近核验日期` / `复查周期` / `失效风险` | REF | 参考资料时效登记，用于评估是否过期 |
| `追溯状态` | L6 追溯矩阵 | 需求与验证要素的追溯覆盖情况 |
| `本文引用` | 文档 | 跨文档契约链接的钉住代际与日期；形态与时机见 [coding-system.md · 本文引用](coding-system.md#本文引用跨文档钉住mandatory) |
| `状态`（注册表列） | 应用注册表行 | 应用登记条目的生命周期位置 |

- `创建日期` / `修订版本号` / `最后修订日期` **不属本类**：它们是[流转伴随字段](#流转伴随字段只随指定转换写入)，只由创建动作或指定的状态转换写入，在 `正式` / `废弃` 态同样 **MUST NOT** 单独改动。

## 状态流转规则

> **格式说明**：使用 Mermaid stateDiagram-v2 语法，确保 AI 解析准确性和可执行性。
> - 支持状态机语义，明确状态转换条件
> - 可视化渲染后人机可读
> - 避免箭头文本图的歧义问题
>
> **简化流程规则**：
> - **单行流程**（无分支、无跳转、无循环）：可使用简化箭头形式 `A → B → C`
> - **复杂流程**（有分支、跳转或循环）：必须使用 Mermaid 图表
> - **多步骤流程**：也可使用表格形式，步骤清晰列示

### 统一状态机（适用所有对象）

```mermaid
stateDiagram-v2
    [*] --> 初稿 : 创建（分配编码，修订号 1）
    初稿 --> 初稿 : 原地编辑（含改标题，不加修订号）
    初稿 --> 正式 : 定稿（不加修订号）
    初稿 --> 废弃 : 作废（编号原地保留、永不复用；MUST NOT 删除）
    正式 --> 草案 : 解冻（修订号 +1）
    草案 --> 草案 : 原地修订（不加修订号）
    草案 --> 正式 : 定稿（沿用当前修订号）
    草案 --> 废弃 : 直接废弃（最后修订号 = 该草案号）
    正式 --> 废弃 : 废弃流程（类别 + 原因 + 替代方案）
    废弃 --> 草案 : 受控复活（条件全满足；修订号 +1；写复活时间）
```

> **放弃本轮修订**：没有单独的状态动作。在 `草案` 期内把内容改回上一 `正式` 基线后再 `草案→正式` 定稿（修订号沿用解冻时已 `+1` 的号），或 `草案→废弃`。文档与细项的 `修订版本号` **均不得改小**。
>
> **复活是受控例外**：`废弃→草案` 仅在 [废弃后受控复活](#废弃后受控复活受控mandatory) 的条件全部满足时允许，**MUST NOT** 以「先复活再说」规避新建对象；不满足条件时走新建（分配新编码）。

### 废弃后受控复活（受控，MANDATORY）

`废弃` 默认是终态。只有**下列条件全部满足**时，才允许把**原对象**从 `废弃` 改回 `草案`（`废弃→草案`）：

| # | 条件 | 判定 |
|---|------|------|
| 1 | 需求基本没变 | 业务含义、适用范围、对象类型码与标题**基本不变**；只是原废弃判断不再成立或需要继续迭代 |
| 2 | 原废弃原因已消除 | 原 `废弃原因` 指出的问题已解决，或原废弃判定有误；**MUST** 在变更记录写清依据 |
| 3 | 无生效替代 | `替代方案` 为「无」，或替代对象也已 `废弃` / 不适用；有生效替代时 **MUST** 改替代对象或新建 |
| 4 | 未归档或可确认误归档 | 细项仍在原文档；文档尚未移入 `deprecated/`，或虽已移入但可确认为误归档 / 归档后无替代且满足条件 1–3 |
| 5 | 不是换皮新需求 | 若含义、范围、类型码或标题需实质变化，或已有生效替代，**MUST** 新建对象并分配新编码，**MUST NOT** 借用旧编码 |

**执行（MANDATORY）**：

1. 暂停确认：列明原废弃登记、复活理由与受影响引用方，取得人确认。**MUST NOT** 自作主张复活。
2. 改状态：`废弃→草案`，该对象 `修订版本号` **+1**（与解冻同为递增时机）；写 `复活时间` = 当天；**MUST NOT** 直接到 `正式`。
3. 保留历史：`废弃时间` / `废弃类别` / `废弃原因` / `替代方案` **MUST** 原样保留，**MUST NOT** 删除或改写（可作为「上次废弃」历史）；标题去掉 `~~已废弃~~` 后缀；删除「本文档已废弃」类横幅。
4. 清理派生状态：若对象上 `退出版本` 有值，**MUST** 清空（下一次升产品版本时按 `added` 回写）；同步清单表、全局索引、应用注册表与 `deprecated/README.md`（文档已归档时先移回原位）。
5. 文档复活按细项粒度：文档 `废弃→草案` 时，只有确需继续使用的细项各自 `废弃→草案`（各自 `+1`）；其余细项保持 `废弃`。文档状态取 `草案`，其 `修订版本号` `+1` 一次。
6. 更新 [本文引用](coding-system.md#本文引用跨文档钉住mandatory)：确认兼容性后按新修订号更新钉住行；引用方仍需遵守下方「引用废弃对象」禁令，直到本对象重新定稿。

- **MUST NOT**：以复活代替新建来规避新编码；复活后跳过 `草案` 直接 `正式`；清除废弃历史；复活仍被产品基线 `removed` 且无新版本计划的对象（先确认产品版本动作）。
- **与新建的取舍**：需求基本不变 → 复活原对象；需求已变、类型变了、或有生效替代 → 新建。两者都不允许删除原编码。

### 各对象的定稿与废弃语义

四态适用于所有对象，下表只说明各对象在关键转换上的**业务含义**（不改变状态机）：

| 对象 | `初稿→正式` 的含义 | `正式→废弃` 的含义 |
|------|-------------------|-------------------|
| L0-L6 文档 / 细项 | 评审通过，成为可引用基线 | 内容不再适用 |
| ADR | 决策被采纳 | 决策失效（`废弃类别` + `废弃原因`）或被新决策替代（`废弃类别：被替代`，`替代方案` 用链接指向新 ADR，即原「取代」语义）；评审未通过亦记 `废弃` + `废弃类别：评审未通过` + 原因（即原「拒绝」语义） |
| REF | 来源与适用边界核验通过 | 资料过时或不可靠 |
| PLN 细项 | 想法已定论、纳入规划库活跃追踪（**不表示已落实**，落实与否见记录型字段 `落实情况`） | 不再纳入产品演进（`废弃类别` + `废弃原因` 记决策依据）；已落实者作为历史规划档案保持 `正式`，**落实本身不是废弃**——仅当想法连同其落地物一并被推翻时才 `废弃`，此时 `落实情况` 保留事实值 `已落实` |

### 需求追溯状态（记录型）

L6 是**设计文档**层级，记录验证策略与追溯覆盖关系，**不记录测试执行结果**（通过 / 失败 / 缺陷数属测试管理系统的职责）。

| 状态值 | 英文对照 | 含义 |
|--------|----------|------|
| **未追溯** | Untraced | 需求尚未建立与验收标准 / 测试场景 / 设计要素的链接 |
| **已追溯** | Traced | 双向追溯链接齐备 |
| **不适用** | Not Applicable | 该项无需独立验证覆盖 |

追溯矩阵列：`需求编码 | 需求标题 | 验收标准 / 测试场景 | 设计要素 | 追溯状态 | 备注`。其中「验收标准 / 测试场景」是**定义**，不是执行记录。

### 应用注册表状态（记录型）

注册表行的 `状态` 列直接取四态，不设专属枚举：`初稿`（已登记、尚未启用）、`正式`（在用）、`废弃`（已停用，保留登记以供追溯）；`草案` 亦合法（登记信息需修订时）。

## 变更流程与版本号（统一，MANDATORY）

状态与修订号**不绑定**，但递增时机封闭：**`正式→草案` 解冻** 与 **`废弃→草案` 受控复活** 是修订号仅有的两个正规递增时机。文档与细项共用同一套整数 `修订版本号`；产品级 `vX.Y` 见 [product-version.md](product-version.md)，**MUST NOT** 写在设计文档元信息里，也 **MUST NOT** 与修订号混用。

> **辅助文档例外**：全局术语表 `ued/glossary.md` **无四态**，新建 `修订版本号` 为 `1`，每次**实质变更** `+1` 并同步 `变更记录`；非实质维护可写 `N（维护）` 行（见 [维护性变更](#维护性变更第三维度mandatory)）。整数、单调、不跳号、不改小的通则仍适用。细则见 [glossary-conventions.md](glossary-conventions.md)。

| 变更动作 | 状态流转 | `修订版本号` | 说明 |
|----------|----------|--------------|------|
| 新建对象 | → `初稿` | 起始 `1` | 新建即 `1` + `初稿` |
| 初稿期修改（含改标题） | `初稿` 原地 | **不递增** | 同一创作过程，零抖动 |
| 定稿 | `初稿→正式` | **不递增** | 状态升格本身即一次变更 |
| 作废（初稿期放弃） | `初稿→废弃` | **不递增**（保持 `1`） | 从未进入基线；编码原地保留、永不复用 |
| 解冻修订 | `正式→草案` | **+1**（递增时机之一） | 与旧基线区别，解冻时加一次 |
| 草案期修订 | `草案` 原地 | **不递增** | 同一修订轮次内反复修改 |
| 再次定稿 | `草案→正式` | **不递增** | 沿用解冻后的号 |
| 废止 | `正式→废弃` | **不递增** | 保留原修订号并标注废弃 |
| 废止修订中的对象 | `草案→废弃` | **不递增** | **最后修订号即该草案号**（如 `2`） |
| 受控复活 | `废弃→草案` | **+1**（递增时机之二） | 须全部满足复活条件；同时写 `复活时间` |

- **递增基准**：以该对象当前修订号为基准，单调、不得改小；解冻或复活 **MUST** `+1`，**MUST NOT** 跳号，也 **MUST NOT** 写成 `vX.Y`。
- 状态表达**生命周期位置**，修订号表达**开锁代际**；二者正交。修订号不是正文指纹（初稿期与草案期内改正文都不改号），正文是否仍成立须人审。
- **MUST NOT** 再用主 / 次版本表达设计对象代际；产品换代问询见 [product-version.md · 升产品版本](product-version.md#升产品版本mandatory)。

**示例**：修订号 `1` 的 `正式` → 解冻 → `2` 的 `草案` → 定稿 → `2` 的 `正式`。放弃本轮则草案期内改回再定稿，仍为 `2` 的 `正式`（**不是**回到 `1`）；或 `草案→废弃`，最后修订号为 `2`。

### 流转伴随字段（只随指定转换写入）

**流转伴随字段**是状态转换的投影：由状态机在**指定的那一次转换**里写入，人 **MUST NOT** 把它当作独立的编辑对象。与[记录型字段](#记录型字段不参与冻结)的分界在**写入者**，不在「像不像正文」——记录型由人在任意状态追加，流转伴随只随转换写入。

| 字段 | 所属对象 | 初值 | 写入时机 |
|------|----------|------|----------|
| `修订版本号` | 文档 | `1` | 创建；此后只在本对象 `正式→草案` 解冻或 `废弃→草案` 受控复活那一刻 `+1`（同一轮次只一次） |
| `创建日期` | 文档 | 创建当天 | 创建时写入一次，此后 **MUST NOT** 修改 |
| `修订版本号` | 编码细项 | `1` | 创建；此后只在本细项 `正式→草案` 解冻或 `废弃→草案` 受控复活那一刻 `+1` |
| `创建日期` | 编码细项 | 新建当天 | 创建时写入一次，此后 **MUST NOT** 修改 |
| `最后修订日期` | 编码细项 | 新建当天 | 随细项 `修订版本号` 成对写入，取递增那天 |

文档 **MUST NOT** 再设元信息 `版本`（`vX.Y` 留给[产品版本](product-version.md)）。文档开锁日期记在 `变更记录`，**MUST NOT** 另造文档级「最后修订日期」（`最后更新` 仍是任意编辑）。

- **MUST NOT 当作独立的修改请求**：**MUST NOT** 以「更新修订号 / 修订日期」为由单独改动它们；需要它们变化，就去执行对应的状态转换。
- **维护性变更不写这些字段**：非语义文字维护只追加 `变更记录` 维护行与 `曾用名`，**MUST NOT** 改动本节任一字段（见 [维护性变更](#维护性变更第三维度mandatory)）。
- **只在那一次转换里写入**：写入时机只有两种转换——**创建**（进入 `初稿`，写初值 `1` / 当天；文档与细项的 `创建日期` 都只有这一次）与**重新开锁**（`正式→草案` 解冻，或 `废弃→草案` 受控复活）。文档开锁一轮 → 文档 `修订版本号` `+1` 一次；本轮实际被解冻 / 复活的细项 → 各自 `+1`，其余细项不动。文档已是 `草案` 时再改别的细项，只刷文档 `最后更新`，**MUST NOT** 再给文档加号。定稿、作废、升产品版本 **MUST NOT** 改这些字段。文档与细项的 `修订版本号` **均不得改小**，**MUST NOT** 互相推导。
- **可机检的只有不变式**（`初稿` → `修订版本号` = `1`、`草案` → ≥ `2`、细项 `最后修订日期` 不晚于本文档 `变更记录` 最新日期；细项 `草案` 而文档 `正式` = 门控违规；`复活时间` 非空 ⇒ `废弃时间` 非空且该对象曾经历 `废弃`；`状态` 仍为 `废弃` 时 `废弃时间` **MUST NOT** 早于 `复活时间`）；「`正式` 态被单独 `+1`」无法从快照判定，由本节禁令约束。

### 细项修订版本号（与文档修订号独立演化）

细项 `修订版本号` 与文档 `修订版本号`、[产品版本](product-version.md) 各自独立：单个整数、新建为 `1`、每轮解冻或受控复活 `+1`。细项号与 `创建日期` / `最后修订日期` 同属流转伴随。散文里可简称「修订号」，属性名 **MUST** 用全称 `修订版本号`。

| 变更动作 | 细项状态流转 | `修订版本号` | `创建日期` | `最后修订日期` |
|----------|--------------|--------------|-----------|----------------|
| 新建细项 | → `初稿` | `1` | 新建当天 | 新建当天 |
| 初稿期修改 | `初稿` 原地 | **不变** | **不变** | **不变** |
| 定稿 | `初稿→正式` | **不变** | **不变** | **不变** |
| 作废（初稿期放弃） | `初稿→废弃` | **不变**（保持 `1`） | **不变** | **不变** |
| 解冻修订 | `正式→草案` | **+1**（递增时机之一） | **不变** | 更新为解冻当天 |
| 草案期修订 | `草案` 原地 | **不变** | **不变** | **不变** |
| 再次定稿 | `草案→正式` | **不变** | **不变** | **不变** |
| 废止 | `→废弃` | **不变** | **不变** | **不变**（作废时间由 `废弃时间` 记录） |
| 受控复活 | `废弃→草案` | **+1**（递增时机之二） | **不变** | 更新为复活当天（同时写 `复活时间`） |

- **递增时机与文档修订号完全一致**（`正式→草案` 解冻、`废弃→草案` 受控复活），但粒度不同：文档开锁一轮只 `+1` 一次；只有本轮**实际被解冻或复活**的细项各自 `+1`，其余不动。
- **状态与修订号的一致性（可机检）**：`细项状态` = `初稿` → **MUST** = `1`；`细项状态` = `草案` → **MUST** ≥ `2`；`最后修订日期` **MUST NOT** 晚于本文档 `变更记录` 的最新日期。文档元信息 `修订版本号` 对文档 `状态` 遵守同一组不变式。
- **修订必须成对**（细项）：`修订版本号` `+1` 时 **MUST** 同步把 `最后修订日期` 更新为当天；反之 **MUST NOT** 只改日期不改号。`创建日期` **MUST NOT** 随解冻改动。
- **用途**：下游只在[本文引用](coding-system.md#本文引用跨文档钉住mandatory)钉住对方当前修订号（细项钉细项号，整份 ADR/REF 钉文档号）；链接与清单 **MUST NOT** 另写修订号。

## 维护性变更（第三维度，MANDATORY）

**维护性变更（Maintenance Change）** 指**不改变设计语义**的文字维护：改标题措辞、改术语名称、统一用语、修正引用路径或链接文本、调整不改变含义的结构顺序等。它**留下修改记录，但不产生新的修订号**，也不改变状态、基线成员与钉住代际。

| 轴 | 回答 | 何时变化 |
|----|------|----------|
| 生命周期状态 | 对象在哪个阶段 | 定稿 / 解冻 / 作废 / 复活 |
| 内容代际（`修订版本号`、基线 `revision`、`本文引用` 钉住） | 含义改到第几代 | 解冻 / 复活 |
| **维护性变更** | 不改含义的前提下做过哪些文字维护 | 每次维护追加一条维护行 |

维护性变更与四态**正交**：`初稿` / `正式` / `草案` / `废弃` 的对象都可做，做完仍是原状态、原修订号。它与「纯格式调整」不同——后者不写任何记录；维护性变更 **MUST** 留下可追溯记录。

### 语义不变判据（MANDATORY）

只有下列**全部不变**，才算维护性变更：适用范围、行为、输入与输出、约束、验收口径、数值、模态词（应当 / 必须 / 不得）、量词、接口、依赖、术语定义、类型码、基线成员身份。

任一项变化 → **不是**维护性变更，按原通道处理：`初稿` / `草案` 直接改；`正式` 先解冻（`修订版本号` +1）；含义根本变化 → 废弃 + 新增编码。**拿不准时按语义变更处理**。

### 变更记录中的维护行（MANDATORY）

维护性变更**不新开表、不另设小节**，记录仍写在对象的 `变更记录` 中，用**维护行**与语义行区分：

| 行种类 | 首列 | 何时写 | 修订号 |
|--------|------|--------|--------|
| 语义行 | `13` | 创建、解冻、复活、定稿等 | 该对象的 `修订版本号` |
| **维护行** | `13（维护）` | 每次维护性变更 | **不变**，取维护发生时的当前修订号 |

- **形态**：`{当前修订号}（维护）`，**MUST** 用全角括号、括号前不留空格；`13(维护)`、`13 （维护）`、`维护` 均为非法。维护行属于**文档级** `变更记录`（细项没有独立变更记录），记录的是**该文档**当前的 `修订版本号`。
- **说明格式**：`MNT-YYYY-MM-DD-NN {类型}：{说明}；语义不变`。
  - `MNT-日期-序号` 是**维护批次号**：同一天的同一次维护，在全部受影响文档与术语表中共用同一个批次号；`NN` 两位，当天从 `01` 起。
  - `{类型}` 取封闭枚举：`命名维护` / `文字维护` / `引用维护` / `结构维护`。
  - 说明 **MUST** 以 `；语义不变` 收尾。
- **排序**：与语义行同表倒序。维护行归入其修订号所在的代际块——同一修订号下，维护行在语义行之**上**（发生更晚），多条维护行按批次日期倒序；更早代际的语义行在其下。
- **引用号必须存在**：维护行的数字 **MUST** 是该文档 `变更记录` 中已出现的语义行修订号（`初稿` 即 `1`），**MUST NOT** 为维护凭空造号。
- **只动记录**：维护行只更新文档 `最后更新`；**MUST NOT** 改动 `修订版本号`、`创建日期`、细项 `最后修订日期`、`状态` / `细项状态`、基线 `items`、`本文引用` 钉住行。
- **历史不可改**：维护行是记录型字段，追加后 **MUST NOT** 删改；后续语义变更照常在其上方追加语义行。

### 曾用名（记录型，MAY）

发生命名维护时，对象 **SHOULD** 在原地保留旧名：

- 形态：`旧称（至 YYYY-MM-DD）；旧称（至 YYYY-MM-DD）`，按时间倒序；日期取该名称停用当天。
- 位置：细项定义块的**维护段**（治理段之后、发版谱系段之前，见 [coding-system.md · 细项定义块形态](coding-system.md#细项定义块形态mandatory)）；文档术语块内作为独立属性行，位于 `英文名称` 之后。
- `曾用名` 是记录型：随维护直接追加，不解冻、不加修订号；它不改变当前标题 / 名称，也不参与标题锁定与索引比对。
- 全局术语表不增设 `曾用名` 列，旧名登记在《补充信息》的同名条目。

### 执行约束（MANDATORY）

1. **人工批准**：先提出维护方案（批次、清单、影响面与语义不变论证），取得人确认后执行；AI **MUST NOT** 自行发起批量改名。
2. **隔离**：一次维护 **MUST** 单独成批，**MUST NOT** 与语义修改、状态转换、基线动作混在同一改动或同一提交中。
3. **全文扫描**：改名前 **MUST** 用 `--refs` 反查全部引用并全文检索旧称；同步修正链接文本、清单、索引、术语表与正文使用处。
4. **同批原子完成**：跨文档的同一批次 **MUST** 一次改完；遗漏即缺陷，不得以「下次再补」收尾。
5. **复核语义不变**：按《语义不变判据》逐项核对；无法确认时停下，改走语义通道。
6. **记录**：在每个受影响对象的 `变更记录` 追加同一批次号的维护行，并刷新文档 `最后更新`。

流程与检查清单见 [maintenance-change.md](workflows/maintenance-change.md)。

### 术语改名

- 对**术语表**：改名是实质变更，`修订版本号` +1，写普通语义行；旧名登记在《补充信息》。
- 对**设计文档与细项**：使用新名属维护性变更，写 `N（维护）` 行，`修订版本号` 不变。
- 两者 **MUST** 使用同一维护批次号以便跨文档追溯；术语表自身的 `修订版本号` 与该批次号无关。

### 与基线、钉住的关系

- 维护性变更 **MUST NOT** 改动 `baselines/vX.Y.yaml`：成员集合与 `revision` 均不变，[增量计算](product-version.md#快照-schema)只看 revision，不会把标题维护计入 `changed`。
- 基线 `items.title` 是**写入时的快照**，允许暂时落后于现行标题；下一次 PATCH / MINOR 重写 `items` 时自然刷新。实现门禁比对 `code` / `revision`，不比对标题。
- 维护性变更 **MUST NOT** 改动 `本文引用`：钉住的是修订号，不是标题文本；引用方的链接文本随全文扫描同步即可。

### 可机检的不变式

- 维护行首列 **MUST** 匹配 `^{\d+}（维护）$`；数字 **MUST** 存在于该文档的语义行。
- 维护行 **MUST NOT** 参与状态 / 修订号推断：文档 `修订版本号` 与**最新语义行**比对，不受维护行影响。
- 同一修订号块内，维护行 **MUST** 位于语义行之上；维护行之间按批次日期倒序。
- `曾用名` 每条 **MUST** 匹配 `.+（至 YYYY-MM-DD）`，且位于规定段位。
- 记录格式与引用号类由 `check_docs.py` 报 WARNING（存量不阻断）；段位类（`维护段位置错乱`、`维护段重复`）报 ERROR。以上只是机检下限，最终仍以人审为准。

## 废弃与归档

| 对象 | 处理 |
|------|------|
| 细项 | **原地标注 `废弃` 即可**，不归档、不删除，留在设计文档中备查；细则见 [item-deprecation.md](item-deprecation.md) |
| 文档 | 两阶段：先原地标 `废弃` 并给出**建议归档日期**（不移动），到期后移入本作用域 `deprecated/`（只移除不删除）；细则见 [doc-deprecation.md](doc-deprecation.md) |
| `初稿` 对象 | 尚未发布、不构成基线，但**同样 MUST NOT 删除**：走同一废弃流程——细项原地标 `废弃`（标题加 `~~已废弃~~` 后缀、原标题保留）；文档原地标 `废弃` + **建议归档日期**，到期移入 `deprecated/`。差别只在 `废弃类别` 取 `初稿作废`、`废弃原因` 记「初稿期作废」、`修订版本号` 保持 `1` |

- 废弃后 `最后更新` 表示废弃发生的时间。
- **废弃默认是终态**：需重新承担同等职责时，默认新建对象并分配新编码（旧编号永不复用给其他对象）。仅当 [废弃后受控复活](#废弃后受控复活受控mandatory) 的条件全部满足时，才允许原对象 `废弃→草案`。

## 状态变更权限

1. `初稿→正式`（定稿）：审核者批准
2. `初稿→废弃`（作废）：对象创建者或项目负责人
3. `正式→草案`（解冻）：对象负责人发起，须请求确认，并在该时刻将该对象 `修订版本号` `+1`
4. `草案→正式`（定稿）：审核者批准
5. `正式→废弃`、`草案→废弃`：项目负责人（ADR 由架构师或技术委员会）
6. `废弃→草案`（受控复活）：对象负责人发起，须按 [废弃后受控复活](#废弃后受控复活受控mandatory) 逐条举证并请求确认；在该时刻将该对象 `修订版本号` `+1` 并写 `复活时间`
7. 记录型字段维护：对象负责人。其中 README `产品版本`、`baselines/vX.Y.yaml` 与对象上 `引入版本` / `退出版本` 缓存只由[升产品版本](product-version.md#升产品版本mandatory)写入（本身不解冻）；定稿与日常编辑 **MUST NOT** 手改谱系两列。`复活时间` 例外：由第 6 条复活动作写入
8. 流转伴随字段（文档 / 细项 `修订版本号`、文档与细项 `创建日期`、细项 `最后修订日期`）：无独立维护权限，只由创建动作与第 3、6 条的开锁动作写入
9. `追溯状态` 变更：验证负责人
10. 维护性变更（非语义文字维护）：对象负责人提出方案、人审批准后执行；只追加维护行与 `曾用名`，单独成批，不改状态与修订号（见 [维护性变更](#维护性变更第三维度mandatory)）

> 以上十项没有任何一项能**删除**一个已分配编码的对象或一份已建档的文档——放弃只能走作废（→ `废弃`）。

## 模板更新说明

所有模板中的状态字段应使用上述标准值，格式为：

- 文档元信息：`状态` = `初稿/正式/草案/废弃`，**新建默认 `初稿`**；`修订版本号` 起始 `1`（**MUST NOT** 再写 `版本 | vX.Y`）。产品切片见 `baselines/`（[product-version.md](product-version.md)）；**MUST NOT** 预填 `引入版本` / `退出版本`（由升版回写）。EVAL 另填 `对照版本` / `评估日期` / `评估类型`（见 [type-profiles.md · EVAL](type-profiles.md#eval-与-adr--ref--tc--met)），定稿表示可作证据引用、不进基线 `items`
- 细项清单：`细项状态` = 同上四态（清单表 **MUST** 含该列，但 **MUST NOT** 增设 `修订版本号` / `创建日期` / `最后修订日期` 列——修订信息只在定义块治理段承载）
- 本文引用：清单之后、变更记录之前（见 [coding-system.md · 本文引用](coding-system.md#本文引用跨文档钉住mandatory)）
- 细项定义块：治理段首四行固定为 `细项状态` / `修订版本号` / `创建日期` / `最后修订日期`；其后 MAY 接维护段（`曾用名`）、发版谱系段（`引入版本` / `退出版本`，升版回写；新稿省略）；废弃时废弃登记段再其后；追溯段固定在末尾（见 [coding-system.md · 细项定义块形态](coding-system.md#细项定义块形态mandatory)）
- 变更记录：语义行首列为整数 `修订版本号`；维护性变更追加 `{当前修订号}（维护）` 行，**MUST NOT** 新开维护表或维护小节（见 [维护性变更](#维护性变更第三维度mandatory)）
- L6 追溯矩阵：字段名 `追溯状态`，取值 `未追溯/已追溯/不适用`
- 应用注册表：字段名 `状态`，取值同上四态
- REF 细项：四态 + 记录型时效字段（`来源版本` / `获取日期` / `最近核验日期` / `复查周期` / `失效风险`）

## 存量文档迁移

本版本把各类型的专属状态枚举统一为标准四态，旧写法按下表就地改写。**迁移只改状态值与字段名、只补新增的治理段字段**，MUST NOT 借此改动标题或编码。

| 存量写法 | 迁移为 | 说明 |
|----------|--------|------|
| `草稿` | 按 `变更记录` 判定 | 有定稿条目 → `草案`；从未定稿 → `初稿`；无法判定 → `草案` |
| ADR `提议` | `初稿` | |
| ADR `采纳` | `正式` | |
| ADR `拒绝` | `废弃` + `废弃类别：评审未通过` + `废弃原因` | 评审未通过 |
| ADR `取代` | `废弃` + `废弃类别：被替代` + `替代方案` | `替代方案` 用链接指向新 ADR |
| REF `登记中` | `初稿` | |
| REF `有效` | `正式` | 迁移时 MUST 一并补齐五个时效字段 |
| PLN `规划状态` | **删除该字段** | `待考虑` → `初稿` + `落实情况：未落实` + `建议复审日期`；`已纳入规划` → `正式` + `落实情况：未落实` + `建议复审日期`；`已落实` → `正式` + `落实情况：已落实` + `落实记录`；`不再考虑` → `废弃` + `废弃类别：其他` + `废弃原因` |
| PLN `正式` 但 `落实记录` 为「无」 | **保持 `正式`** + 补 `落实情况：未落实` + `建议复审日期` | 旧口径要求「定稿与落实同步」，故判为违规；新口径下这是「已定论、活跃追踪中」的**合法态**。确已落实者补 `落实情况：已落实` + `落实记录`，并在目标细项补 `来源` 回指 |
| PLN 缺 `落实情况` | 补该字段 | `落实记录` 非空且想法已全部展开 → `已落实`；否则 → `未落实`。**MUST NOT** 因补该字段而改动 `细项状态` |
| L6 `验证状态` | 列名改 `追溯状态` | `待验证` → `未追溯`；`已验证` → `已追溯`；原「失败」等执行结果移出设计文档 |
| 注册表 `应用状态` | 列名改 `状态` | `使用中` → `正式`；`已停用` → `废弃` |
| `建议移除日期` | `建议归档日期` | 归档只移除不删除 |
| 缺 `修订版本号` / `创建日期` / `最后修订日期` | 补 `修订版本号`（`草案` 填 `2`，其余填 `1`）+ `创建日期` / `最后修订日期` = 本文档 `变更记录` 最新日期（缺日期时取本文档 `创建日期`） | 细项级修订历史无法回溯，一律自迁移起开始计数；`草案` 必然经历过一次解冻故为 `2`。**MUST NOT** 追溯猜测更早的修订轮次 |
| 文档元信息 `版本 | vX.Y` | 改为 `修订版本号` 整数：变更记录中每次解冻顺位 → `1, 2, 3…`；仅 `v1.0` 且无解冻 → `1` | 主 / 次语义改由[产品版本](product-version.md)承担；**MUST NOT** 把 `v2.0` 映射成修订号 `2` |
| 缺 README `产品版本` / `baselines/` | 补 README `产品版本`；用当时全部 `正式` 细项生成首份 `baselines/vX.Y.yaml` | 对象上 `引入/退出` 由下次升版回写；切片 SSoT 以 baselines 为准，**MUST NOT** 追溯猜测更早正文 |
| 编码序列存在缺口（旧规允许 `初稿` 删除、或分配时跳号所致） | 先用 `--refs` 反查缺号：确有对象 → 补齐清单表与全局索引条目；查无对象 → 补一条 `废弃` 占位细项 | 编号一经分配即永久占用，缺口不再是合法形态（工具报 ERROR）。占位块 = 治理段 + 废弃登记四字段：标题写「历史遗留占位」、`细项状态：废弃`、`修订版本号：1`、`创建日期` / `最后修订日期` 取本文档 `变更记录` 最新日期、`废弃时间` 填迁移当天、`废弃类别：其他`、`废弃原因` 记「历史遗留缺口登记」+ 可追溯到的缘由、`替代方案` 填「无」，并同步清单表与全局索引。**MUST NOT** 调低计数器去迁就缺口，也 **MUST NOT** 重编号后续细项 |
| 缺「本文引用」表 | 在清单之后、变更记录之前补表头；下次**文档定稿**前按 [本文引用](coding-system.md#本文引用跨文档钉住mandatory) 填行并人审兼容性 | 存量无表不阻断；钉住从补表当次起算，**MUST NOT** 追溯猜测更早的钉 |

- **不计作修订**：规范对齐属格式迁移，MAY 直接在原状态上改写，**不解冻、不加修订号、不写基线快照（除非本次任务就是建立首版基线）、不追加 `变更记录` 条目**。
- **不阻断校验**：`check_docs.py` 对上表旧值**不判为无效**，而是映射到四态后以 INFO「状态值待迁移」提示；旧列名 / 字段名则提示「追溯列名待迁移」「废弃字段名待迁移」。两类提示均不影响退出码，迁移完成后自行消失。
- **同作用域一次做完**：MUST 覆盖同一作用域内全部文档，避免新旧混用造成引用歧义。

## 国际化支持

为支持国际化协作和工具集成，建议在工具实现中使用以下英文对照：

- New / Approved / Draft / Deprecated（四态）
- Untraced / Traced / Not Applicable（`追溯状态`）
- Revision（`修订版本号`）/ Created（`创建日期`）/ Last Revised（`最后修订日期`）
- Product Version（`产品版本`）/ Product Baseline（`baselines/vX.Y.yaml`）
- Introduced In / Withdrawn In（基线缓存 `引入版本` / `退出版本`）
