# 状态值标准定义

## 状态值原则

- **一致性**：同类型文档使用相同的状态值集合
- **明确性**：每个状态值有清晰的定义和使用场景
- **渐进性**：状态流转遵循文档生命周期规律

## 状态即基线（冻结规则，MANDATORY）

对象的 `状态`（文档）/ `细项状态`（编码）是其**唯一冻结判据**，**与版本库（git/svn）无关**。是否递增版本、是否走废弃流程，只看状态，不看是否已提交。

| 状态 | 冻结 | 修改内容 | 删除 / 废止 | 版本递增 |
|------|------|----------|-------------|----------|
| **草稿** | 否（未发布的创作沙盒） | 直接原地修改，编码可增删改 | **直接删除即可**，不走废弃流程 | **不递增** |
| **正式** | 是（已发布基线） | 变更前 **MUST 先 `正式→草稿` 并同步提升版本号** 以示区别 | **MUST 走废弃流程**（细项原地保留 / 文档两阶段移除） | 解冻修订时递增 |
| **废弃** | 是（终态） | 不可改，只能新建 | 已由废弃流程处理 | — |

- **新建即草稿**：新建文档 / 细项默认 `草稿`；批准前的一切迭代都在草稿期完成，零仪式、零版本抖动。这直接根治"每次改动都 +1"与"修订中的草案误走废弃"。
- **解冻通道（修订）**：要像草稿一样大改已 `正式` 对象，先执行 `正式→草稿` 降级（属受控状态变更，须请求确认/相应权限），改完再 `草稿→正式` 升格。
- **废止 ≠ 修订**：`正式` 对象若要**彻底退场**，走 `正式→废弃`（直接进废弃流程，不必先降草稿）；若要**改**，走 `正式→草稿`（先解冻）。
- **编码冻结时机**：某编码的存在性与含义在其状态首次转为 `正式` 时锁定；此前（草稿）可自由增删改，不计缺口。
- **定稿提示（审查 / 校验时 MANDATORY）**：审查或校验文档时，凡遇到仍为 `草稿` 的文档或细项（含索引表状态列为 `草稿`、`细项状态：草稿`），**MUST** 主动提示用户"该对象尚待定稿（`草稿→正式`）"，请其确认是否定稿。此为提醒而非强制——是否升 `正式` 由人决定；AI **MUST NOT** 自行把 `草稿` 改成 `正式`。

## 标准状态值集合

### 1. 设计文档状态（L0-L6）

| 状态值 | 英文对照 | 含义 | 文档特征 | 备注 |
|--------|----------|------|----------|------|
| **草稿** | Draft | 工作版本，非正式 | 内容编写中，可修改 | 非正式版本，不可作为依据 |
| **正式** | Approved | 已批准，可引用 | 内容稳定，作为依据 | 正式文档，可作为上层引用 |
| **废弃** | Deprecated | 不再使用 | 保留备查，不可引用 | 保留历史记录 |

### 2. 架构决策记录状态（ADR）

| 状态值 | 英文对照 | 含义 | 使用场景 | 备注 |
|--------|----------|------|----------|------|
| **提议** | Proposed | 决策提出，等待讨论 | 新决策提案 | 可修改，征求意见 |
| **采纳** | Adopted | 决策确定，开始执行 | 决策正式通过 | 正式决策，指导设计 |
| **拒绝** | Rejected | 决策未被采纳 | 提议被明确否决 | 保留记录，说明拒绝原因 |
| **废弃** | Deprecated | 决策不再适用 | 被新决策替代 | 保留记录，说明原因 |
| **取代** | Superseded | 被其他决策替代 | 有更好的替代方案 | 标注替代决策编号 |

### 3. 外部参考资料状态（REF）

| 状态值 | 英文对照 | 含义 | 文档特征 |
|--------|----------|------|----------|
| **有效** | Valid | 可引用 | 当前有效的参考资料 |
| **废弃** | Deprecated | 不可引用 | 过时或不可靠，保留备查 |

### 4. 需求追溯状态

| 状态值 | 英文对照 | 含义 | 验证特征 |
|--------|----------|------|----------|
| **待验证** | Pending | 等待测试 | 新需求或修改后需求 |
| **已验证** | Verified | 测试通过 | 满足要求，可用于发布 |
| **失败** | Failed | 测试失败 | 需要修改或重新设计 |

## 状态流转规则

> **格式说明**：使用 Mermaid stateDiagram-v2 语法，确保 AI 解析准确性和可执行性。
> - 支持状态机语义，明确状态转换条件
> - 可视化渲染后人机可读
> - 避免箭头文本图的歧义问题
> 
> **简化流程规则**：
> - **单行流程**（无分支、无跳转、无循环）：可使用简化箭头形式 `A → B → C`
> - **复杂流程**（有分支、跳转或循环）：必须使用 Mermaid 图表
> - **多步骤流程**：也可使用表格形式，步骤清晰列示

### 设计文档（L0-L6）

```mermaid
stateDiagram-v2
    [*] --> 草稿
    草稿 --> 正式 : 审核通过
    正式 --> 草稿 : 实质修订（解冻，须同步提升版本号）
    正式 --> 废弃 : 主动废止或过期
    草稿 --> 草稿 : 原地修改（不递增版本）
    草稿 --> [*] : 直接删除（草稿未发布，无需废弃流程）
    废弃 --> [*]
```

> **说明**：`草稿` 是可自由增删改、不递增版本号的创作沙盒；只有 `正式` 对象的修改才需"先降草稿 + 提升版本号"，其废止才走废弃流程。`正式→草稿` 属受控状态变更，须请求确认。

### 架构决策记录（ADR）

```mermaid
stateDiagram-v2
    [*] --> 提议
    提议 --> 采纳 : 决策通过
    提议 --> 拒绝 : 决策被否决
    提议 --> 废弃 : 提议过期
    采纳 --> 废弃 : 决策失效
    采纳 --> 取代 : 有更好方案
    拒绝 --> [*]
    废弃 --> [*]
    取代 --> [*]
```

### 外部参考资料（REF）

```mermaid
stateDiagram-v2
    [*] --> 有效
    有效 --> 废弃 : 资料过时
    废弃 --> [*]
```

### 需求追溯

```mermaid
stateDiagram-v2
    [*] --> 待验证
    待验证 --> 已验证 : 测试通过
    待验证 --> 失败 : 测试失败
    失败 --> 待验证 : 修改后重新验证
    已验证 --> [*]
```

## 使用规范

1. **状态值必须从标准集合中选择**，不得自定义
2. **状态变更需要记录在变更日志中**
3. **废弃状态不可逆**，只能创建新的版本
4. **版本管理机制（与"状态即基线"绑定）**：
   - **草稿期修改：不递增版本号**（草稿未发布，属同一创作过程；仅在其内部按需要标注 v0.x 表意即可）。
   - 首次批准发布（`草稿→正式`）：确立正式基线，约定版本号为 `v1.0`。
   - 修订已 `正式` 对象：执行 `正式→草稿` 降级的**同时提升版本号**以示与旧基线区别——错别字/格式/无关于承诺的澄清 → 次版本（`v1.0→v1.1`）；影响需求承诺、架构边界或对外接口 → 主版本（`v1.x→v2.0`）；改完再升 `正式`。
   - `正式→废弃`：保持版本号，标注废弃。

### 版本与状态联动（可选）

> **注**：`正式` 对象修订前"先降 `草稿` + 提升版本号"现为**强制**（见上"状态即基线"与第 4 条）。以下仅为在此前提下的**额外细化**，与强制项冲突时以强制项为准。

若希望**「正式」已批准文档**在发生实质修订时更醒目地区分基线，可采用以下策略（与上表不冲突，由组织择一或组合）：

- **按变更影响**：错别字、格式、与需求无关的措辞澄清 → 可在保持「正式」前提下递增**次版本**；若变更影响需求承诺、架构边界或对外接口 → 建议视为**重大变更**，递增**主版本**，并重新走评审（可先降为「草稿」再升「正式」，或采用「修订中」等中间状态——须自行定义且与本节状态集合一致）。
- **正式改稿是否先回草稿**：**可以**作为强流程：任一实质修改先将状态从「正式」改回「草稿」，修订完成后再批准；**代价**是流程更重，适合强合规场景。**不建议**把「主版本递增」与「必须回草稿」机械绑定为唯一规则，否则轻量修订也会触发不必要的状态抖动。
- **与 vX.Y 的对应习惯**：可将 **X** 对应「已批准基线」代际，**Y** 对应同一代际下的修订；是否「正式文档一改就升 X」取决于团队对「重大变更」的判定，而非仅看状态字段。

**结论**：状态（草稿/正式）表达**生命周期位置**；版本号表达**内容修订程度**。二者可配合，但不宜用单一规则替代变更评审与影响分析。
5. **状态变更权限**：
   - 草稿→正式：审核者批准
   - 正式→废弃：项目负责人
   - ADR 提议→采纳/拒绝：架构师或技术委员会
   - ADR 采纳→取代/废弃：架构师或技术委员会
   - REF 有效→废弃：项目负责人
   - 需求追溯状态变更：测试负责人

## 模板更新说明

所有模板中的状态字段应使用上述标准状态值，格式为：
- L0-L6：`草稿/正式/废弃`
- ADR：`提议/采纳/拒绝/废弃/取代`
- REF：`有效/废弃`
- 需求追溯：`待验证/已验证/失败`

## 国际化支持

为支持国际化协作和工具集成，建议在工具实现中使用以下英文对照：
- Draft / Approved / Deprecated
- Proposed / Adopted / Rejected / Deprecated / Superseded
- Valid / Deprecated
- Pending / Verified / Failed
