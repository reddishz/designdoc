# 设计文档审核规范

## 审核流程

审核设计文档时，按以下检查项逐层执行：

同一含义的规则以最贴近的章节为主检查一次；后续章节只保留补充性检查点，避免重复罗列。

### 必选项检查（可自动化验证）

#### 状态值合规性
- [ ] **状态值统一四态**：文档 `状态` 与细项 `细项状态` ∈ {初稿, 正式, 草案, 废弃}（L0-L6 / ADR / REF / PLN 共用，不设专属枚举；见 [status-definitions.md · 标准四态](status-definitions.md#标准四态唯一生命周期状态集合)）
- [ ] **记录型字段取值合规**：L6 追溯矩阵 `追溯状态` ∈ {未追溯, 已追溯, 不适用}；应用注册表 `状态` 列取四态；REF 时效字段（`来源版本` / `获取日期` / `最近核验日期`）齐备且未超复查周期
- [ ] **无第二套状态枚举**：不得出现旧值或专属状态集合（如 `草稿` / `提议` / `采纳` / `拒绝` / `取代` / `登记中` / `有效` / `待验证` / `使用中`），也不得出现旧字段名（`规划状态` / `验证状态` / `应用状态` / `建议移除日期`）；映射表见 [status-definitions.md · 存量文档迁移](status-definitions.md#存量文档迁移)

#### 定稿提示（状态即基线）
- [ ] 遇到未冻结对象（`初稿` / `草案`：文档状态、索引表状态列、`细项状态：X`）时，**提示用户确认是否定稿**；AI 不自行升格
- [ ] `初稿` 对象的删改**不要求废弃流程、不要求版本号递增**，删除也不计缺口；但改标题或删除前 **MUST** 已同步全部引用处与索引（可用 `check_docs.py --refs {编码}` 核对）
- [ ] `草案` 对象**不得直接删除**：只能 `回退`（版本号回到解冻前、变更记录完整保留、该号不复用）或 `废弃`（最后版本号即该草案号）；`正式` / `草案` 对象的标题与编码 **MUST NOT** 被就地修改
- [ ] AI 完成一轮修改后的**交互式提交前定稿确认流程**（提交提示 + 列出本轮未冻结对象 + 批量升格 + 提交）见 [SKILL.md · 修改完毕：定稿确认与提交提示](../SKILL.md#修改完毕定稿确认与提交提示)

#### 元信息完整性
- [ ] 文档编码存在且格式正确（如 `CRM-L0-001`，含项目编码与层级）
- [ ] L0-L6 文档的层级字段与文档类型匹配；ADR 文档的 `层级` 字段为 `L2` 或 `L3`（ADR 编码不含层级，层级靠本字段 + 存放目录 + `关联文档` 共同表达）；REF 文档的类别字段为 `REF - 外部参考资料`
- [ ] 版本字段检查：**L0-L6 / ADR / REF 均 MUST 有 `版本` 字段**且符合语义化规范（vX.Y）；缺 `版本` 字段会使版本号递增与解冻规则无法落地，且使 `check_docs.py` 的版本校验对该文档静默失效
- [ ] **版本号递增时机**：仅在 `正式→草案` 解冻时递增；新建 `v1.0` + `初稿`、初稿期与定稿（`初稿→正式`、`草案→正式`）均不变号；`回退` 时当前号回到解冻前但**变更记录必须完整保留**被弃用的号，且该号不得再次使用（判定表见 [status-definitions.md · 变更流程与版本号](status-definitions.md#变更流程与版本号统一mandatory)）
- [ ] 状态字段检查：`状态` / `细项状态` 为必备字段；缺失时按 `变更记录` 判定（有定稿条目 → `草案`；从未定稿 → `初稿`；无法判定 → `草案`）并纳入定稿确认，不作为阻断性错误
- [ ] 作者或录入人字段非空
- [ ] 日期字段完整：L0-L6 与 **ADR** 需 `创建日期` 和 `最后更新`（ADR **MUST NOT** 用单一的 `日期` 字段同时承担两个语义）；REF 需 `录入日期` 与**最近核验日期**
- [ ] 当前作用域 `README.md` 含必要元信息，至少可识别 `doc_mode`、`project_name` 与 `project_code` 或其缺省状态

#### 编码体系合规性
- [ ] 细项编码全局唯一（无重复）
- [ ] 编码格式符合类型码规范
- [ ] 交叉引用编码确实存在
- [ ] **引用格式**：正文/属性行为链接格式、表格型追溯为裸编码（适用范围见 [coding-system.md · 交叉引用规则](coding-system.md#交叉引用规则)）
- [ ] **定义块形态**：每个细项定义位 MUST 为「锚点行 + 标题行（`{编码}：{标题}`，全角冒号）+ 具名属性行（`- **{要素名}**：{值}`）」，且三部分 MUST 连续（标题行与属性行组之间只允许空行）；MUST NOT 出现 `- **{编码}**：{描述}` 粗体式定义位，也 MUST NOT 出现裸段落属性行，或把图表 / 表格 / 子标题 / 散文段落插在标题行与属性行组之间（房规见 [coding-system.md · 细项定义块形态](coding-system.md#细项定义块形态mandatory)）
- [ ] **锚点定义位**：每个定义位的标题行上方 MUST 有 `<a id="{编码全小写}"></a>`；MUST NOT 使用 `{#编码小写}` 属性语法（详见 [coding-system.md · 锚点定义位](coding-system.md#锚点定义位)）
- [ ] 引用方向正确（仅下层引用上层）

### 合规性检查

- [ ] **术语一致性（可选触发）**：专有名词密集且易造成理解偏差时，是否具备项目词汇表、文档内「术语与概念」小节或文内首次定义（见 [glossary-conventions.md](glossary-conventions.md)）；无此类风险时可跳过
- [ ] 不存在可执行代码、脚本、SQL、配置片段等实现内容（核心约束）
- [ ] 目录结构和文件命名合规
- [ ] 文件名不含中文；文档内容使用中文撰写（二者不可混淆）
- [ ] 若正文定义了明确细项编码，则细项编码清单完整且与正文一致
- [ ] 变更记录存在且最新；仅示例片段或无需维护变更记录的清单型模板可按模板约定处理
- [ ] 项目元信息来源正确：使用作用域 `README.md` 作为配置源，且未再引入额外配置文件
- [ ] 编码生命周期规则遵守（进入 `正式` 后永不删除、永不复用；`初稿` 期可增删改，`草案` 期不得直接删除）
- [ ] **包内一致性**：本 skill 包内对同一规则只存在一种表述；发现不一致即为规范缺陷，当轮合并修正
- [ ] **禁止章节编号引用（强制）**：正文不存在任何“§x.y.z / 第x章 / 见上文”形式的语义引用
- [ ] **稳定引用强制（强制）**：所有引用均使用细项编码或文档编码，不使用章节编号

### 项目编码合规性

- [ ] 项目编码长度为 2-4 位大写字母
- [ ] 项目编码只包含字母 A-Z
- [ ] 项目编码体现项目或产品线特征
- [ ] 跨项目引用包含项目编码前缀
- [ ] 同项目内简写与完整形式符合 `coding-system.md` 约定（索引与跨文档须完整编码）
- [ ] 类型码 REF 的细项计数与引用方式符合 `coding-system.md`（含全局 `*` 行说明）
- [ ] 单应用模式下，`ued/README.md` 承担项目元信息、计数器和索引
- [ ] 多应用模式下，顶层 `ued/README.md` 包含应用注册表，目标应用 `ued/{app-name}/README.md` 承担该应用元信息、计数器和索引
- [ ] 多应用模式下，顶层 `ued/README.md` 未被误用为某个应用的细项索引真值源

### 编码分配合规性

- [ ] 编码计数器按项目编码+类型码独立计数
- [ ] 序号从 001 开始，单调递增
- [ ] 废弃编码保留编号，标注"废弃"
- [ ] 编码分配前检查冲突
- [ ] 编码引用格式正确（如 CRM-FR-001 用户登录功能）
- [ ] **编码锁定检查（两层）**：任何状态下编码 ID / 类型 / 标题均未被就地修改；`正式` 编码的业务含义 / 判定口径未被擅自变更（逐对象判定见 [coding-system.md · 修改操作矩阵](coding-system.md#修改操作矩阵must-comply)）
- [ ] **废弃流程合规**：废弃编码正确标注，未重用编号
- [ ] **废弃信息完整**：包含细项状态、废弃时间、废弃原因、替代方案四个必须字段
- [ ] **引用更新完整**：废弃细项的引用已正确处理
- [ ] **索引同步更新**：全局索引和文档清单已更新废弃状态
- [ ] **变更记录完整**：废弃变更已记录在变更记录中
- [ ] **废弃标题标记**：废弃细项标题包含 `~~已废弃~~` 删除线
- [ ] **废弃时间格式**：废弃时间格式为 YYYY-MM-DD
- [ ] **废弃原因规范**：废弃原因属于标准分类（需求变更、设计优化、技术升级等）
- [ ] **替代方案规范**：有替代方案填写编码，无替代方案填写"无"
- [ ] **即时索引更新**：新编码分配后立即更新所有相关索引
- [ ] **标题命名规范**：编码标题适度宽泛，避免过于具体
- [ ] **全局唯一性验证**：新编码在 ued/ 目录下无重复定义
- [ ] **编码计数器同步**：新编码分配后，“下一可用编号”已递增且备注已更新
- [ ] **README 索引排序**：当前作用域 README 的各类型码索引表均按编码数字升序排列，新项未乱序追加
- [ ] **编号缺口治理**：不存在未解释的编号缺口；新项一律使用“下一可用编号”
- [ ] **文档清单完整性**：若正文定义了明确细项编码，文档末尾细项编码清单包含所有正文中的编码
- [ ] **文档清单完整编码**：若存在细项编码清单，其编码均为完整编码形式
- [ ] **全局索引完整性**：当前作用域 `README.md` 的全局索引包含所有已正式分配并需纳入索引的编码
- [ ] **索引一致性**：对正文定义的细项编码，文档清单与全局索引的编码信息完全一致

### 内容完整性检查

- [ ] L0 文档包含愿景声明、商业背景、成功标准、范围边界
- [ ] L1 文档包含利益相关者分析、场景描述、高阶约束
- [ ] L2 文档包含功能需求、非功能需求、用例描述、验收标准
- [ ] L3 文档包含架构目标与约束、架构原则、子系统划分
- [ ] L4 文档包含领域模型、接口契约、模块职责
- [ ] L5 文档包含详细设计、算法逻辑、异常策略
- [ ] L6 文档包含测试策略、需求追溯矩阵、缺陷管理策略
- [ ] **L6 定位正确**：追溯矩阵用 `追溯状态`（未追溯 / 已追溯 / 不适用）表达追溯覆盖关系，**不记录测试执行结果**（通过 / 失败 / 缺陷数属测试管理系统职责）

### 细项定义清晰性检查（概念是否明确）

先按 `coding-system.md` 的“细项定义最小要素（清晰性基线）— 适用性边界（按类型分组）”判定检查强度，避免对 REF/GOL/STK 等类型机械套用同一标准。

- [ ] **一句话定义清晰**：每个新增/变更细项可用 1 句话解释“是什么”
- [ ] **边界明确**：包含适用范围，且至少有 1 条“非目标/不适用范围”
- [ ] **触发条件明确**：细项何时生效、由谁触发、前置条件是什么
- [ ] **可验证口径存在**：存在可验证标准（可直接写指标，或引用 AC/TC/MET）
- [ ] **追溯关系完整**：细项至少可追溯到一个上层依据（如 GOL/SCN/FR/NFR/PRN）
- [ ] **术语歧义可控**：高歧义术语在文内首次定义或引用项目词汇表

补充判定：
- [ ] **REF 例外正确处理**：REF 以来源说明、适用边界、被支撑细项追溯为主，不强制要求触发条件
- [ ] **目标类不误判**：GOL/STK/SCN/DOM/CMP 若无显式触发条件，不应仅因缺少 When 被判不合格

### 引用关系合规性

- [ ] 引用格式包含必要标题信息
- [ ] REF 引用来源信息完整（类型、出处、链接、获取日期）
- [ ] ADR 文档引用相关约束（CON-xxx、NFR-xxx）
- [ ] 需求追溯到验收标准（FR-xxx → AC-xxx）
- [ ] **标准引用格式**：优先使用 Markdown 链接 `[编码（标题）](#锚点)`（见 [coding-system.md · 交叉引用规则](coding-system.md#交叉引用规则)）；纯文本场景再用统一分隔形式
- [ ] **标题一致性**：引用标题与索引完全一致
- [ ] **引用完整性**：重要引用都包含完整标题信息
- [ ] **格式统一性**：同一文档内引用格式保持一致
- [ ] **Markdown 兼容性**：引用格式在 Markdown 中渲染正常

### IF / PLN 类型使用合理性检查

- [ ] **IF 不被误限于 HTTP API**：事件、Webhook、文件交换、内部服务边界等契约可使用 IF
- [ ] **API 分类一致**：对外/对内 API 使用 IF 编码并通过“接口风格”区分，不新增独立 API 类型码
- [ ] **IF/ACT 不重叠误用**：契约语义用 IF，动作语义用 ACT；若同一场景两者都需要，应双编码并建立追溯
- [ ] **PLN 使用边界正确**：仅用于「本轮不实现、留待将来考虑或细化」的想法，不替代已稳定的 FR/NFR/IF/ALG 定义
- [ ] **PLN 未混入执行信息**：PLN 不含工时、工作量、负责团队、排期、完成进度等项目过程字段（`建议复审日期` 是复审提醒、非交付承诺，不属此列）
- [ ] **PLN 与路线图不关联**：路线图不引用 PLN，PLN 不挂在路线图主题下
- [ ] **PLN 处置闭环**：`正式` 即已落实——定稿与落实同步完成，`落实记录` **MUST** 非空且指向目标细项编码，**不得存在 `正式` 而 `落实记录` 为「无」的 PLN**；不再考虑者标 `废弃` 并记原因（`替代方案` 填目标细项或「无」）；从未定稿即放弃者在 `初稿` 期直接删除并回收编号
- [ ] **PLN 落实双向可追溯**：`落实记录` 指向的每个目标细项，其定义块内 **MUST** 有 `来源` 属性行回指该 PLN
- [ ] **PLN 复审兜底**：仍处 `初稿` / `草案`（尚未定论）的 PLN **MUST** 填 `建议复审日期`；已到期者应重新评估（展开 / 延后并更新日期 / 废弃）；转 `正式` 或 `废弃` 后该值置「无」或移除
- [ ] **PLN 默认层级正确**：未显式指定层级时，PLN 默认落在 L2；若落在 L3-L5，具备明确的架构/接口/算法语义依据
- [ ] **PLN 说明三要素齐备**：想法内容、当前不做的原因、重新考虑的条件均可读

### 格式规范检查

- [ ] 层级目录命名规范（L{N}-{英文短名}/）
- [ ] 应用目录小写英文，短横线分隔
- [ ] 文件名不含中文，描述部分使用英文或拼音
- [ ] 日期格式统一（YYYY-MM-DD）
- [ ] 表格格式标准，列名清晰

### 废弃格式规范检查

#### 标题标记规范
- [ ] 废弃细项标题包含 `~~已废弃~~` 删除线（必须）
- [ ] 不使用粗体括号 `(已废弃)` 等其他格式

#### 必须字段检查
- [ ] 废弃细项包含 `**细项状态**：废弃` 字段（结构化状态值统一为 `废弃`，非 `已废弃`）
- [ ] 废弃细项包含 `**废弃时间**：YYYY-MM-DD` 字段
- [ ] 废弃细项包含 `**废弃原因**：{具体原因}` 字段
- [ ] 废弃细项包含 `**替代方案**：{编码} 或 "无"`
- [ ] 废弃时间格式正确（YYYY-MM-DD）
- [ ] 废弃原因清晰明确（至少说明废弃的简要原因）

#### 索引更新检查
- [ ] 全局索引中该细项状态更新为"废弃"
- [ ] 文档清单中该细项状态更新为"废弃"
- [ ] 索引中包含废弃时间信息
- [ ] 索引备注中说明替代方案（如有）

### 流程图格式合规性

- [ ] 单行流程使用简化箭头形式（无分支、无跳转、无循环）
- [ ] 复杂流程使用 Mermaid 图表（有分支、跳转或循环）
- [ ] 多步骤流程使用表格形式，步骤清晰列示
- [ ] Mermaid 语法正确，可渲染
- [ ] 箭头符号使用标准格式（推荐 →，可接受 ->）


### 章节编号引用强制审查与修正指引

#### 强制判定（命中任一即不通过）
- [ ] 出现任何 `§x.y.z / 第x章 / 见上文` 形式的章节编号引用。
- [ ] 引用未使用细项编码或文档编码。
- [ ] 强约束句（唯一开关/必须/禁止/仅当）未给出可执行条件。

#### 审查结论分级
- **A 级（阻断合并）**：出现任意章节编号引用（必须清零后再审）。
- **B 级（当轮修正）**：虽无章节编号引用，但缺失编码化引用或可执行条件。
- **C 级（优化项）**：编码引用存在但追溯链路不完整。

#### 标准修正动作（Reviewer 强制指导）
1. 删除章节编号：移除所有 `§` / `第x章` / `见上文` 引用。
2. 落码替代：将引用改为细项编码或文档编码。
3. 补全定义：落为独立定义块（形态见 [coding-system.md · 细项定义块形态](coding-system.md#细项定义块形态mandatory)），按 What / Scope / When / Verify / Trace 补齐最小要素。
4. 复核通过：确认全文零章节编号引用后再进入下一轮评审。

#### 快速改写模板
- **原句（不合规）**：{业务结论}（详见 §x.y.z）
- **改写（合规）**：落为独立定义块，章节号引用改为 `来源` 属性行的标准链接

```markdown
<a id="{编码全小写}"></a>
### {TYPE-xxx}：{规则标题}

- **定义**：{可独立执行的规则定义}
- **来源**：[{TYPE-xxx}（{细项标题}）]({定义所在文档相对路径}#{编码全小写})
```

> MUST NOT 改写成单行的 `- {TYPE-xxx}：{定义}。引用依据：{Lx-xxx}`：该形态既是被禁的粗体式定义位变体，又用了《追溯类属性行命名》之外的近义名。依据为整份文档时链接不带锚点。

### SSoT 一致性检查

- [ ] 本文前述编码唯一性、引用存在性、引用方向、索引同步等检查项结果一致，且不存在跨章节结论冲突

### 逐层合规性检查

从上层向下层逐级检查，确保下层不违背上层：

- [ ] **L1 vs L0**：利益相关者需求是否对齐战略目标（GOL-xxx）
- [ ] **L2 vs L1**：功能/非功能需求是否覆盖利益相关者场景（SCN-xxx）
- [ ] **L3 vs L2**：架构方案是否满足所有需求（FR-xxx, NFR-xxx）
- [ ] **L4 vs L3**：系统设计是否遵循架构原则（PRN-xxx）和约束（CON-xxx）
- [ ] **L5 vs L4**：详细设计是否符合接口契约（IF-xxx）和领域模型（DOM-xxx）
- [ ] **L6 vs L2**：验证场景是否追溯到需求（FR-xxx）和验收标准（AC-xxx）

## 常见问题检查

- **内容违规**：混入代码、脚本、SQL、配置片段或其他实现内容；流程图形式与复杂度不匹配
- **编码违规**：项目编码不合法、细项编码冲突、编码含义被修改、废弃编码重用、标题过度具体
- **索引违规**：正文定义的细项编码与文档清单、当前作用域 `README.md` 全局索引不同步；计数器未递增；废弃信息缺失
- **引用违规**：引用编码不存在、引用方向错误、格式不统一、标题缺失、Markdown 锚点渲染异常、REF 信息不完整
- **结构违规**：元信息缺失、变更记录缺失、命名不规范、日期或版本格式错误、表格或 Mermaid 语法不合法
- **完整性缺陷**：层级必需章节缺失、追溯链断裂、约束/假定/风险/度量指标遗漏
- **质量问题**：文档间结论冲突、表述模糊、结构混乱、过度设计、范围蔓延

## 编码索引完整性校验

### 校验原则

**核心要求**：对**正文中定义的细项编码**，必须在以下三个位置同时建立，缺一不可：
1. 文档正文中定义位置（符合《细项定义块形态》的完整定义块，含 `<a id>` 锚点行）
2. 文档末尾的细项编码清单
3. 当前作用域 `README.md` 的全局编码索引

### 校验步骤

#### 步骤 1：检查文档正文的编码定义

**方法**：在文档中搜索所有编码格式的标题（如 `### CRM-FR-001：用户登录功能`，其上方一行应为 `<a id="crm-fr-001"></a>`）

可使用编辑器搜索、仓库搜索工具或 `python3 scripts/check_docs.py` 提取这些标题；本文不绑定特定平台命令。

**检查项**：
- [ ] 每个编码标题包含项目编码（如已启用）、类型码、三位序号，且用**全角冒号**分隔标题文本
- [ ] 每个编码标题**上方紧邻一行**为 `<a id="{编码全小写}"></a>`（锚点房规单点见 [coding-system.md · 锚点定义位](coding-system.md#锚点定义位)，本文不复述细则）
- [ ] 锚点命名符合规范（全小写，短横线分隔），且与编码一一对应

#### 步骤 2：检查文档末尾的细项编码清单

仅适用于正文中定义了明确细项编码的文档。

**方法**：找到文档末尾的"细项编码清单"或"编码清单"章节

**检查项**：
- [ ] 清单包含正文中的所有编码
- [ ] 每个条目格式正确（编码 | 类型 | 标题 | 细项状态）
- [ ] 编码、类型、标题与正文完全一致
- [ ] 清单中的编码均为完整编码
- [ ] 无遗漏、无重复

#### 步骤 3：检查当前作用域 `README.md` 的全局索引

**方法**：打开当前作用域 `README.md`，找到对应的类型码表格（如 FR 类型码表格）

**检查项**：
- [ ] 新编码已在对应的类型码表格中
- [ ] 编码、标题与文档完全一致
- [ ] 编码计数器的“下一可用编号”已递增（如 CRM-FR 下一可用 016 → 017）
- [ ] 新编码按数字升序插入对应类型码表格，未追加到乱序位置
- [ ] 备注已更新（如"下一可用 017；序列无缺口"）

#### 步骤 4：验证一致性

**方法**：对比以下三个来源

| 来源 | 编码数量 | 最小编码 | 最大编码 |
|------|---------|---------|---------|
| 文档正文 | | | |
| 文档清单 | | | |
| 全局索引 | | | |

**检查项**：
- [ ] 三个来源的编码数量一致
- [ ] 三个来源的最小编码和最大编码一致
- [ ] 三个来源的编码列表完全相同（无遗漏、无多余）

### 编码冲突检查（防止重复定义）

**方法**：在 ued/ 目录下搜索目标编码

可使用编辑器全文搜索、仓库搜索工具或自定义脚本检索目标编码（本包附带 `scripts/check_docs.py --refs {编码}` 可直接列出全部定义 / 登记 / 引用位置）。

**检查项**：
- [ ] 新编码在 ued/ 目录下无重复定义
- [ ] 如发现重复，判断是复用现有编码还是冲突
- [ ] 冲突时需重新分配编码

### 编码计数器验证

**方法**：对比编码计数器与实际使用情况

建议提取当前作用域 `README.md` 的计数器信息，再对比所有 Markdown 文档中的实际编码使用情况；实现方式可按团队环境选择。

**检查项**：
- [ ] 计数器的“下一可用编号”未被使用
- [ ] 编码序列无未解释缺口；废弃编号仍保留索引记录，不形成缺口（`初稿` 期删除的编号可回收、不计缺口）

### 常见问题识别

| 问题 | 表现 | 处理方法 |
|------|------|---------|
| 编码重复定义 | 同一编码在多个文档中定义 | 检查是否为同一定义的多处引用，否则需重新分配 |
| 编码清单不完整 | 正文有编码但清单缺失 | 补充到清单中 |
| 全局索引缺失 | 编码在文档清单但全局索引缺失 | 补充到全局索引中 |
| 计数器未更新 | 新编码已使用但“下一可用编号”未递增 | 更新计数器和备注 |
| 索引乱序 | 新编码追加到类型码表尾，导致 051/052 出现在 008 前 | 按编码数字升序重排该类型码表 |
| 编号缺口 | 索引序列中缺少某个**已正式化**或已废弃编号（`初稿` 期删除不计缺口） | 补齐索引记录或废弃记录，确保正式基线序列完整 |
| 标题不一致 | 不同位置标题文字不同 | 统一为首次分配时的标题；`初稿` 期改标题须同步全部引用处，`正式` / `草案` 对象的标题**不得就地修改**（只能废弃 + 新增） |
| 锚点缺失 | 编码标题上方无 `<a id="{编码全小写}"></a>` | 补锚点行；**MUST NOT** 用 `{#编码小写}` 属性语法（该语法在 GitHub 等 cmark-gfm 渲染器下不生效），细则见 [coding-system.md · 锚点定义位](coding-system.md#锚点定义位) |
| 锚点语法错用 | 标题带 `{#编码小写}` 后缀 | 删除花括号后缀，改为标题行上方的 `<a id>` 锚点行 |
| 定义位形态不合规 | 写成 `- **{编码}**：{描述}` 粗体式，或属性行为裸段落 / 缺粗体 | 改为完整定义块（锚点行 + 标题行 + `- **{要素名}**：{值}`） |
| 定义块顺序被打断 | 图表 / 表格 / 子标题 / 散文段落插在标题行与属性行组之间 | 把叙述与图示移到属性行组之后，或作为某个属性行的值（三部分 MUST 连续，见 [coding-system.md · 细项定义块形态](coding-system.md#细项定义块形态mandatory)） |
| 锚点命名错误 | 锚点大小写或格式错误 | 修正为全小写短横线格式 |

### 校验清单总结

#### 文档级别校验
- [ ] 正文所有编码都带锚点
- [ ] 清单包含正文所有编码
- [ ] 清单编码与正文完全一致
- [ ] 无遗漏、无重复

#### 全局级别校验
- [ ] 新编码已添加到当前作用域 `README.md` 对应类型码表格
- [ ] 全局索引信息与文档完全一致
- [ ] 编码计数器的“下一可用编号”已正确递增
- [ ] 计数器备注已更新，编码序列无缺口
- [ ] 各类型码索引按编码数字升序排列
- [ ] 全局编码无冲突

#### 一致性校验
- [ ] 正文、清单、索引三方一致
- [ ] 编码序列无缺口；新增项均使用“下一可用编号”
- [ ] 项目编码、类型码正确
- [ ] 锚点命名符合规范

## 审核流程总结

### 第一阶段：自动化检查（可自动化验证）

1. **状态值合规性**：检查状态值是否在标准集合中
2. **元信息完整性**：验证必要字段是否存在
3. **编码格式检查**：验证编码格式是否符合规范
4. **文件命名检查**：确保文件名和目录名符合规范
5. **README 配置验证**：检查作用域 `README.md` 中的元信息区块、编码模式与应用注册信息

### 第二阶段：内容审核（人工检查）

1. **代码混入检查**：确保无可执行代码和实现片段，但允许算法、流程、状态机、逻辑与模型描述
2. **引用关系验证**：检查交叉引用的有效性和方向
3. **内容完整性**：验证各层级必需章节
4. **层级一致性**：确保下层不违背上层
5. **流程图格式**：验证图表格式符合复杂度要求

### 第三阶段：质量保证（综合评估）

1. **可追溯性**：验证需求到验证的完整链路
2. **一致性检查**：跨文档的一致性验证
3. **可维护性**：文档结构和表述的清晰度
4. **完整性评估**：设计覆盖范围的充分性

### 审核结果处理

| 审核结果 | 处理方式 | 责任人 |
|----------|----------|--------|
| 通过 | 文档状态更新为"正式" | 审核人 |
| 需修改 | 返回作者修改，明确修改项 | 审核人、作者 |
| 严重问题 | 重新设计，重大问题需讨论 | 审核人、架构师 |

### 审核工具支持

1. **编码冲突检查**：搜索全局编码重复
2. **引用有效性验证**：检查引用编码存在性
3. **格式规范检查**：自动化验证命名和格式
4. **内容完整性检查**：根据模板验证章节完整性
5. **平台建议**：优先采用仓库搜索、编辑器诊断、自定义脚本或 CI 检查，不把规范绑定到某一类 shell 命令
