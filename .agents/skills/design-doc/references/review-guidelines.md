# 设计文档审核规范

检查项清单。规则本体在 [object-model.md](object-model.md)、[coding-system.md](coding-system.md)、[type-profiles.md](type-profiles.md)、[status-definitions.md](status-definitions.md)；本节只列「查什么」，不复述「为什么」。

## 审核流程

审核设计文档时，按以下检查项逐层执行。同一含义只在最贴近的章节检查一次。

### 必选项检查（可自动化验证）

#### 状态值合规性
- [ ] **状态值统一四态**：文档 `状态` 与细项 `细项状态` ∈ {初稿, 正式, 草案, 废弃}（L0-L6 / ADR / REF / PLN 共用，不设专属枚举；见 [status-definitions.md · 标准四态](status-definitions.md#标准四态唯一生命周期状态集合)）
- [ ] **记录型字段取值合规**：L6 追溯矩阵 `追溯状态` ∈ {未追溯, 已追溯, 不适用}；PLN `落实情况` ∈ {未落实, 已落实}；应用注册表 `状态` 列取四态；REF 时效字段（`来源版本` / `获取日期` / `最近核验日期`）齐备且未超复查周期
- [ ] **无第二套状态枚举**：不得出现旧值或专属状态集合（如 `草稿` / `提议` / `采纳` / `拒绝` / `取代` / `登记中` / `有效` / `待验证` / `使用中`），也不得出现旧字段名（`规划状态` / `验证状态` / `应用状态` / `建议移除日期`）；映射表见 [status-definitions.md · 存量文档迁移](status-definitions.md#存量文档迁移)

#### 定稿提示（状态即基线）
- [ ] 遇到未冻结对象时提示是否定稿，并含「不得作为实现依据」（见 [SKILL.md · 据文档实现](../SKILL.md#据文档实现消费侧mandatory)）；AI 不自行升格
- [ ] 放弃 / 改标题 / 删除通道按 [object-model.md · 锁定矩阵](object-model.md#锁定矩阵mandatory)；改标题前 `--refs`
- [ ] **层级门控**与依据方向：见 [status-definitions.md · 层级门控](status-definitions.md#层级门控文档状态--细项状态mandatory)
- [ ] 提交前定稿确认流程见 [SKILL.md · 修改完毕](../SKILL.md#修改完毕定稿确认与提交提示)

#### 元信息完整性
- [ ] 文档编码存在且格式正确（如 `CRM-L0-001`，含项目编码与层级）
- [ ] L0-L6 文档的层级字段与文档类型匹配；ADR 文档的 `层级` 字段为 `L3`（ADR 归属概念架构，存于 `L3-architecture/`；ADR 编码不含层级，层级靠本字段 + 存放目录 + `关联文档` 共同表达，依据见 [layer-system.md · 层级定义](layer-system.md#层级定义)）；REF 文档的类别字段为 `REF - 外部参考资料`
- [ ] 版本字段检查：**L0-L6 / ADR / REF 均 MUST 有 `版本` 字段**且符合语义化规范（vX.Y）；缺 `版本` 字段会使版本号递增与解冻规则无法落地，且使 `check_docs.py` 的版本校验对该文档静默失效
- [ ] **版本号递增时机**：仅在 `正式→草案` 解冻时递增；新建 `v1.0` + `初稿`、初稿期与定稿（`初稿→正式`、`草案→正式`）均不变号；`回退` 时当前号回到解冻前但**变更记录必须完整保留**被弃用的号，且该号不得再次使用（判定表见 [status-definitions.md · 变更流程与版本号](status-definitions.md#变更流程与版本号统一mandatory)）
- [ ] **流转伴随字段不被单独改动**：文档 `版本`、细项 `修订版本号` / `最后修订日期` 由状态转换写入（创建时取初值，此后只在 `正式→草案` 解冻那一刻写），**MUST NOT** 作为独立修改请求单独调整；号与日期 **MUST** 成对；回退时文档 `版本` 回到解冻前的号，细项 `修订版本号` **不回退**、`最后修订日期` 不变（见 [status-definitions.md · 流转伴随字段](status-definitions.md#流转伴随字段只随指定转换写入)）
- [ ] 状态字段检查：`状态` / `细项状态` 为必备字段；缺失时按 `变更记录` 判定（有定稿条目 → `草案`；从未定稿 → `初稿`；无法判定 → `草案`）并纳入定稿确认，不作为阻断性错误
- [ ] 作者或录入人字段非空
- [ ] 日期字段完整：L0-L6 与 **ADR** 需 `创建日期` 和 `最后更新`（ADR **MUST NOT** 用单一的 `日期` 字段同时承担两个语义）；REF 需 `录入日期` 与**最近核验日期**；`创建日期` 属流转伴随字段，创建时写入一次后 **MUST NOT** 修改；本轮改过的文档 `最后更新` **MUST** 已刷为当天（记录型字段，任何一次编辑都动，即使不解冻、不递增 `版本`）
- [ ] 当前作用域 `README.md` 含必要元信息，至少可识别 `doc_mode`、`project_name` 与 `project_code` 或其缺省状态

#### 编码体系合规性
- [ ] 细项编码全局唯一（无重复）
- [ ] 编码格式符合类型码规范
- [ ] 交叉引用编码确实存在
- [ ] **引用格式**：正文/属性行为链接格式、表格型追溯为裸编码（适用范围见 [coding-system.md · 交叉引用规则](coding-system.md#交叉引用规则)）
- [ ] **定义块形态 / 属性行组三段 / 属性名封闭集 / 正文不混用属性行**：见 [coding-system.md · 细项定义块形态](coding-system.md#细项定义块形态mandatory) 与 [属性行定义集（封闭）](coding-system.md#属性行定义集封闭)
- [ ] **锚点定义位**：标题行上方 `<a id="{编码全小写}"></a>`；MUST NOT 用 `{#编码小写}`（见 [锚点定义位](coding-system.md#锚点定义位)）
- [ ] 引用方向正确（仅下层引用上层）

### 合规性检查

- [ ] **术语一致性（可选触发）**：专有名词密集且易造成理解偏差时，是否具备项目词汇表、文档内「术语与概念」小节或文内首次定义（见 [glossary-conventions.md](glossary-conventions.md)）；无此类风险时可跳过
- [ ] 不存在可执行代码、脚本、SQL、配置片段等实现内容（核心约束）
- [ ] 目录结构和文件命名合规
- [ ] 文件名不含中文；文档内容使用中文撰写（二者不可混淆）
- [ ] 若正文定义了明确细项编码，则细项编码清单完整且与正文一致
- [ ] 变更记录存在且最新；仅示例片段或无需维护变更记录的清单型模板可按模板约定处理
- [ ] 项目元信息来源正确：使用作用域 `README.md` 作为配置源，且未再引入额外配置文件
- [ ] 编码生命周期规则遵守（编号一经分配即**永不删除、永不复用**，全状态一致；放弃只能作废 → `废弃`；`初稿` 期可增改，`草案` 期不得直接删除）
- [ ] **包内一致性**：本 skill 包内对同一规则只存在一种表述；发现不一致即为规范缺陷，当轮合并修正
- [ ] **禁止章节编号引用（强制）**：正文不存在任何“§x.y.z / 第x章 / 见上文”形式的语义引用
- [ ] **稳定引用强制（强制）**：所有引用均使用细项编码或文档编码，不使用章节编号

### 项目编码合规性

- [ ] 项目编码符合字符集与消歧约束（2-5 位、大写字母开头、其余位可数字；不与类型码同形、不形如 `L` 加数字；房规见 `coding-system.md` ·《项目编码规则》）
- [ ] 项目编码体现项目或产品线特征
- [ ] 跨项目引用包含项目编码前缀
- [ ] 同项目内简写与完整形式符合 `coding-system.md` 约定（索引与跨文档须完整编码）
- [ ] 类型码 REF 的细项计数与引用方式符合 `coding-system.md`（含全局 `*` 行说明）
- [ ] 单应用模式下，`ued/README.md` 承担项目元信息、计数器和索引
- [ ] 多应用模式下，顶层 `ued/README.md` 包含应用注册表，目标应用 `ued/{app-name}/README.md` 承担该应用元信息、计数器和索引
- [ ] 多应用模式下，顶层 `ued/README.md` 未被误用为某个应用的细项索引真值源

### 编码分配合规性

- [ ] 编码计数器按项目编码+类型码独立计数
- [ ] 序号从 001 开始，单调递增
- [ ] 废弃编码保留编号，标注"废弃"
- [ ] 编码分配前检查冲突
- [ ] 编码引用格式正确（如 CRM-FR-001 用户登录功能）
- [ ] **编码锁定检查**：按 [object-model.md · 锁定矩阵](object-model.md#锁定矩阵mandatory) 核对 ID / 类型码 / 标题 / 含义通道
- [ ] **废弃流程合规**：废弃编码正确标注，未重用编号
- [ ] **废弃信息完整**：包含细项状态、废弃时间、废弃原因、替代方案四个必须字段
- [ ] **引用更新完整**：废弃细项的引用已正确处理
- [ ] **依赖图已处理**：作废前已评估「谁依赖我」（MUST）与「我依赖谁」孤儿（SHOULD，禁止自动级联）
- [ ] **索引同步更新**：全局索引和文档清单已更新废弃状态
- [ ] **变更记录完整**：废弃变更已记录在变更记录中
- [ ] **废弃标题标记**：废弃细项标题包含 `~~已废弃~~` 删除线
- [ ] **废弃时间格式**：废弃时间格式为 YYYY-MM-DD
- [ ] **废弃原因规范**：废弃原因属于标准分类（需求变更、设计优化、技术升级等）
- [ ] **替代方案规范**：有替代细项时用标准链接指向其定义位（带 `#{编码全小写}` 锚点），无替代时填「无」；**MUST NOT** 只写裸编码，也 **MUST NOT** 写替代思路一类的散文（思路归 `废弃原因`）——见 [item-deprecation.md · 标准标记格式](item-deprecation.md#标准标记格式)
- [ ] **即时索引更新**：新编码分配后立即更新所有相关索引
- [ ] **标题命名规范**：编码标题适度宽泛，避免过于具体
- [ ] **全局唯一性验证**：新编码在 ued/ 目录下无重复定义
- [ ] **编码计数器同步**：新编码分配后，“下一可用编号”已递增且备注已更新
- [ ] **README 索引排序**：当前作用域 README 的各类型码索引表均按编码数字升序排列，新项未乱序追加
- [ ] **编号缺口治理**：编号序列 **MUST** 无缺口（作废项原地保留、仍占编号，因此不存在合法缺口）；计数器“下一可用编号” **MUST** 等于已用最大编号 + 1；新项一律使用“下一可用编号”
- [ ] **文档清单完整性**：若正文定义了明确细项编码，文档末尾细项编码清单包含所有正文中的编码
- [ ] **文档清单完整编码**：若存在细项编码清单，其编码均为完整编码形式
- [ ] **全局索引完整性**：当前作用域 `README.md` 的全局索引包含所有已正式分配并需纳入索引的编码
- [ ] **索引一致性**：对正文定义的细项编码，文档清单与全局索引的编码信息完全一致

### 内容完整性检查

- [ ] L0 文档包含愿景声明、商业背景、成功标准（MET 定义块）、范围边界
- [ ] L1 文档包含利益相关者分析、场景描述、高阶约束；场景优先级表与 L2 FR 的 P0/P1/P2 各自取值
- [ ] L2 文档包含功能需求、非功能需求、用例描述、验收标准；概述按需含系统上下文 / 用户特征 / 对外接口一览；FR / NFR 首段为「系统应当」句式，且能通过换实现测试
- [ ] L3 文档包含架构目标与约束、架构原则、子系统划分；系统上下文是架构边界，不复制 L2 产品边界
- [ ] L4 文档包含领域模型、接口契约；IF 有 `所属组件`；有独立业务动作时才定义 ACT；不定义 FR / NFR / AC / UC
- [ ] L5 文档包含算法逻辑、流程与约束、异常策略；组件引用 L3 CMP，不在 L5 重复定义，也不定义 FR / NFR / AC / UC
- [ ] L6 文档包含测试策略、需求追溯矩阵、缺陷管理策略；功能与非功能测试均有 TC；不定义 AC
- [ ] **对层正确**：文档回答的问题与 [layer-system.md · 分层问题](layer-system.md#分层问题对层判据) 一致；L2 不写架构方案，L3 不另编特性类型；用户可见路径用 UC，系统路径用 FLW
- [ ] **定义与引用分离**：锁定类型只在定义层写定义块，他层只链接（[coding-system.md · 细项定义层级](coding-system.md#细项定义层级mandatory)）
- [ ] **L6 定位正确**：追溯矩阵用 `追溯状态`（未追溯 / 已追溯 / 不适用）表达追溯覆盖关系，**不记录测试执行结果**（通过 / 失败 / 缺陷数属测试管理系统职责）

### 细项定义清晰性检查（概念是否明确）

先按 `coding-system.md` 的“细项定义最小要素（清晰性基线）— 适用性边界（按类型分组）”判定检查强度，避免对 REF/GOL/STK 等类型机械套用同一标准。

- [ ] **一句话定义清晰**：每个新增/变更细项可用 1 句话解释“是什么”
- [ ] **边界明确**：包含适用范围，且至少有 1 条“非目标/不适用范围”
- [ ] **触发条件明确**：细项何时生效、由谁触发、前置条件是什么
- [ ] **可验证口径存在**：存在可验证标准（可直接写指标，或引用 AC/TC/MET）
- [ ] **追溯关系完整**：细项至少可追溯到一个上层依据（如 GOL/SCN/FR/NFR/PRN）
- [ ] **理由可读**：FR / NFR 正文能看出为什么需要这条（不自造 `理由` 属性行）
- [ ] **术语歧义可控**：高歧义术语在文内首次定义或引用项目词汇表

#### 需求陈述（FR / NFR）

口径见 [coding-system.md · 需求陈述](coding-system.md#需求陈述should)。

- [ ] **句式**：首段是可验证的对外承诺（条件 + 系统应当 + 动作 + 对象 + 约束）
- [ ] **单数**：未用「和 / 以及 / 并且」把两条需求焊进同一细项
- [ ] **无需实施**：换一种库、表、框架或算法，本句仍成立；手段不写进 FR / NFR
- [ ] **无模糊词**：未把「最好 / 用户友好 / 尽可能 / 视情况 / 适当」当作不可判定的主约束
- [ ] **正式需求可验收**：`细项状态` 为 `正式` 的 FR / NFR 有 `验证方式` 指向 AC（检查器 WARNING）

#### 依赖与集合完整性

- [ ] **`来源` 不是 `依赖`**：派生 / 下放 / 落实回指用 `来源`；同层前提用 `依赖`
- [ ] **依赖影响已评估**：本轮解冻、改含义或作废前已看 `--refs` 的「谁依赖我 / 我依赖谁」
- [ ] **正式文档无待定**：文档 `状态` 为 `正式` 时，定义块与概述不含 TBD / TBS / TBR / 待定 / 待补充 / 待填写
- [ ] **Necessary / Feasible**：拿掉该细项是否缺能力；代价是否可接受（不加字段）

补充判定：
- [ ] **REF 例外正确处理**：REF 以来源说明、适用边界、被支撑细项追溯为主，不强制要求触发条件
- [ ] **目标类不误判**：GOL/STK/SCN/DOM/CMP 若无显式触发条件，不应仅因缺少 When 被判不合格

### 引用关系合规性

- [ ] 引用格式包含必要标题信息
- [ ] REF 引用来源信息完整（类型、出处、链接、获取日期）
- [ ] ADR 文档引用相关约束（CON-xxx、NFR-xxx）
- [ ] 需求追溯到验收标准（FR-xxx → AC-xxx）
- [ ] **标准引用格式**：优先使用 Markdown 链接 `[编码（标题）](#锚点)`（见 [coding-system.md · 交叉引用规则](coding-system.md#交叉引用规则)）；纯文本场景再用统一分隔形式
- [ ] **标题一致性**：引用标题与索引完全一致
- [ ] **引用完整性**：重要引用都包含完整标题信息
- [ ] **格式统一性**：同一文档内引用格式保持一致
- [ ] **Markdown 兼容性**：引用格式在 Markdown 中渲染正常

### IF / PLN 类型使用合理性检查

判定细则见 [type-profiles.md](type-profiles.md)。此处只列是否误用：

- [ ] **IF 不被误限于 HTTP API**；不另增 `API` 类型码
- [ ] **IF/ACT 不重叠误用**：契约 → IF，动作 → ACT；双编码须可追溯
- [ ] **UC / FR / FLW / ACT 不混写**：对外承诺 → FR；用户路径 → UC；系统路径 → FLW；单次动作 → ACT；手段不标成 FR（见 [type-profiles.md · UC / FR / FLW / ACT](type-profiles.md#uc--fr--flw--act-的边界)）
- [ ] **PLN 使用边界**：本轮不实现的想法；不替代已稳定 FR/NFR/IF/ALG；不含执行信息；不与路线图互引
- [ ] **PLN 状态与落实正交**：定论即 `正式`，是否展开看 `落实情况`；落实本身不是废弃（见 [规划项生命周期](type-profiles.md#规划项生命周期pln-统一口径)）
- [ ] **PLN 落实一致性**：`已落实` 则 `落实记录` 非空且指向目标编码；`未落实` 写「无」或只记过程条目，MUST NOT 预填终局展开
- [ ] **PLN 落实双向可追溯**：目标细项定义块 MUST 有 `来源` 回指该 PLN
- [ ] **PLN 复审兜底**：`未落实` 且非 `废弃` MUST 填 `建议复审日期`
- [ ] **PLN 默认层级**：未指定时落在 L2；落在 L3–L5 须有架构/接口/算法依据
- [ ] **PLN 说明三要素**：想法内容、当前不做的原因、重新考虑的条件均可读

### 章节编号引用强制审查与修正指引

#### 强制判定（命中任一即不通过）
- [ ] 出现任何 `§x.y.z / 第x章 / 见上文` 形式的章节编号引用。
- [ ] 引用未使用细项编码或文档编码。
- [ ] 强约束句（唯一开关/必须/禁止/仅当）未给出可执行条件。

#### 审查结论分级
- **A 级（阻断合并）**：出现任意章节编号引用（必须清零后再审）。
- **B 级（当轮修正）**：虽无章节编号引用，但缺失编码化引用或可执行条件。
- **C 级（优化项）**：编码引用存在但追溯链路不完整。

#### 标准修正动作（Reviewer 强制指导）
1. 删除章节编号：移除所有 `§` / `第x章` / `见上文` 引用。
2. 落码替代：将引用改为细项编码或文档编码。
3. 补全定义：落为独立定义块（形态见 [coding-system.md · 细项定义块形态](coding-system.md#细项定义块形态mandatory)），按 What / Scope / When / Verify / Trace 补齐最小要素。
4. 复核通过：确认全文零章节编号引用后再进入下一轮评审。

#### 快速改写模板
- **原句（不合规）**：{业务结论}（详见 §x.y.z）
- **改写（合规）**：落为独立定义块，章节号引用改为 `来源` 属性行的标准链接

```markdown
<a id="{编码全小写}"></a>
### {TYPE-xxx}：{规则标题}

- **细项状态**：初稿
- **修订版本号**：1
- **最后修订日期**：YYYY-MM-DD
- **来源**：[{TYPE-xxx}（{细项标题}）]({定义所在文档相对路径}#{编码全小写})

{可独立执行的规则定义}
```

> MUST NOT 改写成单行的 `- {TYPE-xxx}：{定义}。引用依据：{Lx-xxx}`：该形态既是被禁的粗体式定义位变体，又用了《追溯类属性行命名》之外的近义名。依据为整份文档时链接不带锚点。

### 逐层合规性检查

从上层向下层逐级检查，确保下层不违背上层：

- [ ] **L1 vs L0**：利益相关者需求是否对齐战略目标（GOL-xxx）
- [ ] **L2 vs L1**：功能/非功能需求是否覆盖利益相关者场景（SCN-xxx）
- [ ] **L3 vs L2**：架构方案是否满足所有需求（FR-xxx, NFR-xxx）
- [ ] **L4 vs L3**：系统设计是否遵循架构原则（PRN-xxx）和约束（CON-xxx）
- [ ] **L5 vs L4**：详细设计是否符合接口契约（IF-xxx）和领域模型（DOM-xxx）；组件仍指向 L3 CMP
- [ ] **L6 vs L2**：验证场景是否追溯到需求（FR-xxx）和验收标准（AC-xxx）

## 常见问题检查

- **内容违规**：混入代码、脚本、SQL、配置片段或其他实现内容；流程图形式与复杂度不匹配
- **编码违规**：项目编码不合法、细项编码冲突、编码含义被修改、废弃编码重用、标题过度具体
- **索引违规**：正文定义的细项编码与文档清单、当前作用域 `README.md` 全局索引不同步；计数器未递增；废弃信息缺失
- **引用违规**：引用编码不存在、引用方向错误、格式不统一、标题缺失、Markdown 锚点渲染异常、REF 信息不完整
- **结构违规**：元信息缺失、变更记录缺失、命名不规范、日期或版本格式错误、表格或 Mermaid 语法不合法
- **完整性缺陷**：层级必需章节缺失、追溯链断裂、约束/假定/风险/度量指标遗漏
- **质量问题**：文档间结论冲突、表述模糊、结构混乱、过度设计、范围蔓延

## 编码索引完整性校验

### 校验原则

**核心要求**：对**正文中定义的细项编码**，必须在以下三个位置同时建立，缺一不可：
1. 文档正文中定义位置（符合《细项定义块形态》的完整定义块，含 `<a id>` 锚点行）
2. 文档末尾的细项编码清单
3. 当前作用域 `README.md` 的全局编码索引

### 校验步骤

#### 步骤 1：检查文档正文的编码定义

**方法**：在文档中搜索所有编码格式的标题（如 `### CRM-FR-001：用户登录功能`，其上方一行应为 `<a id="crm-fr-001"></a>`）

可使用编辑器搜索、仓库搜索工具或 `python3 scripts/check_docs.py` 提取这些标题；本文不绑定特定平台命令。

**检查项**：
- [ ] 每个编码标题包含项目编码（如已启用）、类型码、三位序号，且用**全角冒号**分隔标题文本
- [ ] 每个编码标题**上方紧邻一行**为 `<a id="{编码全小写}"></a>`（锚点房规单点见 [coding-system.md · 锚点定义位](coding-system.md#锚点定义位)，本文不复述细则）
- [ ] 锚点命名符合规范（全小写，短横线分隔），且与编码一一对应

#### 步骤 2：检查文档末尾的细项编码清单

仅适用于正文中定义了明确细项编码的文档。

**方法**：找到文档末尾的"细项编码清单"或"编码清单"章节

**检查项**：
- [ ] 清单包含正文中的所有编码
- [ ] 每个条目格式正确（编码 | 类型 | 标题 | 细项状态）
- [ ] 编码、类型、标题与正文完全一致
- [ ] 清单中的编码均为完整编码
- [ ] 无遗漏、无重复

#### 步骤 3：检查当前作用域 `README.md` 的全局索引

**方法**：打开当前作用域 `README.md`，找到对应的类型码表格（如 FR 类型码表格）

**检查项**：
- [ ] 新编码已在对应的类型码表格中
- [ ] 编码、标题与文档完全一致
- [ ] 编码计数器的“下一可用编号”已递增（如 CRM-FR 下一可用 016 → 017）
- [ ] 新编码按数字升序插入对应类型码表格，未追加到乱序位置
- [ ] 备注已更新（如"下一可用 017；序列无缺口"）

#### 步骤 4：验证一致性

**方法**：对比以下三个来源

| 来源 | 编码数量 | 最小编码 | 最大编码 |
|------|---------|---------|---------|
| 文档正文 | | | |
| 文档清单 | | | |
| 全局索引 | | | |

**检查项**：
- [ ] 三个来源的编码数量一致
- [ ] 三个来源的最小编码和最大编码一致
- [ ] 三个来源的编码列表完全相同（无遗漏、无多余）

### 编码冲突检查（防止重复定义）

**方法**：在 ued/ 目录下搜索目标编码

可使用编辑器全文搜索、仓库搜索工具或自定义脚本检索目标编码（本包附带 `scripts/check_docs.py --refs {编码}` 可直接列出全部定义 / 登记 / 引用位置）。

**检查项**：
- [ ] 新编码在 ued/ 目录下无重复定义
- [ ] 如发现重复，判断是复用现有编码还是冲突
- [ ] 冲突时需重新分配编码

### 编码计数器验证

**方法**：对比编码计数器与实际使用情况

建议提取当前作用域 `README.md` 的计数器信息，再对比所有 Markdown 文档中的实际编码使用情况；实现方式可按团队环境选择。

**检查项**：
- [ ] 计数器的“下一可用编号”未被使用
- [ ] 编码序列无缺口；废弃编号（含 `初稿` 期作废者）仍保留索引记录、仍占编号，因此不形成缺口

### 脚本已覆盖项

上列检查项中凡 `check_docs.py` 能报的，人工不必再逐条复述。跑：

```
python3 scripts/check_docs.py -p <ued>
python3 scripts/check_docs.py --check-templates
```

改技能包或模板时第二条 MUST 跑。人工只查脚本不覆盖的内容项：下层是否违背上层、算法/流程描述是否混入可执行代码、ADR 是否该升格、措辞是否可测试等（见上文各层检查清单）。
