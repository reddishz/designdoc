# 编码体系规范

编码的形态、类型码表、属性名封闭集、定义块形态、引用与分配规则。对象×字段×状态权限见 [object-model.md](object-model.md)；易重叠类型的专论见 [type-profiles.md](type-profiles.md)。

## 需求级别说明

本 skill 在规范正文与 AI 约束里混用 **中文**（必须、应当、可以、禁止）与 **英文**（MUST、SHOULD、MAY、MUST NOT），仅用于区分**约束松紧**，语义上**借鉴** [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) 的常见解释；**本 skill 不以 RFC 合规为交付目标**，也不要求宿主 `ued/` 文档逐条对照 RFC 或附加英文声明。

| 常见写法 | 含义（简要） |
|----------|----------------|
| **必须 / MUST** | 绝对要求，违反即视为不符合本规范 |
| **禁止 / MUST NOT** | 绝对不允许 |
| **应当 / SHOULD** | 强烈建议，除非有充分理由可不照做 |
| **不应当 / SHOULD NOT** | 强烈不建议 |
| **可以 / MAY** | 可选，由实现或项目裁量 |

**对业务文档的建议**：`ued/` 内设计文档一般用中文「必须、应当、可以」即可；若需对外或跨团队对齐，再视情况在文首加一句「关键词按 RFC 2119 理解」。

需求陈述与属性裁剪**借鉴** ISO/IEC/IEEE 29148:2011 第 5 章（个体/集合特征与属性示例）及第 8–9 章信息项大纲作裁剪参考；**本 skill 不以 29148 符合性为交付目标**，也不要求 `ued/` 文档按 StRS / SyRS / SRS 章节一一对应。

## 编码核心原则

1. **简洁优先**：默认忽略项目前缀。这是本系统的**标准模式**，适用于单应用或单作用域项目。
2. **全局唯一**：在同一仓库范围内，编码必须唯一。
3. **不可变更**：编码 ID、类型码与存在性一经分配即锁定。权限切片见 [object-model.md · 锁定矩阵](object-model.md#锁定矩阵mandatory)。

## 标准编码体系（推荐/默认）

### 细项编码

格式：`{类型码}-{三位序号}`，全系统唯一。

示例：`FR-001`、`NFR-003`、`PRN-005`、`RUL-010`

### 类型码表

| 类型码 | 含义 | 典型层级 | 说明 | 典型示例 |
|--------|------|----------|------|----------|
| GOL | 目标（Goal） | L0, L1 | 项目要达成的业务目标 | `GOL-001`: 实现用户月活增长20% |
| STK | 利益相关者（Stakeholder） | L1 | 项目的参与方和影响方 | `STK-001`: 普通个人用户 |
| SCN | 场景（Scenario） | L1, L2 | 用户使用场景和业务场景 | `SCN-001`: 用户在弱网环境下支付 |
| FR | 功能需求（Functional Req.） | L2 | 系统必须提供的功能 | `FR-001`: 支持第三方微信登录 |
| NFR | 非功能需求（Non-functional Req.） | L2 | 性能、安全、可用性等质量属性 | `NFR-001`: 核心接口响应时间 < 200ms |
| UC | 用例（Use Case） | L2 | 具体的用户操作流程 | `UC-001`: 用户找回密码流程 |
| PRN | 原则（Principle） | L3 | 必须遵循的设计规则和约束 | `PRN-001`: 无状态设计原则 |
| DEC | 决策（Decision） | L4, L5 | 从多个可行备选中**自主选定**的具体事项级决策；宏观架构级决策改用 ADR 文档（见 [type-profiles.md · ADR 与 DEC](type-profiles.md#adr-与-dec-的定位)） | `DEC-001`: 订单号采用「日期 + 分片号 + 序列号」三段式生成 |
| CMP | 组件/子系统（Component） | L3, L4 | 系统组成模块 | `CMP-001`: 订单处理子系统 |
| IF | 接口契约（Interface） | L4, L5 | 模块间的接口定义 | `IF-001`: 获取用户信息 API |
| FLW | 流程（Flow） | L4, L5 | 业务流程或系统流程 | `FLW-001`: 订单取消状态流转图 |
| ALG | 算法/逻辑（Algorithm） | L5 | 具体算法、计算逻辑或公式 | `ALG-001`: 阶梯价格计算公式 |
| DOM | 领域对象（Domain Object） | L4 | 业务领域的核心实体 | `DOM-001`: 订单（Order）实体模型 |
| ASM | 假设（Assumption） | 所有层级 | 项目设计时依赖的前提假设 | `ASM-001`: 假设用户手机均支持 HTTPS |
| RSK | 风险（Risk） | 所有层级 | 可能影响项目成功的风险因素 | `RSK-001`: 第三方支付接口可能无法及时上线 |
| MET | 指标（Metric/KPI） | L0, L1 | 用于衡量系统表现的关键指标 | `MET-001`: 系统年可用性达到 99.9% |
| TC | 测试场景（Test Case） | L6 | 测试用例和测试场景 | `TC-001`: 并发 1000 下的下单压力测试 |
| AC | 验收标准（Acceptance Criteria） | L2, L6 | 功能验收的具体标准 | `AC-001`: 支付成功后 5s 内发送短信通知 |
| CON | 约束（Constraint） | 所有层级 | 技术或业务约束 | `CON-001`: 必须兼容 IE11 浏览器 |
| RUL | 规则（Rule） | 所有层级 | 业务规则或计算规则 | `RUL-001`: 只有会员才能参与秒杀活动 |
| ACT | 动作定义（Action） | L4, L5 | 系统执行的具体动作和行为，包括消息、事件、命令、菜单等交互类型 | ACT-001: 用户注册动作定义 |
| PLN | 规划项（Plan Item） | L2-L5 | 当前不实现、留待将来考虑或细化的功能/需求想法 | `PLN-001`: 会话消息撤回能力（待将来考虑） |
| REF | 外部参考（Reference） | L2-L6 | 外部资料细项，需登记来源版本与最近核验日期 | REF-001: 《行业支付安全协议 v2.0》 |

> **`典型层级` 列的语义**：该列是**语义归属建议**，表达「这个类型通常在哪一层产生」，**不是物理存放限制**。细项 MAY 被任何层级文档收录——例如 `DEC` 典型在 L4/L5 产生，但也可作为细项出现在 ADR 文档内；`CON` / `RUL` 标注「所有层级」正因其可在任意层级文档中定义。判断某个细项该落在哪份文档，依据是**它所约束的对象属于哪一层**，而非该类型码的典型层级。横切类型（`CON` / `RUL` / `ASM` / `RSK`）按同一判定落层：`RSK` 定义在它所威胁的对象所在的文档——商业成败 → L0，干系人、交付与合规 → L1，范围与需求可实现性 → L2，技术选型与子系统 → L3，实现与运行 → L4/L5；`ASM` 定义在依赖该前提的那层文档。其余层只引用、不重复定义（见[引用写作强制流程](#引用写作强制流程)）。某层模板未给出某类型码的定义块，不构成违规。

### 属性行定义集（封闭）

属性行组承载的是**元数据**——可机检、可索引、可跨文档比对的离散事实。准入判据只有一条：**能用封闭取值集或一个结构化 token 表达的，才 MAY 写成属性行；需要成句表达的，一律归正文段**（正文段见《细项定义块形态》）。

本节是属性名的**唯一封闭集**：属性行组内 MUST NOT 出现本节未列出的属性名。未列出的语义一律写进正文段，MUST NOT 自造属性名承载——自造名会使该要素脱离机检与跨文档比对，等价于把正文伪装成元数据。

#### 固定属性（全类型码统一）

| 段位 | 属性名 | 值形态 | 出现条件 |
|------|--------|--------|----------|
| 治理段 | `细项状态` | 枚举：`初稿` / `正式` / `草案` / `废弃` | MUST，属性行组首行 |
| 治理段 | `修订版本号` | 正整数，新建为 `1` | MUST，第二行 |
| 治理段 | `最后修订日期` | `YYYY-MM-DD` | MUST，第三行 |
| 废弃登记段 | `废弃时间` | `YYYY-MM-DD` | 仅 `细项状态` 为 `废弃` 时 MUST |
| 废弃登记段 | `废弃原因` | 一句话内的决策依据（含替代思路的结论）；论证过程归正文段 | 同上 |
| 废弃登记段 | `替代方案` | 标准链接 / 「无」 | 同上 |
| 追溯段 | `出处` | 自然语言短语，MUST NOT 含链接 | MAY |
| 追溯段 | `来源` | 标准链接，MUST 含链接 | SHOULD，MAY 多行 |
| 追溯段 | `依赖` | 标准链接，MUST 含链接 | MAY，MAY 多行；无同层支撑时 MUST NOT 写空行 |

段位顺序与流转伴随口径见《细项定义块形态》、[status-definitions.md · 流转伴随字段](status-definitions.md#流转伴随字段只随指定转换写入)；废弃登记三字段的用法见 [item-deprecation.md](item-deprecation.md)；`出处` / `来源` / `依赖` 的语义分界见《追溯类属性行命名》。

- **值形态同样封闭**：自有属性的值 MUST 落在上表给出的形态内。链接类 MUST 用标准链接（见《交叉引用规则》），MUST NOT 写粗体裸编码（`**FR-001**`）——裸编码不可跳转、不可机检跟随，与《追溯类属性行命名》对 `来源` 的要求同理。
- **混合槽位 MUST 拆分**：一个槽位既要放编码又要放叙述时，MUST 拆开——编码进属性行、叙述进正文段。例如规则的判定口径写进正文段，`验证方式` 只留指向 AC / TC 的链接。
- **NFR `类别`**：`可用性` 指运行可用（uptime），`易用性` 指使用质量；功能安全仍用 `安全`，在正文区分。
- **正式 FR / NFR 的 `验证方式`**：`细项状态` 为 `正式` 时 SHOULD 有指向 AC 的 `验证方式`；检查器缺行报 WARNING，不阻断。`度量标准` 不替代该链接。
- **本表可扩充，但 MUST 先改本节**：新类型码或新的确需机检的离散要素，MUST 先在本节登记属性名与值形态，再在模板与文档中使用；MUST NOT 先在文档里写、事后追认。

### 细项定义最小要素（清晰性基线）

为避免“有编码、无定义”或“标题可读但不可执行”的情况，新增或修订细项时，**SHOULD** 至少满足以下要素：

1. **一句话定义（What）**：这个细项到底约束/声明了什么。
2. **边界说明（Scope）**：明确适用范围与不适用范围（至少说明一条非目标）。
3. **触发与条件（When）**：在什么场景、前置条件下生效。
4. **可验证性（Verify）**：给出可检查的验收口径、指标或判定方式（可引用 AC/TC/MET）。
5. **来源与追溯（Trace）**：至少关联一个上层依据（如 GOL/SCN/FR/NFR/PRN）；同层支撑另见 `依赖`。
6. **理由（Why）**：为什么需要这条；**写正文段**，MUST NOT 自造属性名 `理由`。

**承载位（MUST）**：要素分落两处，MUST NOT 混写——**离散事实进属性行组，叙述进正文段**（准入判据见《属性行定义集（封闭）》，两段形态见《细项定义块形态》）。

| 要素 | 承载位 |
|------|--------|
| What（一句话定义） | 正文段首段 |
| Scope（边界说明） | 正文段 |
| When（触发与条件） | 正文段 |
| Verify（可验证性） | 指向 AC / TC / MET 的链接落自有属性行（如 `验证方式`）；判定口径的叙述落正文段 |
| Trace（来源与追溯） | 追溯段属性行（`出处` / `来源`）；前提耦合用 `依赖`，不得写入 `来源` |
| Why（理由） | 正文段 |

#### 需求陈述（SHOULD）

FR / NFR 正文首段 **SHOULD** 写成可验证的对外承诺，不把实现方案写进需求陈述：

- **句式**：`[条件] 系统应当 [动作] [对象] [约束]`；一条一个「应当」；不用「不得」当主句（反面约束改写为正面放行条件，或落入 `不适用范围`）。
- **单数**：MUST NOT 用「和 / 以及 / 并且」把两条需求焊进同一个 FR / NFR。
- **无需实施**：写对外行为，MUST NOT 指定库、表、框架或可执行实现（与「`ued/` 不得含可执行代码」互补）。
- **禁模糊词**：最好、用户友好、尽可能、视情况、适当、不少于（无基准）等，MUST NOT 作为不可判定的主约束。
- **Necessary / Feasible**：评审时问「拿掉是否缺能力」「代价是否可接受」；不加属性行。

#### 标题命名规范（适度宽泛）

细项标题 **SHOULD** 描述可长期复用的设计对象，而非一次性实现细节：

- **适度宽泛**：避免过细（单字段、单按钮、单次会话级行为），也避免空泛到无法区分对象
- **与锁定规则一致**：标题自进入 `正式` 基线起锁定（`初稿` 期可改，但须同步全部引用处），因此命名必须覆盖其长期含义，而非仅当前版本做法（见 [object-model.md · 锁定矩阵](object-model.md#锁定矩阵mandatory)）
- **可检索**：能在全局编码索引中凭标题判断“这是不是我要找的细项”

反例：`FR-021 登录页密码输入框获焦时清除错误提示`（实现细节级）。正例：`FR-021 登录错误提示`。

#### 适用性边界（按类型分组）

不是所有类型码都要“等强度”满足上述要素。评审时应按类型语义做差异化判断：

| 类型分组 | 典型类型码 | 建议判定 | 说明 |
|----------|------------|----------|------|
| 目标/对象类 | GOL, STK, SCN, DOM, CMP | What + Scope + Trace 为主；When/Verify 可弱化 | 这类更偏“定义对象/目标”，不一定存在明确触发条件 |
| 需求/规则类 | FR, NFR, RUL, CON, AC, UC | What / Scope / When / Verify / Trace / Why 完整性要求最高 | 这类直接驱动设计与验收，必须可执行、可验证 |
| 设计/行为类 | IF, FLW, ALG, ACT, DEC, PRN | What + Scope + When + Trace 为主；Verify 通过关联 AC/TC/MET 满足 | 允许把验证口径放在下游验证文档，不要求都写在本细项正文 |
| 前瞻/不确定类 | PLN, RSK, ASM, MET | What + Scope + Trace 必需；When/Verify 视场景可选 | 这几类本身描述尚未确定或尚未实现的内容，触发与验证粒度可按项目裁量 |
| 外部参考类 | REF | What（来源说明）+ Scope（适用边界）必需；Trace 应指向被支撑细项；When/Verify 通常不作硬性要求 | REF 是“证据/依据”而非内部需求细项，不应机械套用触发条件 |

> 说明：以上是“定义质量”的基线与适用边界，不改变编码分配、索引同步、废弃处理等既有强制流程。


### 细项表达强制约束（彻底禁止章节编号引用）

为避免章节重排导致语义漂移，设计文档中执行以下**强制规则**：

- **MUST NOT（绝对禁止）**：使用章节编号（如 `§x.y.z`、`第x章`、`见上文`）进行任何语义引用。
- **MUST（引用替代）**：一切引用必须使用稳定标识：细项编码（如 `FR-001`、`RUL-012`）或文档编码（如 `L2-003`）。
- **MUST（独立定义）**：可独立成立的语义（规则、流程、算法、约束、背景结论）必须先落为独立细项定义并绑定细项编码。
- **MUST（强约束可执行）**：若句中出现“唯一开关/必须/禁止/允许/仅当”等强约束词，句内必须给出可执行条件（状态集合、阈值、触发者、对象边界、异常策略）。

#### 章节编号禁用原因（规范性说明）

- 章节编号会因文档重构、拆分、合并、排序变化而漂移，无法作为稳定真值锚点。
- 同一编号在不同版本可能映射不同语义，导致前后引用含义不一致。
- SSoT 体系要求“可追溯、可比对、可验证”的稳定标识，章节编号不满足该要求。

#### 引用写作强制流程

1. 先定义细项：将语义写成独立细项并分配编码。
2. 再做引用：在其他位置仅引用该细项编码/文档编码。
3. 禁止回退：不得以任何章节编号替代或补充上述稳定引用。

**反例（不合规）**：
- 生命周期状态是交易开关（详见 §1.4.3）。

**正例（合规）**：落为独立定义块（形态见《细项定义块形态》），章节号引用改为 `来源` 属性行的标准链接：

```markdown
<a id="rul-012"></a>
### RUL-012：生命周期状态交易放行开关

- **细项状态**：初稿
- **修订版本号**：1
- **最后修订日期**：YYYY-MM-DD
- **来源**：[L4-002（{文档标题}）]({L4 文档相对路径})

`RUNNING`、`EXITING` 允许交易，`WAITING`、`CLOSED` 禁止交易。
```

> 依据为整份文档时链接不带锚点；依据为某个细项时带该细项的锚点（见《锚点命名规范》）。

### 细项定义块形态（MANDATORY）

**术语**：
- **定义块**：一个细项编码在文档中的唯一完整定义所在处，由「锚点行 + 标题行 + 属性行组 + 正文段」四部分按序构成。
- **属性行**：属性行组内以 `- **{属性名}**：{值}` 书写的单行，一个属性独占一行、属性名具名，承载**元数据**。
- **属性行组三段**：属性行组按职责分为**治理段 → 内容段 → 追溯段**三段，段位与段内顺序均固定。
- **正文段**：属性行组之后、下一个标题或下一个定义块锚点之前的全部内容，承载**叙述**（段落、列表、表格、图、子标题均 MAY）。

**形态（MUST）**：定义块 MUST 按下列顺序书写，前三部分缺一不可；正文段按需书写。

```markdown
<a id="{编码全小写}"></a>
### {编码}：{标题}

- **细项状态**：{初稿/正式/草案/废弃}
- **修订版本号**：{正整数，新建为 1}
- **最后修订日期**：{YYYY-MM-DD}
- **{自有属性名}**：{离散值}
- **出处**：{自然语言，MUST NOT 含链接}
- **来源**：[{编码}（{标题}）](#{锚点})
- **依赖**：[{编码}（{标题}）](#{锚点})

{一句话写明本细项约束或声明了什么。}

{边界、触发条件、判定口径、异常处理等叙述，MAY 分段、用列表、用表格、用图或开子标题承载。}
```

- **锚点行**：MUST 为 `<a id="{编码全小写}"></a>`，独占一行，紧接标题行上方；编码含项目前缀时一并小写（`CRM-FR-001` → `<a id="crm-fr-001"></a>`）。锚点值与编码一一对应，MUST NOT 随标题改动而变动。
- **标题行**：MUST 为 Markdown 标题，格式 `{编码}：{标题}`，分隔符 MUST 用全角冒号 `：`。标题层级由所在小节深度决定，MUST 比父小节深一级；标题措辞见《标题命名规范》。
- **属性行**：MUST 为列表项 `- **{属性名}**：{值}`，MUST NOT 写成裸段落 `**{属性名}**：{值}` 或无粗体的 `- {属性名}：{值}`。属性名 MUST 取自《属性行定义集（封闭）》，值 MUST 落在该节给出的形态内。
- **三段 MUST 按序、MUST NOT 交错**：治理段（首）→ 内容段（中）→ 追溯段（末）。内容段即本类型码的自有属性，MUST NOT 把治理段或追溯段的属性名夹在内容段中间。
- **治理段（MUST，全类型码统一）**：`细项状态` / `修订版本号` / `最后修订日期` 三行 MUST 齐备、MUST 按此序位于属性行组最前；三者名与序全类型码一致，MUST NOT 改名、MUST NOT 缺行。新建时取 `初稿` / `1` / 新建当天；后两行属**流转伴随字段**，由 `正式→草案` 解冻动作写入，**MUST NOT** 单独手改（写入时机见 [status-definitions.md · 流转伴随字段](status-definitions.md#流转伴随字段只随指定转换写入)，递增与回退口径见 [status-definitions.md · 细项修订版本号](status-definitions.md#细项修订版本号与文档版本号独立演化)）。细项 `废弃` 时，废弃登记字段（`废弃时间` / `废弃原因` / `替代方案`）MUST 紧随治理段之后、内容段之前（见 [item-deprecation.md](item-deprecation.md)）。
- **追溯段（MUST 位于末尾）**：`出处` / `来源` / `依赖` MUST 置于属性行组末尾，顺序为 `出处` → `来源` → `依赖`（无则省略，不得颠倒）；MUST NOT 把它们夹在内容段中间。**值形态**：`来源` 与 `依赖` 的值 MUST 含标准链接，`出处` 的值 MUST NOT 含链接（命名与用法见《追溯类属性行命名》）。`依赖` **不受**依据方向豁免（见 [status-definitions.md · 层级门控](status-definitions.md#层级门控文档状态--细项状态mandatory)）。
- **前三部分 MUST 连续（顺序不可打断）**：标题行下方 MUST 紧接属性行组（其间只允许空行），MUST NOT 插入图表、表格、子标题或散文段落——夹在中间会使属性行组的边界不可机检。
- **正文段 MUST 紧随属性行组、且与它空一行**：属性行组结束即元数据结束，其后的叙述全归正文段。不空行会使正文被解析为属性行组的续行或裸段落。
- **正文段形态自由**：MAY 按本细项的特征自行组织——分段、列表、表格、图、子标题均可；子标题 MUST 比定义块标题行深一级，遇到同级或更浅的标题即本定义块结束。最小要素的叙述完整性由《细项定义最小要素》与评审清单把关，不由形态约束。
- **正文段 MUST NOT 与属性元数据混淆**：正文段内 MUST NOT 出现 `- **{名}**：{值}` 形态的行，也 MUST NOT 用去掉列表符的 `**{名}**：{值}` 绕过——两种写法在 `ued/` 文档中均为属性行专用。需要带小标题的并列叙述，MUST 改用表格、子标题或不给 `{名}` 加粗的普通列表（`- {名}：{值}`）。MUST NOT 把 `MUST` / `MUST NOT` / `SHOULD` 一类规范关键字、或「一句话」「推论」「理由」一类写作提要词当作属性名。

**禁止形态（MUST NOT）**：MUST NOT 以列表项加粗编码充当定义块，即 MUST NOT 写 `- **{编码}**：{描述}`。该形态下编码不进文档大纲、标题与描述争夺同一槽位、无属性行组可承载元数据、且不产生任何锚点。

**无编码小节 MUST NOT 用属性行形态**：`ued/` 文档中不带细项编码的小节（如概述、职责划分、测试范围、后果、统计概览）同样 MUST NOT 用 `- **{名}**：{值}` 或 `**{名}**：{值}` 罗列内容。离散数据改用表格，叙述改用段落或不给 `{名}` 加粗的普通列表；确需承载元数据时 MUST 先落为带编码的定义块。追溯字段（`出处` / `来源` / `依赖`）尤其 MUST NOT 出现在无编码小节内——脱离定义块的追溯关系不进索引、不可机检跟随，改为在正文里用标准链接写明依据。

**属性行形态的唯一豁免**：REF 文档的 `## 来源信息` 小节承载**文档级**元数据（本文档所引外部资料的类型、出处、链接与时效字段），MAY 用属性行形态且不带细项编码；属性名 MUST 取自《属性行定义集（封闭）》的 REF 行。豁免范围仅限该小节，MUST NOT 推广到其他无编码小节。

**同类多项**：同一小节定义多个同类细项时，MUST 逐项重复完整定义块，MUST NOT 用连续列表项罗列。

**与「独立定义」的关系**：本条是《细项表达强制约束》中 `MUST（独立定义）` 的形态落地——凡要求「落为独立细项定义」处，一律指落为符合本条形态的定义块。

### 追溯类属性行命名（MANDATORY）

`出处` 与 `来源` 回答「这条细项从哪来」；`依赖` 回答「本细项要成立或可验证，还需要谁同时有效」。三者 MUST NOT 混用、MUST NOT 另造近义名。

| | `出处` | `来源` | `依赖` |
|--|--------|--------|--------|
| **问题** | 编码体系外从哪来 | 这条陈述从哪条已编码依据派生 / 下放 / 落实 | 本细项要成立或可验证，还需要谁同时有效 |
| **写法** | 自然语言，MUST NOT 含链接 | 标准链接，MUST 含链接 | 标准链接，MUST 含链接 |
| **例子** | 用户反馈、评审遗留、某法规 | `[SCN-001（…）](…)`、回指 PLN | 维持舱温 → 测外温；审计日志 → 登录 |
| **位置** | 追溯段内、`来源` 之前 | `出处` 之后、`依赖` 之前；MAY 多行 | 属性行组末尾；MAY 多行，每行一个对象 |

**`出处` / `来源` 判别**：能写成 `{类型码}-{编号}` 或文档编码 → `来源`；不能（没有对应编码）→ `出处`。派生自上层细项、规划项、ADR，测试用例派生自需求，一律 `来源`。

**`来源` / `依赖` 判别**：

- 删了对方，我还是不是同一句话？→ `来源`（细化 / 落实）。
- 对方不在了，我还能否单独成立 / 还有没有存在理由？→ `依赖`（前提 / 支撑）。
- 反转 `来源` 只得到「谁引用了我」，不是依赖图。

**`依赖` 方向（只存一种）**：A `依赖` B 表示 A 需要 B 同时有效。反向边（谁依赖我）由检查器与作废流程反转，MUST NOT 双向手写。无同层支撑时 MUST NOT 写空的 `依赖` 行。

- **互斥**：同一对象 MUST NOT 既出现在 `来源` 又出现在 `依赖`。已有专名的关系 MUST NOT 再写 `依赖`：`处理规则`、`所属组件`、`参与者`、`验证方式`、`满足需求`。
- **自指**：`依赖` MUST NOT 指向本细项。
- **可机检**：追溯段 MUST 居末且 `出处` → `来源` → `依赖`；`来源` / `依赖` 值无链接、或 `出处` 值含链接，均为违规（段位见《细项定义块形态》）。
- **依据方向**：`依赖` **不豁免**。[status-definitions.md · 层级门控](status-definitions.md#层级门控文档状态--细项状态mandatory) 的豁免只覆盖 `出处` / `来源` / `落实记录`。`正式` / `草案` MUST NOT `依赖` `初稿`。
- **不属追溯语义的属性保留专名**：`所属组件`（结构归属）、`参与者`（横向关系）MUST 保留原名，MUST NOT 并入 `来源` 或 `依赖`。
- REF 文档的 `## 来源信息` 是**小节名**，不是本条的属性名；其内文本型属性行仍用 `出处`。该小节的属性行形态豁免见《细项定义块形态》。
- 文档小节名「约束与假设」（`CON` / `ASM`）不是本属性；环境前提落那些类型码，细项间耦合才用 `依赖`。

## 文档编码

格式：`L{层级}-{三位序号}` 或 `ADR-{三位序号}` 或 `REF-{三位序号}`。

示例：`L0-001`（战略文档）、`L2-003`（需求文档）、`ADR-005`（架构决策记录）。

启用项目编码时，前缀加在本格式之前（如 `ERP-L2-003`），见《扩展编码格式》。

**ADR / REF 的层级归属**：二者的序号是**全局序号、不含层级**，因此层级 MUST NOT 写进编码，而由存放目录 + 元信息表的 `层级` 字段 + `关联文档` 字段三处共同表达。ADR 归属 **L3 概念架构**（存于 `L3-architecture/`，且 MUST NOT 单设 `adr/` 子目录；依据见 [layer-system.md · 层级定义](layer-system.md#层级定义)）；REF 不属任何层级，统一存于 `references/`。**MUST NOT** 为 ADR / REF 另造含层级的编码形式（如 `L3-ADR-001`）。ADR 与 DEC 的分工见 [type-profiles.md · ADR 与 DEC](type-profiles.md#adr-与-dec-的定位)。

**未定义前缀 MUST NOT 使用**：路线图、产品规划总览等文档同样属于某个层级，**MUST** 使用其所属层级的文档编码（如路线图 `L0-002`、规划总览 `L1-001`），**MUST NOT** 自创 `PLANNING-001`、`ROADMAP-001` 等未定义文档编码；其内部的规划项仍用 `PLN-xxx` 细项编码。

## 扩展用法：多应用管理（仅多应用模式启用）

在 99% 的场景下，**MUST NOT** 启用此功能。仅当满足以下**所有**条件，且请求发起方明确要求时，才考虑启用：

1. **多应用共存**：在同一个 `ued/` 目录下管理完全独立的应用。
2. **企业级合规**：公司明确规定所有文档、所有设计细项必须带有全局统一的 ID 标识前缀。
3. **已显式登记**：顶层 `ued/README.md` 的应用注册表与应用级 `README.md` 中均声明了 `project_code`。

### 强制提示启用场景

提示时机、确认话术与解析链见 [SKILL.md · AI 运行时配置解析规则](../SKILL.md#ai-运行时配置解析规则)。

### 项目编码规则
- **格式要求**：2-5 位，MUST 以大写字母开头，其余各位 MAY 为大写字母或数字（`[A-Z][A-Z0-9]{1,4}`），如 `CRM`、`ERP`、`W3T`。
- **MUST NOT 与类型码同形**：项目编码 MUST NOT 等于[类型码表](#类型码表)里的任何类型码（如 `FR` / `UC` / `CON`）。同形会使 `FR-001` 无法判定是「类型码 `FR` 的第 001 项」还是「项目编码 `FR` 加序号 001」。
- **MUST NOT 形如 `L` 加数字**：文档编码以 `L0-L6` 起头，项目编码取 `L2` 之类会与文档编码 `L2-001` 同形。
- **分配原则**：全局唯一；应体现项目或产品线特征；项目一旦启动并分配编码，禁止中途修改。

解析链与启用确认见 [SKILL.md · AI 运行时配置解析规则](../SKILL.md#ai-运行时配置解析规则)。

### 扩展编码格式
前缀加在**细项编码与文档编码**两者之前，其余形态与简洁编码一一对应：

| 编码类别 | 扩展格式 | 示例 |
|----------|----------|------|
| 细项编码 | `{项目编码}-{类型码}-{编号}` | `CRM-FR-001`、`W3T-RUL-014` |
| 文档编码 | `{项目编码}-{L层级 / ADR / REF}-{三位序号}` | `ERP-L2-003`、`W3G-ADR-001` |

### 编码分配即时更新机制

**核心要求**：新生成编码 ID 时，**MUST** 立即更新所有相关索引。

### README 索引排序与计数器治理（MANDATORY）

当前作用域 `README.md` 是细项索引与编码分配的操作入口，必须遵循：

- **编写阶段**：新增细项只取“下一可用编号”；必须插入到对应类型码表的数字升序位置，禁止为了省事追加到小节末尾。
- **审查阶段**：检查每个类型码小节内的全局编码索引是否按编码数字升序排列（如 `RUL-007`、`RUL-008`、`RUL-029`），并确认正文、文档清单、README 索引三方一致。
- **校验阶段**：校验编码序列完整性（全部分配过的编号，不分状态）；发现缺口时应补齐索引记录或废弃记录，禁止直接分配缺口编号。
- **计数器同步**：新增后把「下一可用编号」更新为新编号 + 1，批量新增时按批量最大值一次性更新。等式（MUST 等于已用最大编号 + 1）与缺口判定见 [object-model.md · 锁定矩阵](object-model.md#锁定矩阵mandatory)。
- **变更倒序**：README 或文档内变更记录按版本号或日期倒序排列，最新记录置顶。

## 交叉引用规则

### 标准引用格式
引用细项编码时，**必须使用链接格式**：
`[{编码}（{标题}）](#{编码锚点})`

**适用范围**：正文叙述与属性行（如 `来源`、`依赖`、`参与者`、`所属组件`）中的引用 **MUST** 使用上述链接格式；**表格型追溯**（追溯矩阵、本文档细项清单、全局编码索引）**MAY** 写裸编码，因列头已表达引用关系。跨文档时链接路径写实际相对路径，模板中的 `{L1 文档相对路径}` 等即为该占位写法。

### 示例
- **默认引用**：`[FR-001（用户身份认证功能）](#fr-001)`
- **跨文档引用**：`[FR-001（用户身份认证功能）](../L2-requirements/user-auth.md#fr-001)`
- **高级引用（含项目编码）**：`[CRM-FR-001（用户身份认证功能）](#crm-fr-001)`

### 锚点命名规范
- 格式：`#{编码全小写}`
- 示例：`#fr-001`、`#crm-fr-001`

### 锚点定义位

锚点由定义块的**锚点行**显式提供，不依赖标题自动生成的 slug：

- 每个细项定义块 MUST 在标题行上方写 `<a id="{编码全小写}"></a>`（形态见《细项定义块形态》）。
- 标题自动 slug **MUST NOT** 用作细项锚点：标题 `### FR-001：用户身份认证功能` 的 slug 含标题文本，会随标题改动而失效。
- **MUST NOT** 使用 `{#编码小写}` 属性语法：该语法在 GitHub 等 cmark-gfm 渲染器下不生效，花括号会作为字面文本渲染进标题。
- 同文档引用写 `](#{编码全小写})`；跨文档引用写 `]({相对路径}#{编码全小写})`。
- 引用 ADR / REF 等**整份文档**时用文档链接 `[{文档编码}（{标题}）]({相对路径})`，不带锚点。
