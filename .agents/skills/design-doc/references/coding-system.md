# 编码体系规范

## 需求级别说明

本 skill 在规范正文与 AI 约束里混用 **中文**（必须、应当、可以、禁止）与 **英文**（MUST、SHOULD、MAY、MUST NOT），仅用于区分**约束松紧**，语义上**借鉴** [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) 的常见解释；**本 skill 不以 RFC 合规为交付目标**，也不要求宿主 `ued/` 文档逐条对照 RFC 或附加英文声明。

| 常见写法 | 含义（简要） |
|----------|----------------|
| **必须 / MUST** | 绝对要求，违反即视为不符合本规范 |
| **禁止 / MUST NOT** | 绝对不允许 |
| **应当 / SHOULD** | 强烈建议，除非有充分理由可不照做 |
| **不应当 / SHOULD NOT** | 强烈不建议 |
| **可以 / MAY** | 可选，由实现或项目裁量 |

**对业务文档的建议**：`ued/` 内设计文档一般用中文「必须、应当、可以」即可；若需对外或跨团队对齐，再视情况在文首加一句「关键词按 RFC 2119 理解」。

## 编码核心原则

1. **简洁优先**：默认忽略项目前缀。这是本系统的**标准模式**，适用于单应用或单作用域项目。
2. **全局唯一**：在同一仓库范围内，编码必须唯一。
3. **不可变更**：编码的 **ID 与类型码** 一经分配即**绝对锁定**（不区分状态）；**标题** 与 **业务含义** 自进入 `正式` 起锁定（`初稿` 期标题可改，但须同步全部引用处）。完整规则单点承载于[编码含义锁定](#编码含义锁定mandatory)，其他章节与本文件以外文件一律引用、不复述。

### 编码锁定约束（MANDATORY）

见本文[编码含义锁定](#编码含义锁定mandatory)与[修改操作矩阵](#修改操作矩阵must-comply)：**编码 ID 与类型码的锁定绝对且与状态无关**；标题在 `初稿` 期可改（须同步引用），进入 `正式` 后锁定；内容修订走 `正式→草案` 解冻通道。

## 标准编码体系（推荐/默认）

### 细项编码

格式：`{类型码}-{三位序号}`，全系统唯一。

示例：`FR-001`、`NFR-003`、`PRN-005`、`RUL-010`

### 类型码表

| 类型码 | 含义 | 典型层级 | 说明 | 典型示例 |
|--------|------|----------|------|----------|
| GOL | 目标（Goal） | L0, L1 | 项目要达成的业务目标 | `GOL-001`: 实现用户月活增长20% |
| STK | 利益相关者（Stakeholder） | L1 | 项目的参与方和影响方 | `STK-001`: 普通个人用户 |
| SCN | 场景（Scenario） | L1, L2 | 用户使用场景和业务场景 | `SCN-001`: 用户在弱网环境下支付 |
| FR | 功能需求（Functional Req.） | L2 | 系统必须提供的功能 | `FR-001`: 支持第三方微信登录 |
| NFR | 非功能需求（Non-functional Req.） | L2 | 性能、安全、可用性等质量属性 | `NFR-001`: 核心接口响应时间 < 200ms |
| UC | 用例（Use Case） | L2 | 具体的用户操作流程 | `UC-001`: 用户找回密码流程 |
| PRN | 原则（Principle） | L3 | 必须遵循的设计规则和约束 | `PRN-001`: 无状态设计原则 |
| DEC | 决策（Decision） | L3/ADR | 从多个可选方案中选择的具体决策 | `DEC-001`: 使用 PostgreSQL 存储业务数据 |
| CMP | 组件/子系统（Component） | L3, L4 | 系统组成模块 | `CMP-001`: 订单处理子系统 |
| IF | 接口契约（Interface） | L4, L5 | 模块间的接口定义 | `IF-001`: 获取用户信息 API |
| FLW | 流程（Flow） | L4, L5 | 业务流程或系统流程 | `FLW-001`: 订单取消状态流转图 |
| ALG | 算法/逻辑（Algorithm） | L5 | 具体算法、计算逻辑或公式 | `ALG-001`: 阶梯价格计算公式 |
| DOM | 领域对象（Domain Object） | L4 | 业务领域的核心实体 | `DOM-001`: 订单（Order）实体模型 |
| ASM | 假设（Assumption） | L1, L2 | 项目设计时依赖的前提假设 | `ASM-001`: 假设用户手机均支持 HTTPS |
| RSK | 风险（Risk） | L1, L2 | 可能影响项目成功的风险因素 | `RSK-001`: 第三方支付接口可能无法及时上线 |
| MET | 指标（Metric/KPI） | L0, L1 | 用于衡量系统表现的关键指标 | `MET-001`: 系统年可用性达到 99.9% |
| TC | 测试场景（Test Case） | L6 | 测试用例和测试场景 | `TC-001`: 并发 1000 下的下单压力测试 |
| AC | 验收标准（Acceptance Criteria） | L2, L6 | 功能验收的具体标准 | `AC-001`: 支付成功后 5s 内发送短信通知 |
| CON | 约束（Constraint） | 所有层级 | 技术或业务约束 | `CON-001`: 必须兼容 IE11 浏览器 |
| RUL | 规则（Rule） | 所有层级 | 业务规则或计算规则 | `RUL-001`: 只有会员才能参与秒杀活动 |
| ACT | 动作定义（Action） | L4, L5 | 系统执行的具体动作和行为，包括消息、事件、命令、菜单等交互类型 | ACT-001: 用户注册动作定义 |
| PLN | 规划项（Plan Item） | L2-L5 | 当前不实现、留待将来考虑或细化的功能/需求想法 | `PLN-001`: 会话消息撤回能力（待将来考虑） |
| REF | 外部参考（Reference） | L2-L6 | 外部资料细项，需登记来源版本与最近核验日期 | REF-001: 《行业支付安全协议 v2.0》 |

### 细项定义最小要素（清晰性基线）

为避免“有编码、无定义”或“标题可读但不可执行”的情况，新增或修订细项时，**SHOULD** 至少满足以下要素：

1. **一句话定义（What）**：这个细项到底约束/声明了什么。
2. **边界说明（Scope）**：明确适用范围与不适用范围（至少说明一条非目标）。
3. **触发与条件（When）**：在什么场景、前置条件下生效。
4. **可验证性（Verify）**：给出可检查的验收口径、指标或判定方式（可引用 AC/TC/MET）。
5. **来源与追溯（Trace）**：至少关联一个上层依据（如 GOL/SCN/FR/NFR/PRN）。

#### 标题命名规范（适度宽泛）

细项标题 **SHOULD** 描述可长期复用的设计对象，而非一次性实现细节：

- **适度宽泛**：避免过细（单字段、单按钮、单次会话级行为），也避免空泛到无法区分对象
- **与锁定规则一致**：标题一经分配即**绝对锁定**，因此命名必须覆盖其长期含义，而非仅当前版本做法
- **可检索**：能在全局编码索引中凭标题判断“这是不是我要找的细项”

反例：`FR-021 登录页密码输入框获焦时清除错误提示`（实现细节级）。正例：`FR-021 登录错误提示`。

#### 适用性边界（按类型分组）

不是所有类型码都要“等强度”满足 5 要素。评审时应按类型语义做差异化判断：

| 类型分组 | 典型类型码 | 建议判定 | 说明 |
|----------|------------|----------|------|
| 目标/对象类 | GOL, STK, SCN, DOM, CMP | What + Scope + Trace 为主；When/Verify 可弱化 | 这类更偏“定义对象/目标”，不一定存在明确触发条件 |
| 需求/规则类 | FR, NFR, RUL, CON, AC, UC | 5 要素完整性要求最高 | 这类直接驱动设计与验收，必须可执行、可验证 |
| 设计/行为类 | IF, FLW, ALG, ACT, DEC, PRN | What + Scope + When + Trace 为主；Verify 通过关联 AC/TC/MET 满足 | 允许把验证口径放在下游验证文档，不要求都写在本细项正文 |
| 前瞻/不确定类 | PLN, RSK, ASM, MET | What + Scope + Trace 必需；When/Verify 视场景可选 | 这几类本身描述尚未确定或尚未实现的内容，触发与验证粒度可按项目裁量 |
| 外部参考类 | REF | What（来源说明）+ Scope（适用边界）必需；Trace 应指向被支撑细项；When/Verify 通常不作硬性要求 | REF 是“证据/依据”而非内部需求细项，不应机械套用触发条件 |

> 说明：以上是“定义质量”的基线与适用边界，不改变编码分配、索引同步、废弃处理等既有强制流程。


### 细项表达强制约束（彻底禁止章节编号引用）

为避免章节重排导致语义漂移，设计文档中执行以下**强制规则**：

- **MUST NOT（绝对禁止）**：使用章节编号（如 `§x.y.z`、`第x章`、`见上文`）进行任何语义引用。
- **MUST（引用替代）**：一切引用必须使用稳定标识：细项编码（如 `FR-001`、`RUL-012`）或文档编码（如 `L2-003`）。
- **MUST（独立定义）**：可独立成立的语义（规则、流程、算法、约束、背景结论）必须先落为独立细项定义并绑定细项编码。
- **MUST（强约束可执行）**：若句中出现“唯一开关/必须/禁止/允许/仅当”等强约束词，句内必须给出可执行条件（状态集合、阈值、触发者、对象边界、异常策略）。

#### 章节编号禁用原因（规范性说明）

- 章节编号会因文档重构、拆分、合并、排序变化而漂移，无法作为稳定真值锚点。
- 同一编号在不同版本可能映射不同语义，导致前后引用含义不一致。
- SSoT 体系要求“可追溯、可比对、可验证”的稳定标识，章节编号不满足该要求。

#### 引用写作强制流程

1. 先定义细项：将语义写成独立细项并分配编码。
2. 再做引用：在其他位置仅引用该细项编码/文档编码。
3. 禁止回退：不得以任何章节编号替代或补充上述稳定引用。

**反例（不合规）**：
- 生命周期状态是交易开关（详见 §1.4.3）。

**正例（合规）**：
- `RUL-012`：生命周期状态是交易放行开关；`RUNNING`、`EXITING` 允许交易，`WAITING`、`CLOSED` 禁止交易。引用依据：`L4-002`。

### 编码生命周期规则

- 序号从 001 开始，在同一类型码内单调递增。
- 编码进入 `正式` 基线后，**MUST NOT** 被删除或复用；`初稿` 期细项可增删改，删除后编号可回收（见 [status-definitions.md](status-definitions.md#状态即基线冻结规则mandatory)）。
- 已正式化的编码不再使用时 **MUST** 标注为"废弃"并保留；`初稿` 期删除则直接删除条目、不留废弃记录、不计缺口。
- `草案` 期（已定稿后重开）**MUST NOT** 直接删除：或 `回退` 到上一 `正式` 基线，或直接 `废弃`。

### 编码含义锁定（MANDATORY）

本节是"编码锁定"的**唯一完整表述**，也是 SSoT 的第一优先级保证：同一编码在任何时刻只指向同一事物。锁定分三层，与“状态即基线”**正交**（状态维度的权限边界见 [status-definitions.md · 锁定矩阵](status-definitions.md#锁定矩阵mandatory)）：

- **第一层：ID / 类型码——绝对锁定，不区分状态**
  - MUST NOT：就地修改已分配编码的 ID 或类型码（编码由分配流程产生，不存在"随意修改"的情形）
  - 类型码确实用错 → `初稿` 期删除该细项后按分配流程重新创建（未发布、编号可回收、不计缺口）；已 `正式` → 只能废弃 + 新增
- **第二层：标题——自进入 `正式` 基线起锁定**
  - `初稿` 期**可改**，但 **MUST** 先扫描全部引用处（可用 `python3 scripts/check_docs.py --refs {编码}`）并一并同步修改
  - `正式` / `草案` 期 MUST NOT 修改；确需改标题 → 只能废弃 + 新增，编号永不复用
- **第三层：业务含义 / 判定口径——自进入 `正式` 基线起锁定**
  - MUST NOT：修改已正式化编码的业务含义；需变更时废弃 + 新增
  - `初稿` 与 `草案` 期可直接编辑含义（前者尚未构成被引用的事实来源，后者已解冻）
  - MUST：保留所有已正式化编码的完整历史记录
- **不锁定的部分**：不触及上述三层的正文描述、属性、图示与追溯关系，在 `正式` 后走解冻修订通道，**不属于违规**；记录型字段（变更记录、落实记录、建议复审日期、核验日期等）在任何状态下均可追加，见 [status-definitions.md · 记录型字段](status-definitions.md#记录型字段不参与冻结)
- **缺口判定**：计数器"下一可用编号"与"不得留缺口"仅对已正式化编码成立；`初稿` 期新增后又被删除的编码可回收，不计缺口。

## 文档编码

格式：`L{层级}-{三位序号}` 或 `ADR-{三位序号}` 或 `REF-{三位序号}`。

示例：`L0-001`（战略文档）、`L2-003`（需求文档）、`ADR-005`（架构决策记录）。

**未定义前缀 MUST NOT 使用**：路线图、产品规划总览等文档同样属于某个层级，**MUST** 使用其所属层级的文档编码（如路线图 `L0-002`、规划总览 `L1-001`），**MUST NOT** 自创 `PLANNING-001`、`ROADMAP-001` 等未定义文档编码；其内部的规划项仍用 `PLN-xxx` 细项编码。

## 扩展用法：多应用管理（仅多应用模式启用）

在 99% 的场景下，**MUST NOT** 启用此功能。仅当满足以下**所有**条件，且请求发起方明确要求时，才考虑启用：

1. **多应用共存**：在同一个 `ued/` 目录下管理完全独立的应用。
2. **企业级合规**：公司明确规定所有文档、所有设计细项必须带有全局统一的 ID 标识前缀。
3. **已显式登记**：顶层 `ued/README.md` 的应用注册表与应用级 `README.md` 中均声明了 `project_code`。

### 强制提示启用场景
- 当 AI 识别到 `ued/` 下已经存在多个应用、多个独立业务域或明显分属不同产品线的设计文档时，**MUST** 提示切换到多应用目录结构，并为每个应用配置独立 `project_code`。
- 当 AI 识别到仓库内已存在某一应用的设计文档，而当前任务是在其基础上新增另一应用的设计文档时，**MUST** 在分配新编码前提示创建应用子目录、补齐应用级 `README.md`，并启用项目编码前缀。
- 此类提示的目的，是保证多应用并行维护时，编码、索引、跨文档引用和废弃追溯仍然保持全局唯一且可辨识。

### 项目编码规则
- **格式要求**：2-4 位大写字母（A-Z）。
- **获取优先级**：
  1. 当前作用域 `README.md` 中的 `project_code`
  2. 顶层 `ued/README.md` 应用注册表中的 `project_code`（多应用模式下交叉校验）
  3. 默认值：空（即不启用前缀，回退简洁编码格式）
- **分配原则**：
  - **全局唯一**：每个项目编码在全局范围内唯一。
  - **语义化**：应体现项目或产品线特征（如 `CRM`, `ERP`）。
  - **不可变更**：项目一旦启动并分配编码，禁止中途修改。

### 扩展编码格式
- 格式：`{项目编码}-{类型码}-{编号}`
- 示例：`CRM-FR-001`、`ERP-L2-003`

### 获取方式
1. 默认情况下，AI 应假设项目编码为空，直接生成标准格式编码（如 `FR-001`）。
2. 若当前作用域 `README.md` 中定义了 `project_code`，AI 应当发起确认：“检测到项目编码配置，后续生成 ID 是否启用该前缀？”
3. 只有在请求发起方明确确认后，才开始在所有新生成的 ID 中加入该前缀。
4. 若 AI 检测到“多应用并存”或“在已有应用基础上新增另一应用”这两类场景，而当前作用域 `README.md` 尚未配置 `project_code`，则 **MUST** 先提示补充配置，再继续后续编码分配流程。

## 编码分配管理

### 作用域级全局编码索引

在当前作用域的 `README.md` 中维护各类别编码的全局索引：
- 单应用模式：`ued/README.md`
- 多应用模式：`ued/{app-name}/README.md`

顶层 `ued/README.md` 在多应用模式下 **MUST NOT** 承担每个应用细项级编码索引的真值源，只维护应用注册表与跨应用入口。

```markdown
## 全局编码索引

### 按类型码索引

#### FR - 功能需求
| 编码 | 标题 | 所属文档 | 细项状态 |
|------|------|----------|------|
| FR-001 | 用户身份认证功能 | L2-001 | 初稿 |
| FR-002 | 商品搜索功能 | L2-001 | 正式 |
```

### 编码分配即时更新机制

**核心要求**：新生成编码 ID 时，**MUST** 立即更新所有相关索引。

1. **作用域级全局编码索引**（当前作用域 `README.md`）：在对应类型码表格中按编码数字升序插入新编码条目，禁止乱序追加。
2. **文档细项清单**（当前文档末尾）：在表格中列出该文档定义的所有编码，并与 README 索引保持标题、状态、所属文档一致。
3. **编码计数器**：仅维护“下一可用编号”；新增细项只使用“下一可用编号”，并确保**已正式化**编码序列完整、无缺口（`初稿` 期删除的编号可回收，不计缺口）。

### AI 编码分配强制流程

新增细项时 **MUST** 严格遵循以下流程：

```
⚠️ 警告：编码的全局唯一性是体系核心，AI 不得随意在文档内自增编号！

1. 确定编码模式（简洁优先原则）
   默认一律采用简洁模式（如 `FR-015`）。
   只有当当前作用域 `README.md` 中声明了 `project_code` 且请求发起方在 Checkpoint 中明确要求使用时，才启用高级模式（如 `CRM-FR-015`）。

2. 读取编码计数器与全局编码索引
   打开当前作用域 `README.md`，读取"编码计数器"中的“下一可用编号”，再定位"全局编码索引"中对应类型码表格。

3. 获取最新编码
   必须使用“下一可用编号”构造编码（如 `FR-015`），若发现**已正式化**编号缺口，先修复索引一致性或补齐废弃记录，不得直接分配缺口编号（`初稿` 期删除的编号可回收）。

4. 搜索现有编码（强制步骤，不可跳过）
   在 ued/ 目录下搜索所有 .md 文件。
   确认目标编码（含前缀，如有）是否已被使用。

5. 外部确认 (Checkpoint)
   如果是批量新增或涉及核心业务规则变更，
   MUST 暂停并请求确认编码标题与定义是否准确。

6. 即时更新索引（编码分配后立即执行，**MUST NOT** 延迟）
   a) **MUST** 在当前文档末尾的"细项编码清单"中添加新编码
   b) **MUST** 在当前作用域 `README.md` 的全局索引中按编码数字升序插入新编码条目，**MUST NOT** 追加到表尾造成乱序
   c) **MUST** 将编码计数器的“下一可用编号”递增到新分配编号的后一位

7. 验证索引一致性与排序
   **MUST** 确认新编码在文档清单和全局索引中都正确建立；同一类型码索引按数字升序排列；编码序列无缺口；变更记录按版本号或日期倒序排列。
```


### README 索引排序与计数器治理（MANDATORY）

当前作用域 `README.md` 是细项索引与编码分配的操作入口，必须遵循：

- **编写阶段**：新增细项只取“下一可用编号”；必须插入到对应类型码表的数字升序位置，禁止为了省事追加到小节末尾。
- **审查阶段**：检查每个类型码小节内的全局编码索引是否按编码数字升序排列（如 `RUL-007`、`RUL-008`、`RUL-029`），并确认正文、文档清单、README 索引三方一致。
- **校验阶段**：校验**已正式化**编码序列完整性；发现缺口时应补齐索引记录或废弃记录，禁止直接分配缺口编号（`初稿` 期删除的编号不属缺口）。
- **计数器同步**：编码计数器只保留“下一可用编号”；新增后“下一可用编号”更新为新编号 + 1，批量新增时按批量最大值一次性更新。**缺口判定与编号回收仅依据 `正式` 基线**：`初稿` 期新增后又被删除的编码可直接回收复用、**不登记分配历史、不计缺口**；一旦该编码转为 `正式` 即纳入序列完整性约束。
- **变更倒序**：README 或文档内变更记录按版本号或日期倒序排列，最新记录置顶。

## IF类型详细说明

### 概念范围
IF（Interface）用于定义**系统边界上的契约**，不仅包含 HTTP API，还包括其他可被调用、可被集成、可被校验的交互边界。

### 常见用途（按实践频次）
1. **HTTP/RPC API 契约**（最常见）：路径、方法、入参/出参、错误语义、幂等性等。
2. **事件/消息契约**：Topic、事件字段、版本兼容、投递与重试语义。
3. **回调/Webhook 契约**：回调触发条件、签名校验、重试策略。
4. **批处理/文件交换契约**：文件格式、字段约束、时序、交付窗口。
5. **内部模块服务边界**：BFF 与领域服务、领域服务之间的调用契约。

### IF 与 API 的关系建议
- **结论**：**不建议**单独新增 `API` 类型码。
- **原因**：
  1. API 本质是 IF 的子集，新增 `API` 易造成语义重叠与分配分叉（同一接口到底用 IF 还是 API）。
  2. 现有 IF 已覆盖“接口契约”主语义，便于统一检索、追溯与治理。
  3. 可通过“接口风格标签”表达差异，不必增加类型码复杂度。

### 推荐做法（不新增类型码）
- 统一使用 `IF-xxx` 编码。
- 在 IF 正文增加标签：`接口风格：HTTP API / RPC / Event / Webhook / FileExchange / InternalService`。
- 对“对外 HTTP API”可在标题中显式标注，如：`IF-012 用户查询 API（HTTP）`。

### IF 与 ACT 的边界判定（防重叠）

**判定核心**：
- 若关注“交互边界的约束与兼容性”（输入输出、版本、错误码、幂等、时序/重试约定）→ **IF**
- 若关注“系统执行了什么业务动作”（命令触发、状态推进、业务语义）→ **ACT**

**可并存场景（推荐双编码）**：
- 同一业务交互同时需要“动作语义 + 接口契约”时，允许 `ACT-xxx` 与 `IF-xxx` 并存
- 约束要求：ACT 必须引用对应 IF；IF 也应关联触发该契约的 ACT（至少单向可追溯）

**快速判定问题**（二选一优先）：
1. 这条定义是否主要用于“调用方/集成方对接”？
   - 是 → IF
2. 这条定义是否主要用于“业务状态/流程推进”？
   - 是 → ACT

若两者都明显成立，应拆分为 IF + ACT，避免单条细项承载双重语义。

## ACT类型详细说明

### 概念范围
ACT类型用于定义系统执行的具体动作和行为，涵盖以下交互类型：

**消息类型（Message）**：
- Actor间的消息传递
- 系统组件间的通信消息
- 异步消息定义

**事件类型（Event）**：
- 领域事件（Domain Event）
- 系统事件（System Event）
- 集成事件（Integration Event）

**命令类型（Command）**：
- 用户命令（User Command）
- 系统命令（System Command）
- 管理命令（Admin Command）

**菜单类型（Menu）**：
- 用户界面菜单动作
- 功能菜单定义
- 操作菜单行为

**其他交互类型**：
- 查询动作（Query Action）
- 通知动作（Notification Action）
- 调用动作（Invocation Action）

### 命名规范
```
ACT-{编号}: {动作类型} - {具体动作描述}
```

**示例**：
- `ACT-001: UserRegistrationCommand - 用户注册命令`
- `ACT-002: OrderCreatedEvent - 订单创建事件`
- `ACT-003: SendEmailMessage - 发送邮件消息`
- `ACT-004: MainMenuAction - 主菜单动作`
- `ACT-005: UserQueryAction - 用户查询动作`

### 与其他类型的关系
- **ACT vs IF**：ACT定义业务动作语义，IF定义交互契约语义（可双编码但不得语义混写）
- **ACT vs FLW**：ACT是单个动作，FLW是完整流程
- **ACT vs ALG**：ACT是业务动作，ALG是计算逻辑

## PLN类型详细说明

### 概念范围

PLN 用于登记**当前不实现、留待将来考虑或细化**的功能与需求想法，是产品规划迭代的想法追踪载体。

> **边界**：本技能面向产品设计文档，不跟踪项目执行过程。PLN 因此**不是工作包或任务**：不记录工时、工作量、负责团队、排期与完成进度，也不承载跨团队协作安排；这类信息属于研发任务管理范畴，不进入 `ued/` 文档体系。

**层级适配**（按想法将来可能落到的文档层级）：
- **L2-PLN**：将来的功能或非功能需求 → 落实为 FR/NFR
- **L3-PLN**：将来的架构能力或组件演进 → 落实为 PRN/DEC/CMP
- **L4-PLN**：将来的接口或交互契约 → 落实为 IF/ACT
- **L5-PLN**：将来的算法或规则演进 → 落实为 ALG/RUL/ACT

### 适用与不适用边界

**适用场景（建议使用 PLN）**：
- 已识别价值但本轮不做，需要在设计文档中留下痕迹的功能或需求想法。
- 想法尚不稳定到单一 FR/NFR/IF/ALG，但方向与用户价值明确。
- 需要说明「为何当前不做」以及「什么条件下值得重新考虑」的事项。

**不适用场景（不建议使用 PLN）**：
- 本轮就要定义的稳定需求或设计内容（直接用 FR/NFR/IF/ALG 等类型码）。
- 执行层面的工程事项（排期、分工、工时、进度），应留在研发任务系统。
- 产品演进的时间与主题安排（属于产品路线图正文，不逐项编码）。
- 外部资料登记（使用 REF）。

### 与其他类型的判别规则
- **PLN vs FR/NFR**：PLN 是「将来再考虑的想法」，FR/NFR 是「已确认的需求定义」。
- **PLN vs PRN/DEC**：PLN 尚未形成决策，PRN/DEC 是已确认的原则/决策。
- **PLN vs REF**：PLN 是内部想法记录，REF 是外部依据对象。
- **PLN vs 产品路线图**：路线图表达产品规划的阶段与主题演进，PLN 表达单条待议想法；**二者互不关联**——路线图不引用 PLN，PLN 也不挂在路线图主题之下。

### 规划项生命周期（PLN 统一口径）

PLN 与其他细项**共用标准四态**（`初稿 / 正式 / 草案 / 废弃`，见 [status-definitions.md](status-definitions.md#状态即基线冻结规则mandatory)），**不设专属状态枚举**。想法在规划迭代中的处置由状态 + 记录型字段表达：

| 规划处置 | `细项状态` | 登记方式 |
|----------|-----------|----------|
| 想法已登记、尚未定论（含长期挂起） | `初稿` | 正文写清想法内容、当前不做的原因、重新考虑的条件；**MUST** 填 `建议复审日期`；轻重由 `优先级` 表达 |
| 已落实后需重新议定想法本身 | `草案` | `正式→草案` 解冻（递增版本号）→ 修订 → 定稿；重议期间 **MUST** 填 `建议复审日期` |
| **已展开为具体细项**（定稿与落实同步完成） | `正式` | `落实记录` **MUST** 非空且指向目标细项编码；目标细项 **MUST** 以 `规划来源` 回指本 PLN |
| 不再纳入产品演进 | `废弃` | 走废弃流程：`废弃原因` 记决策依据，`替代方案` 填目标细项或「无」 |
| 从未定稿即放弃 | 直接删除 | `初稿` 期删除条目、编号回收，同步清理引用与索引 |

> **落实同步（MUST）**：PLN 的定稿与落实是**同一个动作**——展开为目标细项的同时才把 PLN 定为 `正式`，**MUST NOT** 先定 `正式` 挂着、日后再落实。想法在被落实之前一直停在 `初稿`（“已识别价值、本轮不做”本身就是 `初稿` 的正常语义，不需额外状态），由 `建议复审日期` 驱动重新评估。因此 **MUST NOT** 存在 `正式` 而 `落实记录` 为空的 PLN。

### PLN 治理规则

1. **默认层级（MUST）**：未指定层级时，PLN 默认创建在 **L2**；仅当想法明确属于架构、接口或算法层面时才放入 L3-L5。
2. **准入（MUST）**：登记 PLN 须同时满足三项——本轮不实现、值得将来考虑、能写清「当前为何不做」与「何时值得重新考虑」。
3. **反替代约束（MUST NOT）**：已可稳定定义的内容不得停留在 PLN，须展开为对应正式类型码。
4. **禁记执行信息（MUST NOT）**：PLN 不得记录工时、工作量、负责团队、排期、完成进度等项目执行信息。
5. **不做交付时限跟踪（MUST NOT）**：PLN 不设「计划迁移日期」「完成期限」等**交付承诺类**时限字段；何时展开由产品规划迭代自行决定。（复审提醒不属此列，见第 8 条。）
6. **登记视图（SHOULD）**：PLN 的定义块位于其所属层级文档（默认 L2）；产品规划总览（模板见 [planning.md](../assets/templates/planning.md)）提供全局登记视图，只登记不重复定义。
7. **单一状态（MUST NOT）**：PLN 不得引入第二套状态枚举；规划处置一律用标准四态 + 记录型字段（`落实记录`、`废弃原因`、`建议复审日期`）表达。
8. **复审兜底（MUST）**：仍处 `初稿` / `草案`（即尚未定论）的 PLN **MUST** 填 `建议复审日期`，与「重新考虑的条件」互补——条件是被动的触发信号，日期是主动的时间兜底，防止想法在登记库里静默滞留。该字段属**记录型**（不参与冻结、改动不解冻不变号）；到期**只提示复核，不自动改变状态**，处置（展开 / 延后 / 废弃）由人决定；转 `正式` 或 `废弃` 时 **MUST** 置「无」或移除。
9. **落实回指（MUST）**：由 PLN 落实而来的细项 **MUST** 在其定义块中以 `规划来源` 属性行回指该 PLN（标准链接格式），使想法与其落地物**双向可追溯**。

### 命名规范
```
PLN-{编号} {想法标题}
```

**示例**：
- `PLN-001 会话消息撤回`
- `PLN-002 离线消息队列`
- `PLN-003 端到端加密`

### PLN 项结构
```markdown
### PLN-{编号} {想法标题}

**细项状态**：初稿 / 正式 / 草案 / 废弃
**优先级**：高 / 中 / 低（产品规划优先级，非执行排期）
**预期落点**：{将来可能落实为的类型码，如 FR / NFR / PRN}
**想法来源**：{利益相关者 / 用户反馈 / 评审遗留 等}
**登记日期**：{YYYY-MM-DD}
**建议复审日期**：{YYYY-MM-DD}

**想法说明**：
1. 想法内容：{这个能力解决什么问题、为谁带来什么价值}
2. 当前不做的原因：{为什么本轮不实现}
3. 重新考虑的条件：{出现什么信号时值得再次评估}

**落实记录**（与定稿同步写入；记录型字段，不解冻、不递增版本号）：
- {YYYY-MM-DD}：展开为 [{FR 编码}（{细项标题}）]({FR 定义所在文档相对路径})
```

> **`建议复审日期`**：仅 `初稿` / `草案` 填写（尚未定论的想法需要时间兜底）；转 `正式` 或 `废弃` 后置「无」或整行移除。属记录型字段，**MUST NOT** 因它而解冻或递增版本号。
> **目标细项的反向引用**：落实产生的细项在其定义块内加一行属性，写法与其他属性行一致：
> `- **规划来源**：[PLN-{编号}（{想法标题}）]({PLN 定义所在文档相对路径}#pln-{编号})`

### 与其他类型的关系
- **PLN vs FR/NFR**：PLN 是想法的暂存态，FR/NFR 是已确认定义；落实时建立**双向**指向关系——PLN 的 `落实记录` 指向目标细项，目标细项的 `规划来源` 回指 PLN。
- **PLN vs PRN/DEC**：PLN 是待议想法，PRN/DEC 是已确认的原则/决策。
- **PLN vs ACT**：PLN 属规划层面，ACT 是已定义的具体动作。
