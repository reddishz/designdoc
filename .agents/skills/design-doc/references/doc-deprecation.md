# 整份文档废弃操作规范

## 概述

本文档规范**整份设计文档**（如 `L2-001 系统需求`）的废弃操作流程。文档废弃是项目演进中的正常现象，需要规范的流程确保可追溯性与目录整洁。

**与「细项废弃」的区别**：
- **细项废弃**：文档内某个编码细项（如 `FR-001`、`RUL-005`）的作废，**原地保留**、不移动，参见 [item-deprecation.md](item-deprecation.md)。
- **文档废弃**：整份文档的作废，是本文规范的内容，带**建议归档日期**并可在到期后移入 `deprecated/` 目录。

**状态值约定（与 [status-definitions.md](status-definitions.md) 一致）**：
- **结构化状态值统一为 `废弃`**（枚举值，英文 Deprecated），用于 `状态 | 废弃`、索引状态列等可被机器校验的字段。
- 顶部提示与标题中的 `~~已废弃~~`、`⚠️ 本文档已废弃` **仅作视觉标记**，不是状态值。

**适用范围（状态即基线，MANDATORY）**：本文流程适用于**任意状态**的文档（`草案` 可直接废弃，**最后修订号即该草案号**）。
- 状态仍为 `初稿` 的文档**尚未发布、不构成基线**，但存在性同受锁定：**MUST NOT** 删除文件，不需要时走同一废弃流程（`初稿→废弃`），只在三处与 `正式` 有别——`废弃类别` 取 `初稿作废`、`废弃原因` 记一句话放弃依据、`修订版本号` 保持 `1`（从未解冻故从未递增）。文档编码一经分配即永久占用、**永不复用给其他对象**，索引条目与引用原地保留（房规见 [object-model.md · 锁定矩阵](object-model.md#锁定矩阵mandatory)）。
- 若只是要**修改**一份 `正式` 文档而非废止，应先按 [status-definitions.md](status-definitions.md#状态即基线冻结规则mandatory) 执行 `正式→草案` 解冻并将文档 `修订版本号` `+1`；只有**彻底废止**才走本文两阶段归档。
- 已废弃文档确需继续使用的，按 [status-definitions.md · 废弃后受控复活](status-definitions.md#废弃后受控复活受控mandatory) 判断可否原地复活；条件不满足时新建文档。

## 核心原则

**1. 只归档、不删除**：废弃文档**永不 `rm` 删除**；所谓"归档"仅指把文档移入本作用域的 `deprecated/` 目录继续留存，历史仍可追溯。
**2. 作用域隔离**：每个作用域拥有**各自独立**的 `deprecated/` 子目录，**不使用系统根共享目录**。单系统为 `ued/deprecated/`，多子系统结构为 `ued/{subsystem}/deprecated/`。
**3. 无 `active/` 目录**：活跃文档与"原地废弃"文档共同存放于作用域目录（`ued/` 或 `ued/{subsystem}/`），不存在也不需要 `active/`。
**4. 两阶段**：先**原地标注废弃**（不移动，仅加状态与字段）；到达建议归档日期后再**归档**入 `deprecated/`。
**5. 标注与追溯**：清晰标注废弃状态、类别、一句话原因、替代方案与影响范围，并同步处理引用。
**6. 整份废弃自底向上**：文档 `→废弃` 是收口，不是改封面。前置见 [整份废弃的前置](#整份废弃的前置mandatory)。

## 整份废弃的前置（MANDATORY）

整份 `废弃` 与定稿对称：**自底向上收口**。把元信息 `状态` 改成 `废弃`，**不是**「封面一翻、文内全部作废」。只在**文内已无仍生效内容**时才允许。

**细项（检查器 ERROR）**：文档内每个编码细项的 `细项状态` **MUST** 已为 `废弃`（清单与定义块一致）。缺 `细项状态` 视为未废弃。任一 `初稿` / `正式` / `草案`（或缺状态）→ **MUST NOT** 改文档 `状态`。

**非细项正文（须人审，本版检查器不 ERROR）**：**MUST NOT** 另造「正文状态」字段。概述、叙述、图示、无编码说明若仍当实现依据，**MUST** 先迁到后继文档；不再当依据则划掉或标明已退出。仍有一段正文当依据 → **先拆分，再废壳**。

**禁止为过门而级联**：用户说「把某文档整份废了」但活细项仍在时，AI **MUST NOT** 先把未确认的 `正式` 细项批量标 `废弃` 再改文档状态。**MUST** 停下，列出活细项与仍当依据的非细项正文标题，等人选路径：（a）只废部分细项、文档保持；（b）活内容迁到新文档后再废空壳；（c）用户**逐项**确认后再按 [item-deprecation.md](item-deprecation.md) 作废细项，最后才整份废弃。

**误标存量**：已把仍含未废弃细项的文档标成 `废弃`（如整份废了仍有大量 `正式` 细项的 L5）时，修正 **MUST** 是**恢复文档状态**，**MUST NOT** 把活细项杀掉来迁就错误封面。

无编码细项的 ADR / REF：细项门过空集；非细项正文仍须人审。文档可保持 `正式` 而全部细项已 `废弃`（空壳基线；定稿门控仍满足）。

## 判断标准

**建议废弃整份文档的场景**：

| 场景类型 | 说明 | 示例 |
|---------|------|------|
| 项目终止 | 项目被取消或暂停，相关文档不再维护 | 项目终止，废弃所有相关文档 |
| 版本替换 | 文档内容被新版本完全替代 | V1.0 需求文档被 V2.0 替代 |
| 架构重构 | 整体架构调整，原设计文档失效 | 单体迁移到微服务，原 L3 架构文档失效 |
| 业务调整 | 业务方向重大调整，原设计文档不再适用 | B2C 转 B2B，原用户画像文档失效 |
| 合并重组 | 多个文档合并为一个新文档 | 两个子系统需求文档合并为统一文档 |

**不应废弃整份文档的场景**（改用细项流程或状态调整）：
- 仅修改部分内容 → 走 [item-deprecation.md](item-deprecation.md) 细项废弃。
- 仅少量细项失效 → 废弃对应细项，保留文档。
- **仍有未废弃细项，或仍有作为实现依据的非细项正文** → **MUST NOT** 整份废弃；先作废细项、迁出或划掉仍生效正文，或拆文档。见 [整份废弃的前置](#整份废弃的前置mandatory)。
- 临时性调整 → 按 `正式→草案` 解冻修订，改完再 `草案→正式` 定稿；未采用的改法在草案期内改正文后再定稿，或走本文废弃。修订号 **MUST NOT** 改回解冻前。

## 目录布局

废弃文档始终归属于**它所在作用域**的 `deprecated/` 子目录，并保持原有相对结构。文件名 **MUST** 遵守 [命名规则](layer-system.md#命名规则)（`L{N}-{序号}-{英文描述}.md`，**不含中文**；序号默认三位补零、超过 999 自然四位），移入 `deprecated/` 时**保持原文件名不变**。

**单系统**：

```
ued/
├── README.md                    # 全局索引 / 编码计数器
├── L2-001-user-mgmt-req.md           # 活跃或"原地废弃"文档同在此处
├── L3-001-arch-design.md
└── deprecated/                  # 本作用域到期归档的文档
    ├── README.md                # 归档索引
    └── L2-001-user-mgmt-req.md       # 保持原文件名，镜像原相对结构
```

**多子系统结构**（每个子系统各自独立，系统根不设共享 `deprecated/`）：

```
ued/
├── README.md                    # 系统根：子系统注册表、系统发布（system-design-doc）
├── crm/
│   ├── README.md                # 子系统：元信息、索引、计数器
│   ├── L2-001-user-req.md
│   └── deprecated/              # 属于 crm 的废弃文档
│       ├── README.md
│       └── L2-001-user-req.md
└── oms/
    ├── README.md
    └── deprecated/              # 属于 oms 的废弃文档，独立于 crm
        └── README.md
```

## 废弃字段（整份文档专用）

在细项废弃登记字段的基础上，文档废弃**额外**包含「影响范围」「建议归档日期」等字段。统一字段集如下（`废弃类别` 与细项共用同一封闭枚举，见 [item-deprecation.md · 废弃类别](item-deprecation.md#废弃类别封闭枚举mandatory)）：

| 字段 | 必填 | 说明 | 示例 |
|------|------|------|------|
| 文档编码 | ✅ | 待废弃文档完整编码 | `L2-001`（配置 project_code 时如 `CRM-L2-001`） |
| 文档标题 | ✅ | 文档完整标题 | 用户管理系统需求 |
| 状态 | ✅ | 结构化状态值，固定为 `废弃` | 废弃 |
| 废弃时间 | ✅ | 最近一次废弃操作日期 | 2024-03-23 |
| 废弃类别 | ✅ | 封闭枚举，逐字取 [废弃类别](item-deprecation.md#废弃类别封闭枚举mandatory) 中一项 | 业务重构 |
| 废弃原因 | ✅ | 一句话说明，**MUST 非空**（可简略） | 系统重构，需求完全变更 |
| 替代方案 | ✅ | 替代文档链接 / 编码；无则填「无」 | `[L2-005 新用户管理系统需求](./L2-005-new-user-mgmt-req.md)` |
| 影响范围 | ✅ | 受影响的其他文档列表 | `L3-001, L4-002` |
| 建议归档日期 | ✅ | 到期后可移入 `deprecated/` | 2024-09-23 |
| 复活时间 | ⚠️ | **仅复活过的文档才有**；最近一次 `废弃→草案` 日期 | 2024-06-01 |

## 操作流程

### 阶段一：原地标注废弃（不移动）

**第一步：评估必要性**
- [ ] 确认需整体废弃，而非仅改部分内容（后者走细项废弃）
- [ ] **细项扫描**：本文全部编码细项 `细项状态` 均为 `废弃`（清单与定义块一致；缺状态视为未废弃）。任一未废弃 → **MUST NOT** 改文档状态，列出缺口
- [ ] **非细项正文**：列出概述 / 图示 / 无编码说明的标题；仍当依据者属[须人审](coding-system.md#须人审不能靠号)，未迁出或划掉前 **MUST NOT** 改文档状态
- [ ] 上两项未清零而用户要求整份废弃 → **MUST NOT** 批量改细项状态来过门；给出三条路径等人选（见 [整份废弃的前置](#整份废弃的前置mandatory)）
- [ ] 确认是否有替代文档及其编码
- [ ] 确认废弃类别（封闭枚举）、一句话废弃原因与影响范围

**第二步：引用排查（MANDATORY，标注前必须执行）**

在**本作用域目录**内搜索引用（不存在 `active/`，活跃文档就在作用域目录）：

```bash
# 单系统；多子系统结构则把 ued/ 换成 ued/{subsystem}/
grep -rn "L2-001" ued/ | grep -v "ued/deprecated/"
grep -rn "用户管理系统需求" ued/ | grep -v "ued/deprecated/"
```

排查项：文档编码全量/简写引用、文档标题引用、相对路径引用、全局索引引用、各文档文末「本文引用」表中钉住本文档或其细项的行。记录引用位置与影响范围。引用方是否仍成立属[须人审](coding-system.md#须人审不能靠号)，**MUST** 列出并等人确认后再改指。

**第三步：添加废弃元信息块**（置于文档开头）

```markdown
> ⚠️ **本文档已废弃**
>
> - 文档编码：L2-001
> - 文档标题：用户管理系统需求
> - 状态：废弃
> - 废弃时间：2024-03-23
> - 废弃类别：业务重构
> - 废弃原因：系统重构，需求完全变更
> - 替代方案：[L2-005 新用户管理系统需求](./L2-005-new-user-mgmt-req.md)
> - 影响范围：L3-001, L4-002
> - 建议归档日期：2024-09-23
>
> 本文档暂留原处仅供历史追溯，不再作为依据；到期后将归档至 `deprecated/`。请参考替代方案。
```

**第四步：更新文档元信息表**

```markdown
| 属性 | 值 |
|------|-----|
| 文档编码 | L2-001 |
| 层级 | L2 - 系统/产品需求 |
| 修订版本号 | 1 |
| 状态 | 废弃 |
| 废弃时间 | 2024-03-23 |
| 废弃类别 | 业务重构 |
| 废弃原因 | 系统重构，需求完全变更 |
| 替代方案 | L2-005 |
| 影响范围 | L3-001, L4-002 |
| 建议归档日期 | 2024-09-23 |
```

- **同步记录**：`变更记录` 追加一条**作废语义行**（首列沿用当前 `修订版本号`，说明如 `作废（草案→废弃）`，可并入必要说明），`最后更新` 改为废弃当天；**MUST NOT** 递增修订号。作废是状态转换，不并入上一条语义行（见 [status-definitions.md · 变更记录](status-definitions.md#变更记录mandatory)）。
- 细项作废不走这一步：细项没有独立变更记录，其时间线由 `废弃时间` 等字段承载。

**第五步：更新引用文档**
- 有替代方案：将引用改指替代文档（并更新对方「本文引用」钉住行）；或保留原引用并加删除线标注。
- 无替代方案：保留引用并标注 `（已废弃，无替代）`。
- 此阶段文档**仍在原处**，相对路径不变。改指后的兼容性仍须人审，不得默默升钉。

**第六步：更新作用域全局索引**

在本作用域 `README.md` 中新增/更新「废弃文档」小节：

```markdown
## 废弃文档

| 文档编码 | 文档标题 | 废弃日期 | 废弃类别 | 替代方案 | 建议归档日期 | 位置 |
|---------|---------|---------|---------|---------|-------------|------|
| L2-001 | 用户管理系统需求 | 2024-03-23 | 业务重构 | L2-005 | 2024-09-23 | 原地 |
```

### 阶段二：到期归档

**第七步：判断是否到期**

当"今天 ≥ 建议归档日期"，且确认无活跃文档仍以该废弃文档为有效依据时，执行归档。

```bash
# 基于文档头部"建议归档日期"字段判断（勿依赖文件修改时间）
grep -rl "建议归档日期" ued/deprecated 2>/dev/null
```

**第八步：移入本作用域的 `deprecated/`（保持相对结构）**

归档 = 移动文件，**不删除、不改名**。

```bash
# 单系统
mkdir -p ued/deprecated
mv ued/L2-001-user-mgmt-req.md ued/deprecated/

# 多子系统结构（移入该子系统自己的 deprecated，不动其他子系统）
mkdir -p ued/crm/deprecated
mv ued/crm/L2-001-user-mgmt-req.md ued/crm/deprecated/
```

若原作用域内文档有进一步子目录结构，`deprecated/` 内**镜像同样的相对路径**。

**第九步：更新所有引用路径**

文档移入 `deprecated/` 后，相对路径需修正：

```markdown
# 归档前（同作用域根目录）
参见 [L2-001 用户管理系统需求](./L2-001-user-mgmt-req.md)

# 归档后（进入 deprecated/）
参见 ~~[L2-001 用户管理系统需求](./deprecated/L2-001-user-mgmt-req.md)~~（已废弃）
```

**第十步：更新索引**
- 作用域 `README.md`「废弃文档」小节中该行的"位置"由 `原地` 改为 `deprecated/`。
- 在本作用域 `deprecated/README.md` 归档索引中登记该文档。

## 建议归档日期计算规则

| 文档类型 | 保留期限 | 计算方式 | 示例 |
|---------|---------|---------|------|
| 临时文档 | 3 个月 | 废弃时间 + 3 个月 | 2024-03-23 → 2024-06-23 |
| 项目文档 | 6 个月 | 废弃时间 + 6 个月 | 2024-03-23 → 2024-09-23 |
| 架构文档 | 1 年 | 废弃时间 + 1 年 | 2024-03-23 → 2025-03-23 |
| 核心文档 | 2 年 | 废弃时间 + 2 年 | 2024-03-23 → 2026-03-23 |

**文档类型判断参考**：

| 文档类型 | 典型文档 | 特征 |
|---------|---------|------|
| 临时文档 | TEMP-*、试验性设计 | 临时、试验、短期 |
| 项目文档 | L2 需求、L4 设计 | 具体项目的需求/设计 |
| 架构文档 | L3 架构、ADR | 系统架构、架构决策 |
| 核心文档 | L0 战略、L1 利益相关者 | 战略级、影响面大 |

未明确类型时，默认 6 个月。

## 废弃后复活（受控）

整份废弃的文档默认不复用；确需继续使用同一文档时，**MUST** 先按 [status-definitions.md · 废弃后受控复活](status-definitions.md#废弃后受控复活受控mandatory) 逐条校验（需求基本不变、原废弃原因消除、无生效替代、未归档或可确认误归档）。全部满足才可原地复活：

1. **请求确认**：列出原废弃登记、复活理由、影响范围与引用方。
2. **移回原位**：已归档的文档从 `deprecated/` 移回本作用域原路径（保持原文件名），并更新 `deprecated/README.md` 归档索引。
3. **改状态**：文档 `状态` 改回 `草案`，`修订版本号` **+1**，`最后更新` = 当天，写 `复活时间` = 当天；**MUST NOT** 直接改回 `正式`。
4. **细项按需复活**：只把确需继续使用的细项各自 `废弃→草案`（各自 `+1`、写 `复活时间`）；其余细项保持 `废弃`。文档升 `草案` 后仍受 [层级门控](status-definitions.md#层级门控文档状态--细项状态mandatory) 约束。
5. **保留历史**：`废弃时间` / `废弃类别` / `废弃原因` / `替代方案` 原样保留；删除顶部「⚠️ 本文档已废弃」横幅与标题删除线；清空对象上 `退出版本` 缓存（下一次立新基线时按成员归属回写）；移除或刷新 `建议归档日期`。
6. **同步索引与引用**：把作用域 `README.md`「废弃文档」行改为在用（或删除该行），按确认后的兼容性更新 [本文引用](coding-system.md#本文引用跨文档钉住mandatory) 与相对路径。

- **MUST NOT**：复活仍有生效替代的文档；复活后跳过 `草案` 直接 `正式`；清除废弃历史；在未确认引用方兼容性时改指钉住。
- **与新建的取舍**：需求基本不变 → 复活原文档；内容已实质变化或已有生效替代 → 新建文档并分配新编码。两者都不删除原文件。

## 最佳实践

**1. 只归档不删除**：
- ❌ `rm` 删除废弃文档
- ✅ 到期后移入本作用域 `deprecated/`，永久留痕

**2. 作用域独立**：
- ❌ 多个子系统共用系统根 `ued/deprecated/`
- ✅ 每个子系统各自维护 `ued/{subsystem}/deprecated/`

**3. 移动（归档）前先排查引用**（MANDATORY）：
- ✅ 在作用域目录内排查全部引用，记录后再处理

**4. 分阶段执行**：
- ✅ 先原地标注废弃并给出建议归档日期；到期后再归档，避免过早打断追溯

**5. 基于字段而非文件时间判断到期**：
- ✅ 按文档头部"建议归档日期"判定
