# 分配新编码与含义变更

> 分配新 ID，或处理「改编码 ID/类型码/正式标题/正式含义」请求时加载。

**MUST 另读**：[`object-model.md` · 锁定矩阵](../object-model.md#锁定矩阵mandatory)、[`coding-system.md` · 编码分配管理](../coding-system.md#编码分配管理)。

## 分配新编码

1. 读当前作用域 `README.md` 对应类型码的「下一可用编号」。
2. 一律用该号；发现缺口先修索引或补废弃记录，**MUST NOT** 直接占用缺口号。
3. Grep 确认目标编码在 `ued/` 未使用。
4. **Checkpoint 2**：批量、核心规则变更、或增量须动上层时，暂停确认。
5. 索引表按编码数字升序插入，**MUST NOT** 追加到末尾。
6. 更新文档清单 + 全局索引 + 计数器；「下一可用」= 新编号 + 1。
7. 验证正文、清单、README 三方一致，升序、无缺口、变更记录倒序。
8. **Checkpoint 3**：大规模变更或废弃前二次确认。

### 并发与撞号（MANDATORY）

默认**单写者**：同一作用域同一时刻只允许一个 Agent / 任务改写计数器与索引。多人或多 Agent 并行时按乐观并发执行：

1. **取号前重读**：以磁盘上 `README.md` 的当前计数器与索引为准，MUST NOT 依赖本轮早先读到的值。
2. **取号即回写**：拿到编号后，在同一轮内立即写回计数器、文档清单与全局索引；MUST NOT 先写正文、稍后再补计数器。
3. **写前复核**：写入前再次确认目标编码未被占用、计数器未被他人推进；任一变化 → 放弃本轮取值，重读后取新的「下一可用」。
4. **冲突不回收**：已被他人写入的编号归对方所有，MUST NOT 覆盖、改写或复用；无法判定归属时停下报告，不自行裁决。
5. 检查器只校验最终状态，不感知并发；冲突处理完后 MUST 重跑 `check_docs.py`。

## 处理编码含义变更请求

触发：（a）改已分配编码的 ID 或类型码（**不区分状态**）；（b）改已 `正式`/`草案` 标题的**语义**；（c）改已 `正式` 的业务含义。`初稿` 改标题（须同步引用）与 `初稿`/`草案` 改正文不属此列；**不改含义**的维护走 [maintenance-change.md](maintenance-change.md)，不是违规。

AI **MUST** 按下列框响应（可复述，不必另套话术）：

```
❌ 违规：禁止就地改编码 ID/类型码；禁止就地改正式/草案标题的语义；禁止就地改已正式化业务含义
✅ 正确流程：
1. 初稿：改标题 → --refs 同步引用；类型码错 → 初稿作废再以正确类型码新建（原号永不复用）
2. 正式/草案：语义变化 → 废弃原编码 + 新含义用下一可用编码
3. 任意状态：只改措辞且语义不变 → 维护性变更（maintenance-change.md；人审 + 单独成批 + 全文扫描；`正式`/`废弃` 写维护行，`初稿`/`草案` 直接改）
4. --refs 做影响评估
```

仅修订 `正式` **正文**且不改含义与标题：`正式→草案` 解冻（修订号 +1）→ 修订 → 定稿。解冻前 **MUST** `--refs`，列出[须人审](../coding-system.md#须人审不能靠号)项；**MUST NOT** 在用户确认兼容前升钉。见 [本文引用](../coding-system.md#本文引用跨文档钉住mandatory)。
