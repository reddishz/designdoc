# 据文档实现（消费侧，MANDATORY）

> 依据已定设计实现或完善代码时加载（含 [before-code-change.md](before-code-change.md) 判定为 A「允许实现」，或判定 B / C 的设计已定稿并入基线之后）。

**MUST 另读**：[`product-version.md`](../product-version.md)；状态判定见 [`status-definitions.md`](../status-definitions.md)。

1. **未入当前产品基线 MUST NOT 作为实现依据**：取 README `产品版本` → `baselines/{该版本}.yaml`；目标编码 **MUST** 在其 `items` 中。**MUST NOT** 依据未列出细项，或整篇为 `初稿`/`草案`/`废弃` 的文档实现。
2. **先判状态与基线、后拒绝**：
   - `初稿`/`草案`/`废弃`（或缺字段推定未冻结）→ **MUST 拒绝**；`草案` 豁免须用户逐项明确并留痕，且定稿后复核、升基线后方可作基线依据。
   - `正式` 但不在 `items` → **MUST 拒绝**：首份基线提示 **PATCH** 同步当前工作集（PATCH 是同步动作，不是成员变更审批）；已有前驱的基线提示 **MINOR**（成员集合不能原地改）。
   - `正式` 在 `items` 但 revision 落后 → **MUST 拒绝**按新语义实现，提示 **PATCH**。
   - 无基线或无 `产品版本` → **MUST 拒绝**，提示先建基线。
3. **运行版本展示（SHOULD）**：可见版本与当前 `full_version`（`vX.Y.Z`）一致；设计文档 **MUST NOT** 登记构建号/包路径。
4. 审查/Checkpoint 5 提示须含「未入当前产品基线不得作为实现依据」；漂移按基线层级询问：首份基线走 PATCH，非首份仅 revision 落后走 PATCH、成员进出走 MINOR。

## 实现中：范围漂移即停

5. 实现过程中，一旦要做的事超出所依据细项的条文，**MUST 立即停止并回到** [Gate](before-code-change.md)（判定 B 或 C），**MUST NOT** 默默补全、顺手实现或「先这样、以后再补文档」。超出的情形包括：新增或改变产品可观察行为、数据结构、接口、约束、取值范围、错误处理口径，或发现条文本身有误。

## 实现后：逐条对照

6. 完成后、报告完成前，**MUST** 逐条回读所依据的设计条文，并在回复中给出对照表：

   | 编码 | 条文要点 | 实现是否一致 |
   |------|----------|--------------|
   | {细项编码} | {条文原意，含格式、取值、边界} | 一致 / 偏差：{说明} / 未实现 |

   - 出现「偏差」或「未实现」：**先改代码使其一致，或回到 Gate 改设计**；**MUST NOT** 保留静默分叉。
   - 「测试通过」「日志正常」**不是**完成标准；完成标准是条文逐条一致。
   - 同时检查：没有引入设计之外的行为；本轮是否需要同步改文档。
7. 本轮改过 `ued/` 时运行 `check_docs.py`。**检查器是核对工具，不是通关条件**：报错 **MUST** 先查清是哪条规则、为何触发，再按规则改；**MUST NOT** 为让它不报而改措辞、补一句说明或手填字段。通过只说明机械一致，不证明语义一致。
8. 收尾回复（及提交说明）**SHOULD** 写明本轮所依据的编码，便于追溯。**MUST NOT** 把代码路径、构建号写进设计文档。
