# 维护性变更（非语义维护）

> 触发：统一用语、修正措辞与错别字、修正引用路径或链接文本、调整不改变含义的结构顺序、对名称 / 标题做非语义调整等；对象可能处于任意四态。
>
> **MUST 另读**：[`status-definitions.md` · 维护性变更](../status-definitions.md#维护性变更第三维度mandatory)、[`object-model.md` · 锁定矩阵](../object-model.md#锁定矩阵mandatory)、[`coding-system.md` · 本文引用](../coding-system.md#本文引用跨文档钉住mandatory)。

本流程只处理**语义不变**的维护。它不改状态、不改修订号、不碰基线与钉住，只留下可追溯的维护记录。

## 第一步：判定性质（MUST）

按 [语义不变判据](../status-definitions.md#语义不变判据mandatory) 逐项核对：适用范围、行为、输入与输出、约束、验收口径、数值、模态词、量词、接口、依赖、术语定义、类型码、基线成员身份。

| 结论 | 走哪条路 |
|------|----------|
| 全部不变 | 本流程 |
| 任一项变化 | **不是**维护性变更：`初稿` / `草案` 直接改；`正式` 先解冻（`修订版本号` +1）；含义根本变化 → 废弃 + 新增编码 |
| 拿不准 | 按语义变更处理，**MUST NOT** 用维护性变更降低审批强度 |

**不是维护性变更的典型**：把「应当」改成「可以」、把「≤ 200ms」改成「≤ 300ms」、增删限定条件、改变术语定义、把标题改成另一个业务对象。

`初稿` / `草案` 的普通维护可直接进行，不强制走本流程；跨文档批量维护 **SHOULD** 走本流程，以便用批次号追溯。

## 第二步：建立维护方案（Checkpoint M1，MUST）

先出方案，取得人确认后动手；AI **MUST NOT** 自行发起批量维护。

1. **定批次号**：`MNT-YYYY-MM-DD-NN`。扫描作用域内当日已有批次，`NN` 两位从 `01` 递增；同一次维护在全部受影响文档与术语表中共用同一批次号。
2. **列清单**：逐个对象写「文档编码 / 细项编码 / 维护内容（旧 → 新） / 维护类型」。维护类型取封闭枚举：
   - `命名维护`：标题、术语名、文件标题等专名变化；
   - `文字维护`：统一用语、修正措辞、错别字（不改变含义）；
   - `引用维护`：修正引用路径或链接文本；
   - `结构维护`：调整不改变含义的结构顺序。
3. **做影响面**：对每个编码跑 `--refs`；涉及名称 / 标题变化时另全文检索旧称。列出定义位、链接文本、文档清单、README 全局索引、术语表 / `所用术语`、正文使用处、归档文档。历史记录（旧 `变更记录`、正文沿革说明）**不列入**待改清单。
4. **写语义不变论证**：逐项说明为什么只是措辞变化，附新旧对照。
5. **停点**：向人确认批次号、清单、影响面与论证。**未确认不得开工**。

## 第三步：执行（同批原子完成）

1. **改定义位**：按维护类型改标题、措辞、路径或顺序；锚点行 `<a id="{编码全小写}"></a>` **MUST NOT** 变。废弃对象保留 `~~已废弃~~` 后缀。
2. **记录细节**：对象级旧值就地写进维护行的 `{说明}`（如 `旧称 → 新称`、`旧路径 → 新路径`）；需要更多上下文时写进正文段或术语表《补充信息》的普通说明文字。**MUST NOT** 新增属性行、定义块段位或术语表列。
3. **同步引用与索引**：全部链接文本、文档细项清单、README 全局索引、正文使用处一次改完；`本文引用` 只改行外链接文本，**MUST NOT** 改钉住代际与钉住日期。
4. **术语名称调整加做**：
   - 定义文档的术语块改用新名，旧名写进该文档维护行说明；
   - 全局术语表改术语行，旧名写进术语表语义行说明或《补充信息》的普通说明文字；
   - 各文档 `所用术语` 中的名称同步；
   - 术语表 `修订版本号` **+1** 并写普通语义行（名称调整对术语表是实质变更），与文档维护行共用同一批次号。
5. **不动的字段**：`细项状态` / `状态`、`修订版本号`、`创建日期`、`最后修订日期`、基线 `items`、`本文引用` 钉住列。

## 第四步：写维护记录（MUST）

在每个受影响对象的 `变更记录` 顶部、其当前修订号代际块内追加维护行（不新开表、不新开小节）：

```markdown
| 修订版本号 | 日期 | 作者 | 变更说明 |
|------------|------|------|----------|
| 13（维护） | 2026-10-28 | {作者} | MNT-2026-10-28-01 命名维护：设定子系统 → 训练策略子系统；语义不变 |
| 13 | 2026-09-01 | {作者} | 解冻修订（正式→草案） |
| 12 | 2026-08-20 | {作者} | 定稿 |
```

- 首列 `{当前修订号}（维护）`：全角括号、括号前不留空格、修订号不变。
- 说明格式 `MNT-日期-序号 {类型}：{说明}；语义不变`。
- 同一修订号下多条维护行按日期倒序，位于同号语义行之上。
- 只刷新文档 `最后更新`；README 只改标题单元格与 `last_updated`（README 无变更记录表）。

## 第五步：验证（Checkpoint M2，MUST）

1. **检查器**：`check_docs.py -p <ued>`；改过技能包或模板时另跑 `--check-templates`。
2. **旧称残留**：涉及名称 / 标题变化时全文检索旧称，命中只允许出现在 `变更记录` 维护行、术语表《补充信息》与历史归档文档；正文、标题、索引、链接、`所用术语` 中出现即缺陷。
3. **引用一致性**：逐个编码跑 `--refs`，确认定义位、链接文本、清单、索引四处同名。
4. **差异形态**：审 diff，只应出现标题 / 名称 / 措辞 / 路径文本、维护行与 `最后更新`；出现正文语义、状态、修订号、基线或钉住变化即停。
5. **基线**：确认 `baselines/` 无 diff；标题滞后是预期快照，**MUST NOT** 顺手 PATCH。
6. **停点**：向人报告批次号、命中文件、检查结果与差异摘要，确认后才可提交。

## 回滚与纠错

- 维护性变更不改代际，回滚只需把文字改回并**再追加一条**维护行说明纠正；历史维护行 **MUST NOT** 删除。
- 若发现本次实际改了语义：停止维护流程，按语义通道处理（`正式` 先解冻 +1）；**MUST NOT** 用「维护」记录掩盖语义变更，也 **MUST NOT** 把修订号改回。

## 禁止事项

- **MUST NOT** 与语义修改、状态转换、基线动作混在同一改动或同一提交中。
- **MUST NOT** 借维护之名改编码 ID / 类型码、拆分或合并对象、改变依赖关系。
- **MUST NOT** 为维护单独发版或改 `baselines/`；基线标题在下次 PATCH / MINOR 时自然刷新。
- **MUST NOT** 跳过人审或分批收尾；跨文档批次遗漏一处即缺陷。
