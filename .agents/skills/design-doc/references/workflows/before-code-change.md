# 编码前设计 Gate（消费侧，MANDATORY）

> 项目**声明采用 design-doc**（根 `AGENTS.md` 含托管块，见 [project-agents-guide.md](../project-agents-guide.md)）或已有 `ued/`，且用户意图是增加功能、改功能、修缺陷/bug、改产品可观察行为、按需求实现某能力，**或改动 `ued/` 内任何文档**时，**MUST** 先过本 Gate。  
> **本 Gate 早于第一次编辑**：Gate 记录是本轮第一个输出，**MUST** 写在任何编辑工具调用、任何修改文件的终端命令之前。**MUST NOT** 先改代码或文档、再补写 Gate 记录。

**MUST 另读**（按判定）：维护性变更 → [maintenance-change.md](maintenance-change.md)；改/补设计 → [change-feature.md](change-feature.md) / [allocate-and-lock.md](allocate-and-lock.md) / [lifecycle.md](lifecycle.md)；可实现 → [implement-from-design.md](implement-from-design.md)。术语口径见 [status-definitions.md · 实现依据口径](../status-definitions.md#实现依据口径术语对照)。

## 步骤

1. **定位**：在 `ued/` 与当前产品基线检索相关细项（关键词、编码、`--refs`、模块/接口名），列出候选编码。无候选 → 记为「无对应细项」。拟改 `ued/` 文档时，同样列出拟动文档。
2. **读事实，不凭记忆**：对每个候选编码打开文档与 `baselines/{产品版本}.yaml`，记下 `细项状态`、文档与细项 `修订版本号`、基线 `items` 中的 revision。拟改 `ued/` 文档时同样记下其 `状态`。
3. **判定**（五选一；涉及多个编码时取最严格者；拿不准一律取 B）：

   | 判定 | 条件 | 后续 | 暂停 |
   |------|------|------|------|
   | **M 维护性变更** | 仅限 `ued/` 文档。通过[语义不变判据](../status-definitions.md#语义不变判据mandatory)全部项：错别字、措辞、链接与路径、非语义结构调整、非语义命名 | 按 [maintenance-change.md](maintenance-change.md) 执行；不解冻、不改修订号、不改基线；冻结对象写维护行 | 否 |
   | **A 允许实现** | 设计正确，代码偏离；细项 `正式`、在当前基线 `items` 中、revision 对齐 | 进入 [implement-from-design.md](implement-from-design.md) | 否 |
   | **B 先改设计** | 设计与预期不符或已过时；或语义不变判据任一项变化；或拿不准 | **先**请求解冻确认（`正式` 须 `正式→草案`，修订号在解冻那一刻 +1），确认后才改文档；增量走 [change-feature.md](change-feature.md)；改完定稿并同步基线，**然后**才改代码 | **是** |
   | **C 先补设计** | 无对应细项 | **先**分配编码并起草设计，经定稿、入基线，**然后**才依据该设计实施代码；向已 `正式` 的文档新增细项须先解冻该文档 | **是** |
   | **D 暂停待人审** | 设计无需改但缺人决策：细项 `草案` / `初稿` 想豁免、正式细项未入基线或 revision 落后需 PATCH / MINOR、范围不清、判定不了 | 说明缺口与选项，等用户确认；**MUST NOT** 自行定稿、豁免或 `--bump-product` | **是** |

   - 「设计未入基线」不是独立判定：它是 A 的前置不满足，按 D 处理。
   - M 只适用于 `ued/` 文档。代码的纯笔误不走 M，见下文「免审声明」。
   - M 的判据是**语义是否改变**，不是改动大小。把「应当」改成「可以」、改数值、增删限定条件、改术语定义、改标题所指对象，都不是 M。

4. **输出 Gate 记录（MUST，本轮第一个输出）**：

   ```text
   编码前设计 Gate
   - 已读：{本轮已打开的 Gate 相关文件，如 SKILL.md、本文件、拟改文档、基线文件}
   - 设计依据：{编码列表；无则写「无对应细项」}
   - 产品版本 / 基线：{vX.Y / vX.Y.Z；无基线写「无基线」}
   - 设计状态：{各编码的 细项状态；拟改文档的 状态}
   - revision（文档 / 基线）：{各编码对照；无则「—」}
   - 拟改动 ued/ 文档：{路径与当前 状态；不改写「无」}
   - 判定：M | A | B | C | D
   - 后续动作：{下一步，含需用户确认的事项}
   ```

   记录 **MUST** 基于第 1–2 步的真实检查结果填写，**MUST NOT** 先写结论再补查。

5. **继续或暂停**：
   - **M、A**：记录输出后可直接继续，不必等待批准；完成后在最终回复里说明本轮判定。
   - **B、C、D**：记录输出后，**本回合到此结束**——不再调用编辑工具，也不用终端命令修改任何文件，等待用户在下一条消息中确认。用户确认后，按 [lifecycle.md](lifecycle.md) 的合并确认方式执行。

   B/C 的人审按下表合并，**避免把同一件事拆成多次追问**，但也不省略任何一次确认：

   | 阶段 | 确认内容 |
   |------|----------|
   | 动 `正式` 文档前 | 解冻（B；C 中向 `正式` 文档新增细项时）。一次性列出所有要解冻的对象，用户一次确认 |
   | 起草完成后 | **大纲与核心细项（Checkpoint 1 / 2）、定稿、基线动作合并为一次确认**：呈现起草内容、未冻结对象表与按升格后状态预判的 PATCH / MINOR，用户一次同意即连续执行；`MAJOR` 仍单独询问（见 [lifecycle.md](lifecycle.md) Checkpoint 5） |

   全新项目（尚无 `正式` 文档）只有第二阶段这一次确认。确认之前 **MUST NOT** 改代码或改文档。

## 免审声明

仅限：代码中的纯笔误、与规格无关的构建/环境失败。这类请求 MAY 跳过判定 A–D，但 **MUST** 在回复中写一行：「未触及设计对象；已检索：{关键词 / 文档范围}」。

- 「小改」「顺手改一下」「用户直接要求改代码」「我已经理解需求」**都不是**免审理由。
- 改动 `ued/` 内文档**不适用**免审：语义不变的文档改动走 M，其余走 B–D。

## 禁止

- **MUST NOT** 以「先改代码后面再补文档」「小改不用改设计」跳过本节。
- **MUST NOT** 在编辑之后补写 Gate 记录，或让记录与实际检查结果不符。
- **MUST NOT** 把 `初稿` / `草案` / 未入基线的内容当作已批准规格去改代码（豁免见 [implement-from-design.md](implement-from-design.md)）。
- **MUST NOT** 手填修订号、状态、`引入版本` / `退出版本` 等谱系字段：修订号与状态只随受控状态转换变化，谱系由立新基线回写（见 [status-definitions.md](../status-definitions.md)、[product-version.md](../product-version.md)）。
- **MUST NOT** 把 M 当作逃避 B–D 的通道：拿不准时取 B。
