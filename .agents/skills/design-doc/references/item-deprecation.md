# 细项废弃处理规范

## 概述

细项废弃指文档内某个编码细项（如 `FR-001`、`RUL-004`）的作废，是设计文档演进过程中的正常现象。本规范确保废弃过程的规范性和一致性。整份文档的废止不在本文范围，见 [doc-deprecation.md](doc-deprecation.md)。

> **适用范围（状态即基线，MANDATORY）**：本文废弃流程作用于**已进入 `正式` 基线的细项**与**处于 `草案` 的细项**（`草案` 可直接废弃，**最后版本号即该草案号**，不必先回退）。
> - `初稿` 期细项要作废时**直接删除即可**（同步清理全部引用与索引条目），无需本流程、不留删除线、不写废弃字段、不计缺口。
> - `草案` 期细项 **MUST NOT** 直接删除：或按 [status-definitions.md](status-definitions.md#变更流程与版本号统一mandatory) `回退` 到上一 `正式` 基线（版本号回到解冻前、变更记录完整保留），或走本文废弃。
> - 若目标是**修改**某个 `正式` 细项而非废止，按 [status-definitions.md](status-definitions.md#状态即基线冻结规则mandatory) 先 `正式→草案` 解冻并提升版本号，改完再 `草案→正式` 定稿；只有**彻底作废**才走本文废弃。

**状态值约定（与 [status-definitions.md](status-definitions.md) 一致）**：
- **结构化状态值统一为 `废弃`**（枚举值，英文 Deprecated），用于 `细项状态：废弃`、索引状态列等可被机器校验的字段。
- 标题删除线 `~~已废弃~~` **仅作人眼视觉标记**，不是状态值；二者不要混为一套枚举。

**与「文档状态」的关系（同一枚举、不同字段、各自取值）**：`初稿 / 正式 / 草案 / 废弃` 是文档与细项**共用**的标准枚举，但登记在不同字段：整份文档写在元信息表的 `状态`，编码细项写在 `细项状态`（文档内清单与全局索引的列名也为 `细项状态`）。两者**各自独立取值**：细项废弃时，承载它的文档仍可为 `正式`；若整份文档一并废止，则走 [doc-deprecation.md](doc-deprecation.md)。

**与编码体系的关系**：全文示例使用项目编码 **CRM**；当前作用域 `README.md`、跨文档引用、锚点须与 [coding-system.md](coding-system.md) **全量编码**一致（如 `CRM-RUL-004`、`#crm-rul-004`）。同文档内叙述可沿用简写，但索引与对外引用须写全。

## 核心原则

**1. 保留原则**：废弃的细项必须保留，不能删除  
**2. 标注原则**：通过状态字段和标题标注废弃状态  
**3. 追溯原则**：反向追溯所有引用，同步标注废弃  
**4. 传播原则**：若某细项被废弃，依赖它的内容可能失效；**优先**将引用**更新为替代细项**（替代方案），仅在引用方语义不再成立时，再将引用方细项**标注废弃**。避免无必要的级联废弃。

## 废弃流程

### 第一步：标记细项废弃

**在细项中添加废弃标记**：

```markdown
<a id="crm-rul-004"></a>
### CRM-RUL-004：账号格式规范 ~~已废弃~~

- **细项状态**：废弃
- **修订版本号**：1
- **最后修订日期**：2024-01-15
- **废弃时间**：2024-03-23
- **废弃原因**：需求变更，采用新的账号格式规范
- **替代方案**：[CRM-RUL-018（新账号格式规范）](#crm-rul-018)
- **规则内容**：账号长度 6-20 位，包含字母数字
```

> **形态依据**：上例严格遵循 [coding-system.md · 细项定义块形态](coding-system.md#细项定义块形态mandatory)——锚点行 + 标题行（全角冒号分隔）+ 具名属性行（列表项，非裸段落），且属性行组分三段：**治理段**（`细项状态` / `修订版本号` / `最后修订日期`）→ **废弃登记字段**（`废弃时间` / `废弃原因` / `替代方案`）→ **内容段**。废弃标注**不改变锚点值**：`<a id>` 与编码一一对应，MUST NOT 随标题后缀变化。
>
> **废止不递增修订号**：`修订版本号` 停在废止前的值（上例为 `1`）、`最后修订日期` 也不变，终态时间由 `废弃时间` 记录（口径见 [status-definitions.md · 细项修订版本号](status-definitions.md#细项修订版本号与文档版本号独立演化)）。

**标记方式**：
- **标题标记**：在细项标题后添加 `~~已废弃~~`
- **状态字段**：在定义块内以属性行 `- **细项状态**：废弃` 明确标注（勿与文档元信息中的 `状态` 混淆）
- **保留原内容**：保留原细项内容，不删除

**字段说明**：
- **细项状态**：必须标注为"废弃"（枚举值，`~~已废弃~~` 只是标题视觉标记）；它是治理段首行，也是清单表 `细项状态` 列的对应值，两处取值 MUST 一致
- **修订版本号** / **最后修订日期**：治理段第二、三行，废止时**保持不变**
- **废弃时间**：格式为 YYYY-MM-DD，追溯废弃时间
- **废弃原因**：说明废弃的具体原因
- **替代方案**：如有替代细项，**MUST** 用标准链接指向其定义位（`[{编码}（{标题}）](#{编码全小写})`）；如无替代方案，填写「无」——**MUST NOT** 只写裸编码，也 **MUST NOT** 写替代思路一类的散文（思路归 `废弃原因`）；取值口径单点见《废弃标记规范 · 标准标记格式》

### 第二步：反向追溯引用

**搜索所有引用**（须同时搜简写与全量编码，避免漏网）：

在 `ued/` 目录中同时检索 `CRM-RUL-004` 与 `RUL-004`。

**追溯范围**：
- 同文档内的引用
- 其他文档的引用
- 跨项目的引用
- 索引中的引用

### 第三步：评估并处理引用

对每个引用，按以下决策树处理：

```
1. 是否有替代方案？
   ├─ 有 → 更新引用为替代编码，标注原引用废弃
   └─ 无 → 进入 2

2. 引用方是否仍成立？
   ├─ 仍有其他有效引用 → 标注本条引用废弃，保留引用方
   ├─ 可更新为替代方案 → 更新为替代编码，标注原引用废弃
   └─ 完全依赖废弃细项 → 标注引用方废弃
```

**处理示例**：

**情况 1：有替代方案（推荐）**

```markdown
# 废弃前
根据 [CRM-RUL-004（账号格式规范）](#crm-rul-004) 的要求，系统需要...

# 废弃后
根据 ~~[CRM-RUL-004（账号格式规范）](#crm-rul-004)~~（已废弃）和 [CRM-RUL-018（新账号格式规范）](#crm-rul-018) 的要求，系统需要...
```

**情况 2：无替代方案，引用方仍成立**

```markdown
<a id="crm-fr-001"></a>
### CRM-FR-001：用户认证需求

- **细项状态**：草案
- **修订版本号**：2
- **最后修订日期**：2024-03-23
- **描述**：根据 ~~[CRM-RUL-004（账号格式规范）](#crm-rul-004)~~（已废弃）和 [CRM-RUL-005（密码安全规范）](#crm-rul-005) 的要求，系统需要...
```

> **标注引用属内容修订（MUST 走解冻通道）**：给已 `正式` 的引用方加删除线标注，改的是其正文属性，因此 MUST **先解冻所在文档、再解冻该细项**（`正式→草案`），`修订版本号` 随之 `+1`、`最后修订日期` 更新为当天；改完再定稿回 `正式`（定稿不再变号）。顺序与前置见 [status-definitions.md · 层级门控](status-definitions.md#层级门控文档状态--细项状态mandatory)。

**情况 3：无替代方案，引用方也废弃**

```markdown
<a id="crm-fr-002"></a>
### CRM-FR-002：登录功能 ~~已废弃~~

- **细项状态**：废弃
- **修订版本号**：1
- **最后修订日期**：2024-01-20
- **废弃时间**：2024-03-23
- **废弃原因**：依赖的 [CRM-RUL-004（账号格式规范）](#crm-rul-004) 已废弃，且无替代方案
- **替代方案**：无
```

**全局编码索引更新**（列结构与 [readme-template.md](../assets/templates/readme-template.md) 的全局编码索引一致；废弃时间、废弃原因与治理段的 `修订版本号` / `最后修订日期` 均只记在细项定义块与变更记录中，**不列入索引与清单表**）：

**文档细项清单更新**：

```markdown
| 编码 | 类型 | 标题 | 细项状态 |
```

## 废弃标记规范

### 标准标记格式

定义块的完整形态单点表述于《第一步：标记细项废弃》（实例）与 [coding-system.md · 细项定义块形态](coding-system.md#细项定义块形态mandatory)（房规），引用处的删除线写法单点表述于《第三步：评估并处理引用》，本节不复述，只定四个必备字段的取值口径：

| 字段 | 取值 | 说明 |
|------|------|------|
| `细项状态` | `废弃` | 标准四态之一；`~~已废弃~~` 只是标题视觉标记，机器识别读本字段 |
| `废弃时间` | `YYYY-MM-DD` | **记录型字段**：改动不解冻、不递增文档版本号，也不递增 `修订版本号`；AI 自动使用当前日期 |
| `废弃原因` | 自然语言 | 分类口径见《废弃原因分类》 |
| `替代方案` | 标准链接 / 「无」 | 有替代细项时 MUST 用链接指向其定义位（带 `#{编码全小写}` 锚点）；无替代时填「无」 |

> 四个字段 MUST 写在定义块的属性行组内（`- **{字段名}**：{值}`），MUST NOT 写成裸段落；**位置**上 `细项状态` 居治理段首行，其余三个废弃登记字段紧随治理段（`修订版本号` / `最后修订日期`）之后、内容段之前（段位见 [coding-system.md · 细项定义块形态](coding-system.md#细项定义块形态mandatory)）。锚点行 MUST 保留且锚值不变（引用方仍需跳得到）。

### 废弃原因分类

| 废弃原因 | 说明 | 示例 |
|----------|------|------|
| 需求变更 | 业务需求发生变化 | 业务模式调整，原有需求不再适用 |
| 设计优化 | 设计方案被更好的方案替代 | 采用新的架构设计，原设计被淘汰 |
| 技术升级 | 技术栈升级导致规则变更 | 升级到新版本，技术规范发生变化 |
| 业务重构 | 业务流程重新设计 | 组织架构调整，业务流程重组 |
| 约束解除 | 原有约束条件不再存在 | 监管政策变化，合规要求解除 |
| 依赖废弃 | 依赖的细项已废弃 | 依赖的规则或需求已废弃，导致本细项无效 |
| 重复冗余 | 与其他细项重复或冗余 | 发现功能重复，合并处理 |

## 特殊情况处理

### 批量废弃

**场景**：业务重构导致大量细项废弃

**推荐方案：按依赖层级分批废弃**

**批次划分**：
1. **底层细项**：RUL、PRN、CON 等基础规则和约束
2. **中层细项**：FR、NFR、IF 等功能和接口
3. **上层细项**：GOL、SCN、STK 等目标和场景

**处理流程**（每批）：

1. **批量标记废弃**：为该批所有细项添加4个必须字段
2. **批量追溯引用**：搜索该批细项的所有引用（含简写和全量编码）
3. **批量评估引用方**：按决策树判断每个引用方是否需要废弃
4. **批量更新索引**：该批处理完成后，立即更新全局索引和文档清单

**关键注意事项**：
- 按从下到上的顺序处理，避免引用方在引用源还未处理时就被评估
- 每批处理完成后，立即更新索引，不要等到所有批次都处理完
- 保持详细的废弃记录，便于追溯

### 循环依赖废弃

**场景**：A 依赖 B，B 依赖 A，其中之一需要废弃

**处理流程**：
1. **同时废弃**：将循环依赖的细项同时标记废弃
2. **说明原因**：在废弃原因中说明循环依赖问题
3. **统一处理**：同时处理所有相关引用

### 紧急废弃

**场景**：发现重大问题需要立即废弃

**处理流程**：
1. **立即标记**：先标记废弃，后续完善信息
2. **快速追溯**：快速处理主要引用
3. **后续完善**：补充完整的废弃信息

### 推荐工具与命令

**1. 搜索引用**

```bash
# 搜索完整编码
grep -r "CRM-RUL-004" ued/

# 搜索简写编码
grep -r "RUL-004" ued/

# 组合搜索（排除已处理的废弃引用）
(grep -r "CRM-RUL-004" ued/; grep -r "RUL-004" ued/) | grep -v "已废弃"
```

**2. 区分已处理引用**

```bash
# 已处理引用：包含 ~~已废弃~~ 或已改为替代编码
grep -r "CRM-RUL-004" ued/ | grep "已废弃\|已替代"

# 未处理引用：包含原编码，但不包含废弃标记
grep -r "CRM-RUL-004" ued/ | grep -v "已废弃\|已替代"
```

**3. 批量处理脚本思路**

```bash
# 伪代码示例，根据实际需求实现
for item in $(cat deprecation-list.txt); do
```

## 审核要点

### 废弃处理审核

**审核清单**：
- [ ] 废弃细项已标记 `~~已废弃~~`
- [ ] 废弃细项状态字段已更新
- [ ] 所有引用已追溯并标注废弃或已改为替代编码
- [ ] 引用方状态已正确评估（优先替代，避免过度级联废弃）
- [ ] 全局索引已更新废弃状态
- [ ] 文档清单已更新废弃状态

### 常见问题

**问题1：遗漏引用**
- 检查方法：使用 `grep` 同时搜索完整编码和简写编码
- 解决方案：补充标注遗漏的引用

**问题2：引用方状态评估错误**
- 检查方法：按决策树重新评估每个引用方
- 解决方案：修正评估结果，更新引用方状态

**问题3：索引未同步**
- 检查方法：对比细项状态和索引状态
- 解决方案：立即更新所有索引（全局 + 文档清单）

## 最佳实践

### 预防措施

1. **谨慎创建**：避免创建可能很快废弃的细项
2. **充分评审**：创建前充分评审必要性和稳定性
3. **依赖分析**：分析细项间的依赖关系

### 处理原则

1. **完整性**：确保废弃处理完整，无遗漏
2. **一致性**：遵循统一的废弃标记格式与全量编码（见 coding-system）
3. **及时性**：及时处理废弃和引用更新
4. **可追溯性**：保留完整的废弃历史

通过这套清晰的废弃处理规范，可以确保废弃细项得到规范、完整的处理。
