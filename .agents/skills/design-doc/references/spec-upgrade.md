# 规范版本与规范迁移

本技能（设计文档规范）频繁迭代。已有设计文档跟随升级时，靠三处**版本记录**界定「哪些已对齐、哪些待迁移」，并按本文判定每项调整是**维护性变更**还是**实质变更**。不对全部文档做一次性批量改写，也不因规范版本号变化而解冻文档。

## 三处记录

| 位置 | 字段 | 含义 | 何时更新 |
|------|------|------|----------|
| 作用域 `README.md`（单系统 / 子系统） | `规范版本目标` | 本作用域当前要求对齐到的规范版本（裸数字，如 `10.11`） | 升级技能后，作者确认[升级影响表](#升级影响表)，再把目标改为新版本（声明要求，不代表已完成） |
| 每份设计文档封面表 | `规范版本` | 本篇**已完成迁移或已核对确认无需迁移**时所对齐的规范版本 | 仅在**该篇**迁移或核对之后更新；未动的文档不改 |
| 产品基线 `baselines/vX.Y.yaml` | `spec_version` | 基线**创建时使用**的规范版本（加引号，如 `"10.10"`），仅追溯基线生成环境，**不代表**成员文档均已迁移到该版本 | 创建时写入；冻结后不改；PATCH 原样保留 |

取值均为裸数字 `主.次`，与 `SKILL.md` 的 `metadata.version` 同形。它**不是**产品版本（`vX.Y`），也**不是**文档修订版本号；三者互不替代。

三处记录统称**迁移元信息**。它记录迁移状态，不属于设计内容。三者回答三个不同的问题：

| 记录 | 回答的问题 |
|------|------------|
| 基线 `spec_version` | 这份基线是在哪一版规范下创建的 |
| 文档 `规范版本` | 这篇文档迁移 / 核对到了哪一版规范 |
| README `规范版本目标` | 当前作用域要求对齐到哪一版规范 |

**创建基线不受迁移进度约束**：立新基线（MINOR / MAJOR / 首份）时，若有文档的 `规范版本` 缺失或低于目标，`--bump-product` 只输出一条 INFO 提示数量，不阻止创建；产品发版与规范迁移互不阻塞。

## 判定规则

1. **目标与已装不一致**：`规范版本目标` ≠ 已装规范版本 → 检查器 WARNING。这是「有待跟进的升级」的正常信号，直到作者确认目标。
2. **逐篇待迁移**：文档 `规范版本` 低于作用域 `规范版本目标` → WARNING，列出该篇。检查器**不**据版本号大小判定是否需要改内容，判定以[迁移性质](#迁移性质判定)与升级影响表为准。
3. **文档超前**：文档 `规范版本` 高于已装规范版本 → ERROR。通常是技能回退或版本不一致，MUST 恢复对应版本的技能包后再校验。
4. **缺失**：文档缺 `规范版本` → WARNING（存量允许，不阻断）；新建文档由模板带入当前已装版本。
5. **迁移元信息不计修订**：只更新 `规范版本`（或 `规范版本目标` / `spec_version`）时，不递增文档 `修订版本号`、不写 `N（维护）` 行、不改基线。该字段本身即迁移记录。
6. **冻结基线只读**：历史基线不因规范升级而就地迁移。`spec_version` 保留其创建时的规范版本，作为该快照的历史记录。
7. **核对即可**：某篇按影响表判定无需改动时，核对后直接把 `规范版本` 更新为目标版本即可（不改内容，依第 5 条不写维护行）。这一步是「已确认无需迁移」的记录，不得省略，否则清单永远不收敛。
8. **归档文档不参与迁移**：`deprecated/` 下的归档文档是历史记录，保留原 `规范版本`（或缺失），检查器不统计、不提示。

## 迁移性质判定

规范迁移是**独立的文档维护活动**，默认归入**维护性变更**。判据是**应用设计的语义是否改变**，而不是规范是否新增了要求。

| 迁移情况 | 处理方式 |
|----------|----------|
| 纯格式、结构调整：章节顺序、表格、编号与引用格式、模板替换、内容迁移到新章节结构 | **维护性变更**，类型 `规范迁移` |
| 补充已确定但未记录的内容：设计早已决定，只是以前没有写进文档 | **维护性变更**，类型 `规范迁移` |
| 改变应用设计的决策、约束或验收口径：如新增强制设计内容并改变接口语义、权限划分或验收条件 | **实质变更**：正式文档解冻，修订号 +1，基线按既有流程立项 |
| 无法确认是否改变设计语义 | **实质变更**（拿不准按实质，现行原则） |

判定时注意：

- **规范新增要求 ≠ 设计改变。** 若新要求能用「把已有设计写下来」满足，属于维护；若必须做出新的设计决定才能满足，属于实质。
- **补记必须有依据。** 「补充已确定内容」须能指出依据：既有正式文字、已批准的决策、或现行实现。指不出依据的，一律按实质处理。
- **同一改动不得混合。** 规范迁移 MUST NOT 与实质变更、状态转换或基线动作放在同一改动或同一提交中（隔离原则）。
- 冻结态的规范迁移按维护流程留痕：`变更记录` 写 `N（维护）` 行，类型 `规范迁移`，说明末尾 `；语义不变`，细则见 [status-definitions.md · 维护性变更](status-definitions.md#维护性变更第三维度mandatory)。非冻结态（`初稿` / `草案`）直接改，不写维护行。
- 规范迁移 **MUST** 人审批准后单独成批执行（见 [maintenance-change.md](workflows/maintenance-change.md)）。

## 升级影响表

每个规范版本在本节登记一张影响表，作为规范发布时的说明，供作者逐篇判定。它只需回答「改什么、影响谁、是什么性质」，不做重型迁移项目。

| 列 | 含义 |
|----|------|
| 规范版本 | 引入该变更的版本 |
| 变更项 | 规则层面的变化（一条一行） |
| 影响文档类型 / 章节 | 哪些类型或哪些小节受影响 |
| 动作 | `需迁移`：该类文档须改内容；`仅新建`：只约束新建，存量不动；`不处理存量`：历史文档保持原样；`核对即可`：只需确认后更新 `规范版本` |
| 性质 | `维护`：格式、结构或补记，按规范迁移处理；`可能实质`：可能改变设计语义，发布时须列出受影响文档与章节，逐篇按[迁移性质](#迁移性质判定)判定 |

动作与性质取值均封闭。影响表缺失、或某行性质不明，视为规范缺陷，当轮补齐。

## 操作步骤

1. 升级技能包后运行 `check_docs.py`，查看「规范版本目标与已装规范不一致」。
2. 阅读本文件的版本记录与影响表，确认每行的动作与性质。
3. 把作用域 `README.md` 的 `规范版本目标` 改为新版本（声明要求）。
4. 逐篇处理「文档待迁移规范」清单，按迁移性质分流：
   - 格式、结构、补记 → 规范迁移维护批次：人审批准、同批完成、冻结态写维护行；
   - 改变设计语义 → 实质变更流程（解冻、修订号、基线）；
   - 无需改动 → 核对后仅更新 `规范版本`。
5. 清单清空、目标与已装一致后，本次升级结束。`规范版本` 是进度的唯一记录，不另建迁移清单文件。

## 与其他规则的边界

- 规范版本号**不进入**文档修订版本号、产品版本、基线 `full_version` 或 `items`。
- 规范迁移本身不触发基线 PATCH / MINOR / MAJOR：规范维护性更新不改 `items` 与 `revision`。是否发版由产品版本规则单独决定（见 [product-version.md](product-version.md)）。
- 子系统与系统根的规范版本见 [system-design-doc · version-alignment](../../system-design-doc/references/version-alignment.md)，该层只记作用域 README 目标，不逐篇记录。
