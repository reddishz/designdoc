# 信息安全威胁分析（STRIDE）

本文说明如何用 STRIDE 在安全相关的设计中系统地发现信息安全威胁。它是方法说明，不是需求分类体系：不新增类型码、属性、文档类型、检查器规则或迁移要求。何时检查由 [review-guidelines.md · 信息安全威胁审查](review-guidelines.md#信息安全威胁审查stride) 规定，设计入口见 L3《安全架构概要》与 L4 设计模板。

内容来源区分如下：

- 六类威胁的定义与方法说明：来源于下列 Microsoft Learn 页面，不追溯 STRIDE 的更早原始出处。
  - [Threats - Microsoft Threat Modeling Tool](https://learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-threats)：六类威胁定义
  - [Getting Started - Microsoft Threat Modeling Tool](https://learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-getting-started)：分析流程（建模、识别、缓解、验证）与信任边界说明
- STRIDE 与 ISO/IEC 25010:2023 子特征的对应：本规范的概念性整理，不是标准条款。
- 信息安全（Security）与产品安全（Safety）的边界：本规范依据现有质量属性分类作出的设计选择。

## 适用条件（指导性，非封闭清单）

设计涉及下列情形时，宜做威胁识别；都不涉及时，不必为形式而做：

- 外部网络接口、公开 API、Webhook、消息入口
- 身份认证、授权、角色、权限传递
- 敏感数据、个人信息、凭据、密钥、重要业务数据
- 跨组件、跨子系统或第三方系统交互
- 不可信输入：文件上传、外部命令、反序列化
- 资金、管理操作、关键状态变更等高影响行为

## 六类威胁

| 类别 | 含义 | 设计时问 |
|------|------|----------|
| S 身份伪造（Spoofing） | 冒用他人的身份信息 | 调用者的用户、服务、组件身份能否被冒充 |
| T 篡改（Tampering） | 恶意修改数据，含持久数据与传输中的数据 | 请求、消息、配置、存储数据能否被非法修改 |
| R 抵赖（Repudiation） | 否认做过某操作而无从举证 | 关键操作有无可信记录，事后能否确认是谁做的 |
| I 信息泄露（Information Disclosure） | 信息暴露给无权访问者 | 敏感数据、凭据、内部信息能否被未授权读取 |
| D 拒绝服务（Denial of Service） | 使合法用户无法使用服务 | 能否耗尽资源、阻断服务、影响正常用户 |
| E 权限提升（Elevation of Privilege） | 低权限者获得高权限 | 能否突破授权边界，越权调用 |

同一接口可涉及多类，也可能某些类不适用。不要求六类逐项填写，只记录有意义的威胁。

**与 ISO/IEC 25010:2023 信息安全子特征的概念对应**（辅助理解与 NFR 分类；不是 25010 或 STRIDE 原文规定的映射，也不是一一对应）：

| STRIDE | 主要关联的子特征 | 说明 |
|--------|------------------|------|
| S | 真实性 | 身份伪造影响身份真实性 |
| T | 完整性 | 未授权修改影响数据或系统完整性 |
| R | 不可否认性、可问责性 | 关键操作的证据与责任归属 |
| I | 保密性 | 未授权获取或披露 |
| D | 抵御性 | 对抗攻击；也可能影响可靠性 |
| E | 无直接对应子特征 | 核心是授权控制；具体后果可能涉及完整性、保密性、可问责性等，不强行归入单一子特征 |

识别出某类威胁，不自动产生一条 NFR；是否成立仍按产品质量目标与对外承诺判断。

## 分析步骤（轻量，不要求完整威胁建模流程）

1. **识别对象**：重要资产、参与者及身份、外部入口、组件与子系统、信任边界（不同实体各自控制的分界）、关键数据流。优先复用已有架构图、`IF`、`FLW`、`DOM`；不要求另画数据流图。
2. **检查六类**：围绕相关组件、接口、数据流和信任边界，考虑适用的类别。
3. **区分威胁、缺陷、风险**：威胁是可能发生的攻击方式；安全缺陷是现有设计缺少防护或防护不足；风险是结合系统环境，对某种不确定事件发生的可能性及其潜在后果进行判断，并考虑其对系统成功的影响。威胁不自动等于 `RSK`。
4. **落实到现有对象**：

| 内容 | 承接 |
|------|------|
| 对外安全承诺 | `FR` / `NFR`（`类别` 信息安全） |
| 外部法规、平台、合同要求 | `CON` |
| 架构级安全选择 | `ADR` / `DEC` / `PRN` |
| 安全组件与职责 | `CMP` |
| 接口认证、授权、签名、防重放契约 | `IF` |
| 内部安全处理流程 | `FLW` |
| 设计依赖的安全前提 | `ASM` |
| 尚未解决或后果不明确的风险 | `RSK` |
| 验收与测试 | `AC` / `TC` |

5. **验证缓解措施**：不仅看是否提出措施，还要看措施有无验证依据：`AC` / `TC`，或适当的设计评审证据；不要求每项措施都新增独立 `TC`。只写了防护措施，不能视为威胁已解决。验证措施有效也不等于威胁绝对不存在：仍存在的残余风险，按实际情况决定是否登记 `RSK`，不要求威胁归零。

## 记录方式

不要求单独的威胁报告。按复杂度在 L3–L5 文档用简短表格或正文说明即可（并非每个 L5 都要做，只是允许在适当层级承接分析结果），能看出：威胁是什么、影响、由什么设计处理、措施的验证依据、未解决事项是否登记 `RSK`。已有明确措施且无需单独追踪的威胁，直接写进设计正文，不必另编码。

## 与 RSK 的关系

STRIDE 用于发现威胁，`RSK` 记录可能影响项目成功的风险。只有结合系统环境，判断仍有尚未解决、后果不确定或可能影响项目成功的事项时才用 `RSK`，不要把每个威胁机械转成 `RSK`。涉及架构决策或质量目标的 `RSK`，写法见 [type-profiles.md · ADR 的质量目标影响与权衡](type-profiles.md#adr-的质量目标影响与权衡)。

## 边界

- STRIDE 只用于信息安全（Security）威胁识别，不替代产品安全（Safety）的危险识别、后果分析与故障安全设计，也不替代可靠性分析（见 [coding-system.md · 产品质量属性参考](coding-system.md#产品质量属性参考)）。
- D 威胁可能影响可用性，但服务可用性目标仍按可靠性等质量属性表达；NFR `类别` 仍按主要根因确定。
- 系统级只关注跨子系统信任边界、安全职责分配与关键交互威胁，不重复各子系统内部的分析；子系统内部由其自身 L3–L5 承接（见 system-design-doc）。
- 本文不扩展为安全开发生命周期、渗透测试或合规体系。
