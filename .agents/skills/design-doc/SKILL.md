# 产品设计文档规范（UED）

## AI 运行时配置解析规则

AI 在创建或编辑设计文档时，模板中的 `{当前用户.作者}` 与 `{项目编码}` 按当前作用域的 `README.md` 解析；额外配置文件 **已移除且 MUST NOT 继续创建或使用**。

**作用域判定规则**：
1. **单应用模式**：若业务文档直接位于 `ued/` 下，则 `ued/README.md` 同时承担入口、项目元信息、编码模式、编码计数器与全局索引。
2. **多应用模式**：若存在多个应用，则每个应用 **MUST** 位于 `ued/{app-name}/` 子目录下。
3. **多应用顶层 README**：`ued/README.md` 仅承担多应用总入口、应用注册表、公共规则与跨应用导航，**MUST NOT** 作为某个具体应用的项目编码来源。
4. **多应用应用级 README**：`ued/{app-name}/README.md` 承担该应用的项目元信息、编码模式、编码计数器、文档导航与应用级全局索引。

**解析顺序**（各字段分别按下列顺序取第一个可用值）：

**作者字段**：
1. 当前作用域 `README.md` 中的项目元信息字段（如 `author` / `maintainer`）
2. 运行环境可识别的当前执行主体标识（如工具可获取）
3. 默认值：`产品架构组`

**项目编码字段（高级扩展用法）**：
1. 当前作用域 `README.md` 中的项目元信息字段 `project_code`
2. 顶层 `ued/README.md` 的应用注册表中，与目标应用目录匹配的 `project_code`（仅多应用模式下辅助校验）
3. **默认值**：无（即禁用项目编码前缀，采用简洁编码格式）

**启用规则**：AI **MUST NOT** 启用项目编码前缀，除非已显式配置且请求发起方明确确认。默认情况下，一律采用简洁编码格式（如 `FR-001`）。

**提示规则（MANDATORY）**：
- 当 AI 识别到 `ued/` 下存在多个应用或多个独立业务域的设计文档时，**MUST** 提示将应用迁移到 `ued/{app-name}/` 子目录，并在顶层 `ued/README.md` 注册应用编码，同时在应用级 `README.md` 中定义 `project_code`。
- 当 AI 识别到当前仓库已存在某一应用的设计文档，而当前任务是在此基础上新增另一应用的设计文档时，**MUST** 在创建前提示采用多应用模式，并为新应用补齐子目录 `README.md` 与顶层应用注册表。
- 若尚未配置 `project_code`，AI **MUST** 先提示补充配置，再进入编码分配阶段；未获确认前，**MUST NOT** 擅自启用前缀。
- 上述提示的目标是确保多个应用并存时，编码、索引、引用与废弃追溯仍可保持全局唯一且语义清晰。

若作用域 `README.md` 不存在或未声明相应字段，首次使用时**直接采用默认值继续工作**：
- `author = 产品架构组`
- `project_code = (空)`

随后 AI **SHOULD** 提醒补充或编辑对应作用域的 `README.md` 元信息区块，特别是当检测到目录中存在多个应用或新增独立应用迹象时。

**项目编码规则（高级模式下）**：
- 长度：2-4位大写字母
- 只能包含字母 A-Z
- 有效示例：`CRM`、`ERP`、`CMS`、`COM`、`HRS`

**README 元信息最小字段（RECOMMENDED）**：
- `project_name`
- `project_code`
- `doc_mode`：`single-app` 或 `multi-app`
- `scope`
- `author` / `maintainer`

### 创建设计文档

## 核心原则

**一致性优先**：本 skill 包内（`SKILL.md`、`references/`、`assets/templates/`）对同一规则**只允许存在一种表述**。发现任何两处不一致（含措辞强度、适用范围、示例写法）即视为**规范缺陷**，**MUST** 在发现当轮合并为单一表述并修正其余处。同一规则的完整表述由最贴近的专项文件**单点承载**，其他位置一律以链接指针引用、不复述细则。

**措辞强度**：文中 MUST/SHOULD/「必须」「应当」等仅表示约束松紧，借鉴 RFC 2119 的常见含义，**非 RFC 认证要求**；统一定义见 [coding-system.md — 需求级别说明](references/coding-system.md#需求级别说明)。

**细项即 SSoT（最高优先总原则，MANDATORY）**：
- 细项编码（如 `FR-001`、`RUL-012`）和文档编码（如 `L2-003`）是唯一允许的稳定语义锚点。
- **MUST NOT**：在 `ued/` 设计文档中使用章节编号（如 `§x.y.z`、`第x章`、`见上文`）进行任何语义引用。
- 任何“规则/流程/算法/约束/背景结论”若可独立成立，**MUST** 先沉淀为细项定义并分配编码，再被其他内容引用。
- 写作、审查、复查、校验四个环节均执行“零章节编号引用”门禁：命中即不通过。

**单一事实来源（SSoT）**：
- 所有文档拥有唯一编号
- 所有明确细项拥有独立的全局唯一编码
- **编码 ID 与类型码绝对锁定**：一经分配，编码本身与其类型码 **MUST NOT** 被就地修改，**不区分状态**（类型码用错时：`初稿` 删除后重建、编号可回收，`正式` 只能废弃 + 新增）
- **标题自 `正式` 起锁定**：`初稿` 期可改标题，但 **MUST** 先扫描全部引用处并同步修改；`正式` / `草案` 期 **MUST NOT** 改标题，确需变更只能废弃 + 新增
- **存在性锁定按状态分级**：`初稿` 细项可整体删除（未发布，编号可回收、不计缺口，须同步清理引用与索引）；`草案` **MUST NOT** 直接删除（只能回退或废弃）；进入 `正式` 后 **MUST NOT** 删除或复用，废止只能标注"废弃"并保留
- 细项定义、细项编码清单、全局索引一律使用完整编码
- 互相引用一律使用唯一编码，必要时附带标题
- **定义块形态与属性行组三段**：每个细项定义位 MUST 为「锚点行 + 标题行（`{编码}：{标题}`，全角冒号）+ 属性行组」且三部分连续；属性行组 MUST 按「**治理段**（`细项状态` / `修订版本号` / `最后修订日期`）→ **内容段** → **追溯段**（`出处` → `来源`）」分三段，段位与段内顺序均固定（房规单点承载于 [coding-system.md · 细项定义块形态](references/coding-system.md#细项定义块形态mandatory)）
- 下层可引用上层，上层无需引用下层
- 任何层级均可引用 REF（外部参考资料）编码
- 当前作用域 `README.md` 的全局索引按类型码分组后，组内 **MUST** 按编码数字升序维护；新增细项必须插入到正确位置，**MUST NOT** 追加到小节末尾造成乱序。
- 编码计数器 **MUST** 仅维护“下一可用编号”；新增编码**取用**“下一可用编号”，**已正式化**编码序列必须完整；发现正式基线编号缺口必须先修复索引或废弃记录，**MUST NOT** 直接分配缺口编号（`初稿` 期被删除的编号可回收、不计缺口）。
- 变更记录/变更日志 **MUST** 按版本号或日期倒序维护，最新变更置顶。

**状态即基线（冻结判据，MANDATORY）**：
- 对象（文档 / 编码细项）是否冻结，**只看其 `状态`/`细项状态`，与版本库（git/svn）无关**。
- **状态是基本元素（MUST 存在）**：文档 `状态`、细项 `细项状态` 均为必备字段，取值统一为**标准四态** `初稿 / 正式 / 草案 / 废弃`，**新建即默认 `初稿`**。细项 `细项状态` 的承载位 **MUST 两处**：清单 / 全局索引表的 `细项状态` 列 + 定义块属性行组的**首行**（治理段第一位），缺任一处即违规，两处取值 **MUST** 一致。因历史版本差异缺字段时，按 `变更记录` 判定（有定稿条目 → `草案`；从未定稿 → `初稿`；**无法判定 → `草案`**），并纳入定稿确认（确认者升 `正式`，未确认 / 掠过者保持未冻结并补齐字段），不作为阻断性错误。
- **初稿 = 从未定稿的创作态**：除**编码 ID 与类型码**（绝对锁定）外，标题、正文、属性、描述、追溯关系均可原地编辑（改标题须同步全部引用处）；**不递增版本号**、**不走废弃流程**；不需要时**直接删除**。
- **正式 = 已冻结基线**：
  - 修订前 **MUST** 先执行 `正式→草案` 解冻（属受控状态变更，须请求确认），改完再 `草案→正式` 定稿。
  - 废止（彻底退场）才走废弃流程：`正式→废弃`（细项原地保留 / 文档两阶段归档）。
- **草案 = 从 `正式` 解冻而来的迭代态**：标题与编码同样锁定，正文 / 属性 / 追溯可编辑且**不递增版本号**；**MUST NOT** 直接删除——或 `回退` 到上一 `正式` 基线（版本号回到解冻前、内容回到上一基线，**变更记录完整保留**且该号不复用），或直接 `草案→废弃`（**最后版本号即该草案号**，不必先回退）。
- **版本号唯一正规递增时机 = `正式→草案` 解冻**：新建 `v1.0`（状态 `初稿`）→ 初稿期修改不变号 → `初稿→正式` 定稿本身即变更、**不再递增** → `正式→草案` 解冻时递增 → 定稿沿用该号 → 回退则回到解冻前的号 → `正式→废弃` / `草案→废弃` 不变。判定表见 [status-definitions.md · 变更流程与版本号](references/status-definitions.md#变更流程与版本号统一mandatory)。
- **锁定与基线的关系（正交，不冲突）**：编码 ID 与类型码的锁定是 SSoT 的第一优先级保证，绝对且与状态无关；标题与含义的锁定自进入 `正式` 起生效；`状态` 只决定"标题之外的内容能否直接改"与"能否删除"。`正式` 后的内容修订走解冻通道，**不构成**对编码锁定的违反；只有触及编码 ID / 类型码，或在 `正式` / `草案` 期改写标题与含义，才被禁止或须走废弃 + 新增。
- **细项修订版本号（与文档版本号独立演化）**：治理段的 `修订版本号` 是**细项级**修订计数——单个整数、新建为 `1`、**每轮 `正式→草案` 解冻 +1**（唯一递增时机）、**单调不回退**；`最后修订日期` MUST 与它**成对维护**（`YYYY-MM-DD`，只记修订号递增那天）。与文档 `版本`（`vX.Y`）、产品版本号**各自独立演化**，MUST NOT 互相推导或写成 `vX.Y`；文档解冻一轮，只有本轮**实际被修订**的细项 `+1`。两个字段属**流转伴随字段**——与文档 `版本` 同类、只是粒度不同，由 `正式→草案` 解冻动作写入，**MUST NOT** 当作独立的修改请求单独改动（不属记录型字段，MUST NOT 在任意状态随手追加）；写入时机见 [status-definitions.md · 流转伴随字段](references/status-definitions.md#流转伴随字段只随指定转换写入)，判定表见 [status-definitions.md · 细项修订版本号](references/status-definitions.md#细项修订版本号与文档版本号独立演化)。
- **层级门控（解冻自顶向下、定稿自底向上）**：细项状态机与文档状态机同构，且文档状态门控细项状态——要改细项内容，细项 MUST 处于 `初稿` / `草案`，故细项 `正式→草案` 解冻 **MUST** 先解冻所在文档（因此「细项 `草案` 而文档 `正式`」是**结构违规**）；文档 `→正式` 定稿 **MUST** 以「本文档全部细项 `细项状态` ∈ {`正式`, `废弃`}」为前置，未满足时 MUST 列出未定稿细项并**提示用户确认**。向已 `正式` 的文档**新增细项同受门控**，MUST 先解冻文档。细则见 [status-definitions.md · 层级门控](references/status-definitions.md#层级门控文档状态--细项状态mandatory)。
- **定稿提示**：审查 / 校验遇到未冻结对象（`初稿`、`草案`，含缺字段而按上述规则对待者）时，**MUST** 提示用户确认是否定稿；是否升格由人决定，AI **MUST NOT** 自行把 `初稿` / `草案` 改为 `正式`。
- 细则见 [references/status-definitions.md](references/status-definitions.md#状态即基线冻结规则mandatory)。

**模板与规范自洽（MANDATORY）**：
- `assets/templates/` 中的模板 **MUST 自身符合本规范**（状态字段齐备、引用一律编码化、不以章节编号定位、文件名与链接合规）。模板是 AI 的直接复制源，**模板违例等同于规范违例**，发现即修。
- 模板待复制正文的边界机制为 HTML 注释哨兵，**MUST NOT** 用 ` ```markdown ` 外层围栏包裹整篇正文；完整房规单点承载于 [assets/templates/index.md · 模板边界（哨兵）](assets/templates/index.md#模板边界哨兵)。
- 规范条文（`SKILL.md`、`references/`）**不纳入细项编码体系**——编码只作用于 `ued/` 下的设计对象，避免产生第二套编码命名空间。指向规范条款 **MUST** 使用 `文件#标题锚点`（如 `references/coding-system.md#编码含义锁定mandatory`），**MUST NOT** 使用 `§x.y`、`第 x 条`、`见上文` 等编号式引用。

**核心约束**：`ued/` 下所有文档**不得包含可执行代码和具体实现片段**。只允许设计性内容，例如算法、流程、状态、规则、逻辑、领域模型、接口契约、异常策略、配置约束与决策说明。

**层级使用约束（MANDATORY）**：
- **MUST NOT**：在未获请求发起方明确要求时，默认从 L0 一次性生成到 L6。
- **MUST**：按当前任务意图选择最小必要层级（通常单层或相邻两层）。
- **MUST**：当上游指令未指定层级时，先给出默认建议并按最小必要层级执行（默认优先 L2 或 L4），而不是先反问。
- **SHOULD**：仅在需要战略追溯时补写 L0/L1；仅在需要验证闭环时补写 L6。
- **SHOULD**：L0-L2 在未识别到相关语义前可暂不创建，待出现相关描述后再增补。

**例外情况**：REF（外部参考资料）部分不在此限制内。REF 文档可能包含外部资料中的代码示例、实现片段等引用内容，这些内容作为外部资料本身的组成部分，不受"不得包含代码"约束的限制。

**AI 操作约束（MUST COMPLY）**：
> **前提（锁定分三层，与状态正交）**：**编码 ID 与类型码**一经分配即**绝对锁定**，不区分状态；**标题**与**含义 / 正文 / 属性**的锁定自进入 `正式` 起生效（`初稿` 期标题可改、需同步引用，`草案` 期标题仍锁定）。完整表述由 [coding-system.md · 编码含义锁定](references/coding-system.md#编码含义锁定mandatory) 单点承载。
- **编码锁定（MUST NOT VIOLATE）**：
  - MUST NOT：修改已分配编码的 ID 或类型码（**任何状态**均适用）
  - MUST NOT：修改已 `正式` / `草案` 对象的标题，或已 `正式` 编码的业务含义
  - MUST：不受理上述请求；`初稿` 对象按"同步全部引用处后改标题"或"删除该细项后重新分配"处理，`正式` / `草案` 对象引导走废弃 + 新增
  - MUST：在分配编码前检查引用关系避免冲突；`初稿` 期改标题或删除前 **MUST** 先定位全部引用处（可用 `python3 scripts/check_docs.py --refs {编码}`）并同步修改
- **修改请求处置（MANDATORY）**：收到修改已分配编码 ID / 类型码（任意状态）、修改 `正式` / `草案` 对象标题、或修改已 `正式` 编码含义的请求时，一律不予执行，并给出对应正确流程
- **正确流程指导（REQUIRED）**：明确给出废弃+新增流程
- **冲突检测（MANDATORY）**：修改前必须检查编码引用关系
- **废弃标记规范（MUST COMPLY）**：
  - MUST：废弃流程作用于**已进入 `正式` 或处于 `草案` 的细项 / 文档**（`草案` 可直接废弃，最后版本号即该草案号）；`初稿` 对象要作废时**直接删除**（同步清理引用与索引），不走本流程
  - MUST：废弃细项时必须标记标题删除线 `~~已废弃~~`（视觉标记），结构化状态值统一写 `废弃`
  - MUST：废弃细项必须包含四个必须字段：细项状态、废弃时间、废弃原因、替代方案
  - MUST：废弃后必须更新全局索引和文档清单
  - MUST：涉及大规模废弃时必须请求外部确认
  - MUST：整份文档废弃时，除上述字段外须给出**建议归档日期**，到期后移入本作用域的 `deprecated/`（只归档不删除，各子项目各自独立）；细项废弃**不归档、不删除**，原地保留备查
  - 细项废弃流程见 [references/item-deprecation.md](references/item-deprecation.md)，文档废弃流程见 [references/doc-deprecation.md](references/doc-deprecation.md)

### 写作与审查统一门禁（MANDATORY）

为修正“新写文档与审查文档都无法消除章节引用”的问题，本 skill 在总入口层统一以下门禁：

1. **起草门禁（Before Draft）**：AI 在起草前必须声明“引用仅可使用细项编码/文档编码”。
2. **落码门禁（Before Save）**：正文出现可独立语义时，必须先落细项编码，再允许被其他段落引用。
3. **审查门禁（Review）**：审查时若发现任何章节编号引用，直接判定 A 级阻断并退回修正。
4. **复查门禁（Re-Review）**：复查必须确认“零章节编号引用 + 引用全为编码化引用”。
5. **发布门禁（Before Merge）**：若未通过上述任一门禁，禁止进入合并或正式发布状态。

## 快速操作指南

### 创建新文档

1. **环境初始化**：使用 `LS` 或 `Read` 确认 `ued/` 目录结构。
2. **选择层级**：根据任务意图（L0-L6）从 `assets/templates/` 读取对应模板；**默认按需裁剪，禁止无指令全量生成 L0-L6**。
3. **内容生成**：按模板结构生成内容，**MUST NOT** 包含具体实现代码。
4. **外部确认（Checkpoint 1）**：生成初稿后，**MUST** 暂停，等待请求发起方确认文档大纲与核心细项。
5. **编码分配**：确认后，遵循“分配新编码”流程分配 ID。
6. **索引同步**：立即更新当前作用域 `README.md` 与文档末尾清单（细项清单与全局索引的**状态列默认写 `初稿`**）。
   - 单应用模式：更新 `ued/README.md`
   - 多应用模式：更新 `ued/{app-name}/README.md`；仅当涉及应用注册或跨应用导航时，再更新顶层 `ued/README.md`
7. **自检与优化**：完成后，AI 应主动检查文档逻辑一致性，并输出 1-2 条后续优化建议。
   - **一致性检查**：检查新定义的细项是否与上层目标存在潜在冲突。
   - **颗粒度检查**：检查细项标题是否适度宽泛，避免过度具体（参考 [coding-system.md · 标题命名规范](references/coding-system.md#标题命名规范适度宽泛)）。
   - **合规性审查（MANDATORY）**：使用本技能的审查规则评审刚做的修改：
     - 编码锁定合规性：是否违反了编码含义锁定原则？
     - 约束强度检查：是否正确使用了MUST/MUST NOT等强制性表述？
     - 流程规范性：是否遵循了编码分配和废弃的正确流程？
     - 文档一致性：是否保持了所有相关文档间的约束表述一致？

### 分配新编码

**强制流程**（必须严格遵循）：
1. **读取计数器**：读取当前作用域 `README.md` 中的"编码计数器"，必须读取对应类型码的“下一可用编号”。
   - 单应用模式：读取 `ued/README.md`
   - 多应用模式：读取目标应用目录下的 `README.md`
2. **获取编号**：一律使用计数器中的“下一可用编号”；若发现**已正式化**编号缺口，必须先按审查/校验规则修复索引一致性，**MUST NOT** 直接分配缺口编号（`初稿` 期被删除的编号可回收，不属缺口）。
3. **冲突检测**：使用 `Grep` 或 `SearchCodebase` 确认目标编码在 `ued/` 目录下未被使用。
4. **外部确认（Checkpoint 2）**：如果是批量新增或涉及核心业务规则变更，**MUST** 暂停并请求确认编码标题与定义是否准确。
5. **按序插入索引**：在当前作用域 `README.md` 的对应类型码索引表中，按编码数字升序插入新行，**MUST NOT** 直接追加到小节末尾。
6. **即时更新**：更新文档清单 + 全局索引 + 编码计数器；“下一可用编号”必须递增到新分配编号的后一位。
7. **验证一致性与排序**：确认正文、文档清单、README 索引三方一致，类型码索引升序、编码序列无缺口、变更记录倒序。
8. **大规模变更确认（Checkpoint 3）**：涉及大规模编码变更或废弃时，**MUST** 在执行前请求二次确认。

### 处理编码含义变更请求

**违规行为识别与拒绝**：
响应触发条件（三类）：（a）修改**已分配编码的 ID 或类型码**——**不区分状态**，绝对锁定；（b）修改已进入 `正式` 或处于 `草案` 对象的**标题**；（c）修改**已进入 `正式` 基线**编码的业务含义。`初稿` 对象的标题修改（需同步引用）与 `初稿` / `草案` 对象正文 / 属性 / 边界描述的编辑不属此列。AI **MUST** 按以下方式响应：

```
❌ 违规检测：禁止就地修改编码 ID / 类型码（绝对锁定）；禁止修改 `正式` / `草案` 对象的标题；禁止修改已正式化编码的业务含义
⚠️  系统约束：编码 ID 与类型码一经分配永不修改（与状态无关）；标题与业务含义自进入正式基线后永不就地修改
✅ 正确流程：
1. 判定对象状态：`初稿` → 走下方"初稿处理"；`正式` / `草案` → 走下方"废弃 + 新增"
2. 初稿处理：改标题 → 先用 `check_docs.py --refs {编码}` 定位全部引用处并同步修改；类型码用错 → 确认后删除该细项，再按分配流程重新创建（未发布编号可回收、不计缺口）
3. 正式 / 草案废弃：外部确认 → 标注原编码为"废弃"并记录原因 → 为新含义分配下一个可用编码（如 FR-016）
4. 影响评估：提示检查受影响的下层引用关系
```

> 若诉求仅是**修订 `正式` 编码正文内容而不改变其含义与标题**，不属于违规：按 `正式→草案` 解冻（**此时递增版本号**）→ 修订 → `草案→正式` 定稿。

**AI 响应模板**：
```
检测到请求修改已分配编码 [{编码}] 的{标题/含义}。

根据编码锁定原则：编码 ID 与类型码一经分配即不可修改；标题与含义自进入 `正式` 后不可就地修改。
建议处理方式：
1. （初稿）同步全部引用处后修改标题，或删除该细项后按分配流程重建；（正式 / 草案）废弃原编码 [{编码}]（原含义：{原标题}）
2. 分配新编码承载新标题 / 新含义

是否确认执行废弃操作？
```

### 废弃细项处理

**核心要旨**：
- 废弃细项必须保留，标注废弃状态
- 反向追溯所有引用，同步标注废弃
- 废弃状态可以传播，导致引用方也废弃

**外部确认（Checkpoint 4）**：在将 `正式` 或 `草案` 细项标注为 `废弃` 前，**MUST** 暂停并请求确认废弃原因及替代方案（`草案` 可直接废弃，最后版本号即该草案号）。（`初稿` 细项要作废时直接删除并同步清理引用，不触发本流程。）

**标记格式**：废弃 MUST 保留该细项原有的定义块形态（`<a id>` 锚点行 + 标题行加 `~~已废弃~~` 后缀 + 具名属性行），并补齐四个必备字段：`细项状态`（值 `废弃`，即治理段**首行**，就地改值不挑位置），以及紧随治理段的 `废弃时间`、`废弃原因`、`替代方案`（无替代时填「无」）。

> 标题删除线 `~~已废弃~~` 为视觉标记；结构化状态值统一写 `废弃`。**MUST NOT** 把属性行写成裸段落，也 **MUST NOT** 因废弃而删掉锚点行——引用方仍要跳得到。

**完整格式与示例**单点承载于 [references/item-deprecation.md · 第一步：标记细项废弃](references/item-deprecation.md#第一步标记细项废弃)，四个必备字段的取值口径见同文件[《标准标记格式》](references/item-deprecation.md#标准标记格式)。

**详细操作流程**：完整的废弃流程、引用追溯、索引更新等操作请参见 [references/item-deprecation.md](references/item-deprecation.md)。

### 废弃整份文档处理

**核心要旨**：
- 采用**两阶段**：先在原地标注 `废弃` 并给出**建议归档日期**（不移动），到期后**归档**入本作用域 `deprecated/`（`ued/deprecated/` 或 `ued/{app-name}/deprecated/`）。
- 每个子项目各自独立维护自己的 `deprecated/`，**不使用顶层共享目录**；**只归档、不删除**。
- 不存在也不需要 `active/` 目录；活跃与原地废弃文档同处作用域目录。

**详细操作流程**：请参见 [references/doc-deprecation.md](references/doc-deprecation.md)。

### 修改完毕：定稿确认与提交提示

**触发时机**：AI 每完成一轮 `ued/` 下文档的实质修改后，收尾时**主动**执行以下流程。此为 **Checkpoint 5（定稿确认）**，也是"状态即基线"的操作化闭环——给未冻结对象一个自然晋升窗口，同时避免"AI 自做主张升格"。

**执行步骤（MUST COMPLY）**：

1. **提交提示**：向用户询问"本轮修改已完成，是否需要提交到版本管理系统（git / svn）？"。用户若答"暂不提交"，跳过 2–4，所有未冻结对象保持不变。
2. **未冻结扫描**：用户确认要提交时，**仅扫描本轮 AI 实际修改过的文件**（判定依据 = 本轮会话中 AI 自身执行过创建 / 编辑操作的文件清单，不依赖 git / svn 差异；无法确定时只提示、不扫描），收集处于 `初稿` 或 `草案` 的对象：
   - **文档级**：元信息表 `状态 = 初稿 / 草案` 的整份文档；
   - **细项级**：正文带 `**细项状态**：初稿 / 草案`，或索引/清单表状态列为 `初稿 / 草案` 的编码；
   - **缺字段**：本轮触及的对象若**没有** `状态` / `细项状态`（历史版本遗留），按 `变更记录` 判定（有定稿条目 → `草案`；从未定稿 → `初稿`；无法判定 → `草案`）一并列入，升格时补齐字段。
3. **呈现与确认**：以紧凑表格一次性列出（标明 `初稿` / `草案` 两类），请求用户逐项或批量确认。支持"全定稿 / 全保留 / 除 X,Y 外全定稿 / 逐项指定"等批量口径。
4. **执行升格与提交**：
   - 用户**明确确认**的对象 → 状态改为 `正式`；**定稿本身不递增版本号**（新建文档定稿仍为 `v1.0`；解冻修订轮次沿用 `正式→草案` 时已递增的号）；缺字段的对象在升格时补写 `状态` / `细项状态`。
   - **升格顺序 MUST 自底向上**：批量定稿时先升**细项**、再升**文档**（层级门控要求文档 `→正式` 以全部细项已定稿为前置）；若用户只确认文档而未确认其下细项，**MUST** 回指上表列出待定稿细项并请示，不得先升文档。
   - 用户**未提及 / 略过 / 不确认**的对象 → **保持未冻结**（`初稿` / `草案`），不改动状态或版本。
   - 升格完成后，按用户指示执行 `svn commit` / `git commit`（是否 push 另请示），或交回用户自行提交。

**约束（MUST NOT）**：
- AI **MUST NOT** 未经用户明确确认擅自把任何 `初稿` / `草案` 改为 `正式`。
- AI **MUST NOT** 扫描并提交本轮**未修改**的历史未冻结对象——那属于 `check_docs.py` 或人工审查的静态提示范畴。
- AI **MUST NOT** 代用户删除 `草案` 对象（`草案` 只能由人决定回退或废弃）；`初稿` 对象的删除也须先经确认并同步清理引用与索引。
- 未提及 = 未确认 = 保持未冻结。

### 检查工具

- **静态检查脚本**：[scripts/check_docs.py](scripts/check_docs.py)，对 `ued/` 做格式与一致性校验（编码格式 / 唯一性 / 升序 / 缺口与计数器、状态取标准四态与旧值迁移提示、正文定义与文档清单与全局索引三方一致、标题与引用处一致、定义块形态与属性行组三段、修订号不变式、层级门控、版本递增时机与回退记录完整性、废弃字段（含 `替代方案` 值形态）与建议归档日期、REF 时效字段与复查周期、PLN 落实闭环、锚点可达性、章节编号引用）。
- **引用反查**：`python3 scripts/check_docs.py -p <ued 路径> --refs {编码}`，列出该编码的全部定义 / 登记 / 引用位置；`初稿` 期改标题或删除前 **MUST** 先执行。
- **模板哨兵自检**：`python3 scripts/check_docs.py --check-templates`，校验 `assets/templates/` 的哨兵成对、整篇型模板唯一 H1、无残留外层围栏、使用说明未混入待复制正文。
- **模板实例化预览**：`python3 scripts/check_docs.py --instantiate {模板文件名} [--segment {段名}]`，剥除哨兵输出实例化后的正文，用于评估渲染效果；多段模板（`ref.md`、`readme-template.md`）用 `--segment` 取单段。
- **规则回归集**：`python3 scripts/tests/run_fixtures.py`，用 [scripts/tests/fixtures/](scripts/tests/fixtures/) 下 23 条最小文档夹具断言 19 条校验规则的命中与不命中（每条夹具只验证一条规则，跑台只断言目标问题名、忽略夹具极简结构带来的噪声）。修改 `check_docs.py` 后 **MUST** 跑一遍，退出码非 0 即规则退化；新增校验规则 **MUST** 同时补正反夹具并登记入跑台的期望表。
- 该脚本只输出**静态提示**，不代替人工内容审查，也不代替使用者对未冻结对象（`初稿` / `草案`）的定稿确认。

## 使用场景

### 适用场景

- ✅ 创建产品设计文档（L0-L6）
- ✅ 审查现有设计文档
- ✅ 分配和管理编码
- ✅ 处理文档废弃和更新
- ✅ 维护编码体系完整性

### 不适用场景

- ❌ 代码实现和部署文档
- ❌ 用户手册和操作指南
- ❌ 技术实现细节
- ❌ 运维和监控文档

### 默认起步建议（实战）

- **最常见起步**：L2（系统/产品需求）+ L4（逻辑/系统设计）
- **可选补充**：需要业务背景再补 L0/L1；需要验收闭环再补 L6
- **禁止误用**：不要把“完整层级能力”理解为“AI 每次都必须产出 L0-L6”

### 层级自动识别建议（先建议后补齐）

- **L0 触发信号**：出现愿景、商业目标、成功指标、路线图主题
- **L1 触发信号**：出现角色分层、利益相关者诉求、业务场景冲突
- **L2 触发信号**：出现明确功能需求、非功能约束、验收口径
- **执行策略**：未命中触发信号时先不建对应层；命中后再补建并建立追溯引用

## 常见问题

**Q: 如何分配新编码？**
A: 必须遵循编码分配强制流程，读取计数器→搜索确认→分配编码→立即更新索引。

**Q: 可以修改已分配编码的标题或含义吗？**
A: 编码 ID 与类型码**任何时候都不可就地修改**（绝对锁定，与状态无关）；标题与业务含义自进入 `正式` 起不可就地修改。`初稿` 要改标题 → 先扫描并同步全部引用处再改；类型码用错 → 删除该细项后重新分配；`正式` / `草案` 要改标题或变含义 → 废弃 + 新增。仅改正文内容而不触及含义与标题的修订，走 `正式→草案` 解冻（**此时递增版本号**）再定稿。

**Q: `初稿` 与 `草案` 有什么区别？**
A: 二者都未冻结，区别在**是否曾定过稿**：`初稿` 从未进入基线，标题可改（须同步全部引用处）、可整体删除（编号回收）；`草案` 是 `正式` 对象解冻后的迭代态，标题与编码锁定、**不可直接删除**，只能 `回退` 到上一 `正式` 基线（版本号回到解冻前、变更记录完整保留、该号不复用）或直接 `废弃`（最后版本号即该草案号）。

**Q: 定稿（`初稿→正式`）要升版本号吗？**
A: **不升**。定稿本身就是一种变更；版本号的唯一正规递增时机是 `正式→草案` 解冻。新建文档默认 `v1.0` + `初稿` 状态，初稿期反复修改也不变号；解冻后 `草案→正式` 定稿沿用解冻时已递增的号。

**Q: 存量文档里的 `草稿` / `提议` / `采纳` / `使用中` / `验证状态` 等旧写法怎么处理？**
A: 一律映射到标准四态与统一字段名，就地改写即可，**不解冻、不递增版本号、不追加 `变更记录`**。完整映射表见 [references/status-definitions.md · 存量文档迁移](references/status-definitions.md#存量文档迁移)；`check_docs.py` 对旧值不判无效，而是以 INFO「状态值待迁移」提示、不阻断校验。

**Q: 这个 skill 是给谁用的？**
A: 这是给 AI 用的执行规范，不是给人类阅读的写作教程。其核心目标是把 AI 的文档生成、修改、审查、编号、废弃和停顿点统一成可重复执行的规则集合。

**Q: 废弃的细项如何处理？**
A: 废弃细项必须遵循以下核心要旨：
1. 标题必须添加 `~~已废弃~~` 删除线（视觉标记），结构化状态值统一写 `废弃`
2. 必须包含四个字段：细项状态、废弃时间、废弃原因、替代方案（如无则填"无"）
3. 必须更新全局索引和文档清单
4. 必须追溯并处理所有引用关系
5. **原地保留，不移动**

详细操作流程（反向追溯、引用处理、索引更新等）请参见 [references/item-deprecation.md](references/item-deprecation.md)。

**Q: 废弃整份文档与废弃细项有何不同？**
A: 细项废弃只在原地标注（**不移除、不删除**，留在设计文档中备查）；整份文档废弃采用**两阶段**——先原地标 `废弃` 并给出**建议归档日期**，到期后**归档**入**本作用域独立**的 `deprecated/`（`ued/deprecated/` 或 `ued/{app-name}/deprecated/`），**只归档不删除**，不存在也不需要 `active/` 目录。详见 [references/doc-deprecation.md](references/doc-deprecation.md)。

**Q: 文档中可以包含代码吗？**
A: L0-L6 设计文档不可以包含可执行代码、脚本、SQL、配置片段等实现内容；但可以包含算法、流程、逻辑、模型、约束、状态机和决策说明。REF（外部参考资料）文档不在此限制内，可以包含外部资料中的代码示例和实现片段作为引用内容。
